# 확인한 유리 지지 높이와 실험실 → 프로젝트 저장 연결

2026-09-13. 사진 재구성 전체 목표는 아직 미완료다. 이번 변경은 사용자 보정의 지원 범위와 실제 프로젝트 저장 연결을 확장한다. 자동 관측 모델과 기하 추론을 새로 개선하거나 후보 엔진을 기본으로 채택한 결과가 아니다.

## 바뀐 동작

- 실험실의 기존 분석·개선 후보·사용자 교정 결과마다 **이 결과로 공간 만들기**를 제공한다. 현재 보이는 완료 결과의 장면·원사진·불변 자재 버전·원관측과 보정 스냅샷을 로컬 프로젝트에 함께 저장한다. 아직 결과를 생성하지 않은 편집 칸 변경은 저장하지 않는다.
- **만든 공간 열기**로 실제 편집기에 들어간다. Before는 선택한 재구성 장면이고 After는 같은 공간 크기·카메라의 빈 공간이다. PNG 한 장을 평면에 붙여 프로젝트로 위장하지 않는다. 설비와 타일은 기존 장면 데이터다.
- 이미지·자재 버전·프로젝트는 IndexedDB의 한 트랜잭션에서 확정한다. 오류나 커밋 전 취소는 모두 되돌리고, 커밋 뒤 취소는 성공한 프로젝트를 보존한다. 같은 결과를 재시도해도 이미 만든 프로젝트와 이후 편집을 덮어쓰지 않는다.
- 원래 실험실 기록의 자산·자재 버전 참조도 `shared.comparison.labSource`에 따로 보존한다. Before를 수정하거나 이력에서 빠졌다는 이유만으로 원기록에 필요한 자료를 정리하지 않는다.
- 유리 파티션의 바닥 좌표 배치에 **욕조 테두리 위 / 샤워 턱 위**와 높이 입력을 추가했다. 일반 바닥 제품의 접지 검사는 그대로이고, 명시된 유리 지지면에 대해서만 하단 높이를 검사한다. 방 밖이나 천장을 넘는 입력은 자동 축소·이동하지 않고 거절한다.
- 실험실과 실제 Before 속성 모두 지지 종류·높이를 수정할 수 있다. 높이와 `baseHeightMm`를 함께 바꾸며 기본값과 사용자 입력 출처를 구분한다. 다른 종류로 바꾸면 유리 전용 지지 정보를 해제한다.

## 구조와 보존 조건

`lab.ts`는 메모리 저장소 정리 전에 선택적 `projectBundle`을 돌려준다. 보고서 JSON에는 Blob을 넣지 않는다. `lab-project.ts`의 명시적 저장 API가 보고서와 묶음의 실행 ID·입력·장면 일치를 검증하고, `projects.createWithResources`의 로컬 원자적 저장을 사용한다. 조회·분석·교정만으로 프로젝트를 저장하지 않는다.

UI는 `LabProjectAction`에서 기존 `useAccess`의 쓰기 권한을 따른다. 서버 모드에서는 이 저장을 실행하지 않으며 로컬로 조용히 전환하지 않는다. 새 AI 호출, 사진 외부 전송, Supabase 연결·배포, 제품 배경 제거/TripoSR 변경은 없다.

새 지지면은 `RaisedGlassSupport`의 사용자 확인 데이터다. **욕조나 턱을 검출하거나 지지 물체와 연결한 데이터가 아니다.** 지지 물체의 형상을 새로 만들지 않고 이동·높이 변경에도 자동 연동하지 않는다. 그래서 턱이 그려지지 않은 장면에서는 유리가 떠 보일 수 있다. 높이를 0으로 낮춰 성공 수를 늘리지 않았지만, 원사진의 지지 관계를 완전히 재현한 것으로도 보지 않는다.

## 실제 브라우저 검증

- 저장된 실제 user-04 관측 → 현재 UI의 교정 4설비 → 저장 오류 주입/재시도 → 실제 프로젝트 편집기 → Before/빈 After → 새로고침 → 4096×1366 비교 PNG: Playwright **1개 통과**. 테스트 파일 `e2e/reconstruction-lab-project.spec.ts`, 결과 `test-results/reconstruction-lab-project-ui-20260913/`.
- 원자적 취소 검사는 `assets.add`의 1회 `QuotaExceededError` 주입이다. 실제 디스크 용량을 소진한 시험은 아니다. 실패 시 프로젝트·자산·버전이 남지 않고 현재 결과는 유지되었다.
- 최초 관측은 실제 모델의 저장 보고서를 재생했으며, 이후 교정·렌더·저장·재진입은 현재 앱 코드다. AI·외부 요청·pageerror는 0. 이 시험은 새로운 AI 인식 성공이 아니다. 20.9초는 기능 시험 전체 시간이며 단독 처리 성능 수치가 아니다.
- user-01: 사용자 역할로 확인한 욕조 테두리 높이 600mm에서 유리를 포함한 핵심 6설비를 렌더했다. 기존 보정 방향을 유지해 유리가 옆모습으로 좁게 보이며 방향 정확도 개선으로 주장하지 않는다.
- user-03: 사용자 역할로 확인한 샤워 턱 높이 100mm에서 유리를 포함한 핵심 4설비를 렌더했다. 유리 뒤 타일이 보이고 PNG와 표시 Blob이 일치한다. 지지 높이 스냅샷 복원을 확인했다. user-04의 4설비도 보정 회귀에 사용했다.
- 유리 사례 결과는 `test-results/reconstruction-raised-support-20260913/`에 있다. 높이·위치는 실측이 아니며 원모델 원문과 자동 관측은 유지했다. 세 장의 보정 실행에 새 Worker·모델 POST는 없었다.

## 자동 배치에서 남은 원인

`test-results/reconstruction-contact-anchor-investigation-20260913/`에 실제 저장된 8장 입력·보고서 및 소스 해시와 재현 수치를 남겼다. 관측 재사용 7개 중 6개의 몸체 범위 검사가 실패한다. 5개는 뒤쪽 벽, 1개는 왼쪽 벽을 넘는 계산이다.

보이는 바닥 다각형을 물리 바닥 직사각형으로 대응시키는 기본 범위와, 사진 하단을 제품 앞쪽 접점으로 해석하는 가정이 함께 작용한다. 단순한 부호 오류로 확인되지 않았다. 제품 깊이의 절반을 다른 상수로 바꾸거나 낮은 IoU를 일괄 허용하면 잘못된 배치를 성공으로 만들 수 있어 이 조사에서는 배치 코드를 바꾸지 않았다.

이전 고정 소스의 8장 자동 결과와 이번 사용자 보정/저장 기능 시험을 합산하지 않는다. 자동 설치 면·접점 추론, 실제 지지 물체의 형상·연결, 사람이 필요한 최소 보정 비용은 다음 개선 대상으로 남아 있다.

## 통합 검사

최종 `npm run lint`, `npm run typecheck`, `npm run test`가 모두 통과했다. Vitest는 **88개 파일 1,036개 테스트** 통과다. 이후 `npm run build`(23.415초)와 `npm run build:vinext`(51.503초)를 순차 실행했고 모두 종료 코드 0이다. 기록은 `test-results/reconstruction-support-project-20260913/checks-final.json`과 각 로그에 있다. 첫 타입 검사에서는 새 테스트의 optional 메서드 spy 타입 오류를 발견했고 실제 구현의 메서드 존재를 확인해 타입을 좁히도록 테스트를 수정했다. 처음 실패 로그도 보존했다. 기존 punycode/glob 및 Vite 확장자 경고는 별도 로그에 남으며 배포는 하지 않았다.

추가 Before 속성 브라우저 검사는 합성 유리 한 개로 실제 UI→모형 생성→브라우저 IndexedDB를 실행했다. 기본 600mm/default를 500mm/user로 바꾸고 undo/redo·저장·재읽기를 확인했다. 바닥 직접 설치와 변기로 종류 변경 시 지지 정보가 해제된다. 이 결과는 실제 사진 인식 평가와 구분하며 `test-results/reconstruction-raised-support-20260913/before-properties/verification.json`에 기록했다.

메모리 최고 사용량은 이번 기능 시험에서 측정하지 않았다. 저장 보고서·자산 묶음의 크기와 페이지 heap, 모델·GPU 메모리를 같은 수치로 취급하지 않는다.

빌드 후 로컬 `/`, `/materials`, `/reconstruction-lab`의 HTTP 200 응답도 확인했다. 기록: `test-results/reconstruction-support-project-20260913/health.json`.
