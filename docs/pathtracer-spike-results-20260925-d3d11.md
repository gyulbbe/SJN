# 경로 추적 1b단계: D3D11 무효 출력 원인과 컴파일 시간 · 2026-09-25

[작업 프롬프트](prompts/pathtracer-stage-1b-d3d11-investigation.md)의 결과다. 이전 단계는 [0–1단계 결과](pathtracer-spike-results-20260925.md)에 있다. 브랜치는 `claude/pathtracer-spike`이고 커밋하지 않았다. 사용자 동작·운영 코드·`renderer.ts`는 이번에 바꾸지 않았다. AI 호출은 없고, 웹은 읽기 검색만 했다. 2단계는 시작하지 않았다.

**알려진 이슈(읽기 전용 검색):**

- [three-gpu-pathtracer #325](https://github.com/gkjohnson/three-gpu-pathtracer/issues/325): D3D11 셰이더 내부 컴파일 오류(잘못된 바이트코드) 보고가 있다.
- [#464](https://github.com/gkjohnson/three-gpu-pathtracer/issues/464): 검은 삼각형(Mac M2)이 MIS 관련으로 보고됐다.
- 같은 증상(D3D11에서 물체 전부 0)의 이슈는 찾지 못했다. 새 이슈는 올리지 않았다.

D3D11의 디스크 캐시 효과는 셰이더 소스가 같을 때만 확실하다. 51.6초 실행은 부분 적중으로 보인다.

컴파일을 줄이는 define도 확인했다.

- `FEATURE_DOF`, `FEATURE_BACKGROUND_MAP`, `FEATURE_FOG`는 `onBeforeRender`가 장면에 맞춰 덮어쓴다. 안개 재질이 없으면 이미 0이다.
- 사용자가 고를 수 있는 것은 `FEATURE_MIS`, `FEATURE_RUSSIAN_ROULETTE`, `RANDOM_TYPE`이다. `FEATURE_MIS`를 끄면 Spot·Point·Directional 조명을 쓸 수 없다(README).
- D3D 출력 자체가 무효라 시간 측정은 하지 않았다.

## 대체 감지: 자가 검사

`selfTest()`(64×64, 흰 평면 + 균일 하늘 1, 2샘플)의 규칙은 가운데 8×8 평균이 0.5–2이고, 유한값이고, alpha가 1이면 통과다.

| 백엔드      | 평균                                             | 판정 | 올바른가                                             |
| ----------- | ------------------------------------------------ | ---- | ---------------------------------------------------- |
| Vulkan      | 0.93                                             | 통과 | 예                                                   |
| D3D11       | 0, alpha 0                                       | 실패 | 예                                                   |
| SwiftShader | 약 1.38(이전 픽셀 규칙 실행의 4픽셀 값으로 계산) | 통과 | 출력은 맞다. 다만 렌더러 이름 규칙으로 따로 제외한다 |

- 처음에는 픽셀 하나씩 0.5–1.5인지 봤다. 2샘플 노이즈(0.6–1.8) 때문에 정상인 Vulkan도 실패로 나와서 평균 규칙으로 바꿨다.
- 이 검사는 본 렌더와 같은 셰이더를 쓰므로 냉간 컴파일 비용(D3D11에서는 수 분)을 먼저 떠안는다. 5단계에서는 "자가 검사 실패 또는 시간 초과면 래스터 내보내기"로 쓴다.

## 2단계 의견

**보류한다.** Windows Chrome은 기본으로 ANGLE D3D11을 쓰고, 사용자가 `chrome://flags`를 바꾸게 할 수는 없다. 이 백엔드에서 출력이 무효이고 첫 컴파일이 수 분이면, 대다수 데스크톱 사용자에게는 대체 경로만 보이게 된다. 계속하려면 다음 중 하나가 필요하다.

1. **D3D 문제 우회:** 변환된 HLSL 비교, 셰이더 분할·단순화를 upstream과 함께 하거나 자체 포크한다. 성공 여부가 불확실하고 비용이 크다.
2. **WebGPU 기반 경로 추적:** Chrome Windows의 WebGPU는 D3D12를 직접 쓴다. three.js WebGPURenderer 기반 구현이 필요하고 라이브러리 성숙도는 미확인이다(upstream [WebGPU 지원 이슈 #547](https://github.com/gkjohnson/three-gpu-pathtracer/issues/547)).
3. **서버 렌더:** 비용이 들고 인프라가 필요하다.
4. **FLUX 결과 개선 또는 래스터 사실감 추가 개선:** 이미 동작하는 경로를 다듬는다.
