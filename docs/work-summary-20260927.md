## 1. 휴대폰 사진(Ultra HDR·모션 포토) 업로드

- **문제:** 요즘 Android·iPhone 카메라 JPEG이 "손상된 이미지이거나 지원하지 않는 형식이에요"로 모든 사진 입력에서 거부됐다.
- **원인:** 서버 업로드 검사(`validateD1Image`)가 두 경우를 거부했다.
  - JPEG 안의 APP2 `MPF`(여러 장 목록)
  - 파일 끝이 `FFD9`가 아닌 파일
  - Ultra HDR은 기본 JPEG 뒤에 HDR 게인 맵 JPEG을 붙이고 MPF로 가리킨다. 모션 포토는 뒤에 영상을 붙인다.
- **해결:** 가져올 때(`importImage`, 모든 사진 입력의 공통 단계) JPEG의 **첫 이미지만** 바이트 그대로 남긴다([jpeg-container](../src/lib/jpeg-container.ts), 그 브랜치).
  - 재인코딩하지 않는다. EXIF 방향과 ICC(Display P3)는 유지한다.
  - 뒤의 게인 맵·영상과, 그것을 가리키는 MPF·ISO 21496-1 표지·컨테이너 XMP만 뺀다.
- **서버 검사는 오히려 보강했다.** 모든 스캔을 지나 첫 EOI가 파일 끝이어야 한다. 이전에는 끝이 FFD9인 두 번째 JPEG이 MPF 없이 붙으면 통과했다.
- **HEIC/HEIF:** 받지 않는다. JPG로 저장해 다시 올리라고 안내한다(아이폰 '호환성 우선'). 변환 기능은 없다.
- **영향받던 경로:**
  - 홈 시작 카드·직접 편집 끌어 놓기
  - 비교 공간 만들기와 "사진 다시 분석"
  - 자재 폼의 텍스처·제품 사진
  - 관리자 분석 실험실
  - 배경 제거·입체화는 저장된 자산을 쓰므로 함께 해결됐다.
- **저장 모드:** 로컬(IndexedDB) 저장 모드는 이제 없어 D1/R2 한 경로만 확인했다.
- **검증**
  - 실제 Ultra HDR 사진 5장: 정리 후 서버 검사 통과, 960×1280. sharp와 실제 Chrome 디코딩 픽셀 차 0.
  - 23MB JPEG 서버 스캔 약 14ms.
  - 합성 iPhone·Google·Samsung 형식. 실물이 없어 규격대로 만들었다.
  - e2e 4개(격리 D1/R2): 비교 공간·직접 편집·자재 사진·HEIC 안내. 서버 원본이 첫 이미지와 해시가 같다.
  - 회귀 e2e 42개, vitest 3,304개 통과. 실패 7개는 알려진 환경 실패다. typecheck·lint 통과.
- **남은 한계**
  - HEIC 변환 없음
  - HDR 표시 정보(게인 맵)는 저장하지 않음
  - 실물 iPhone·Samsung 사진과 RST가 든 실물 JPEG은 없어 합성 파일로 시험했다.

## 2. FLUX(AI 현장 사진 변환)가 자재 색을 바꾸는 문제

- **문제:** 3단계 실측에서 흰 벽 타일이 베이지로 나왔다.
- **실제 변화:** 색보다 밝기 변화가 컸다. L\* 88→68~~77로 어두워지고 b\* +1.5~~2가 되어, 흰 위생도기 옆에서 베이지로 보였다.
- **원인 요인**
  - 색 이름 "off-white"
  - 벽 문장이 프롬프트 맨 끝이라 길이를 줄일 때 먼저 빠짐
  - 사진 조명 프로젝트에서 그림과 글의 색 불일치
- **넣은 것**
  - **C 프롬프트 보강**
    - 밝은 무채색은 "white"로 부른다.
    - 벽·바닥 색 문장을 설비 앞에 두고 "그림 0에 보이는 이 색 그대로" 문장을 붙인다. 길이를 줄일 때도 색 문장이 끝까지 남는다.
    - 사진 조명 프로젝트는 그림에 보이는 색으로 쓴다.
  - **B 면별 색 보정**(AI 없음)
    - 렌더와 결과의 구도가 맞으면(정렬 0.4 이상) 벽·바닥마다 결과의 a\*b\* 평균을 렌더로 옮긴다.
    - 어두워진 밝은 타일은 밝기 절반을 되돌린다.
    - 명암·질감은 AI 그대로이고, 설비·유리·면 밖 픽셀은 바꾸지 않는다. 렌더 픽셀을 붙이지 않는다.
  - **A 색 경고:** 흰 벽이 따뜻해지거나 색이 크게 바뀌면 알린다.
  - **화면**
    - 보정한 결과를 기본으로 보이고 "AI 원본 색 보기"로 바꿀 수 있다. 원본을 볼 때 경고를 보인다.
    - 구도가 바뀐 결과는 "비교하지 못했어요"로 알린다.
    - 다운로드는 보이는 결과를 받는다.
  - 호출 수는 그대로다(한 클릭에 FLUX 1 + 제품 확인 1).
- **평가**
  - **기존 결과 10장(무료)**
    - A: 정상 결과 거짓 경고 0, 흰 벽이 따뜻해진 결과는 모두 잡음.
    - B: 보정 뒤 색 차이(명도 제외) 0.5 이하, 설비 픽셀 변경 0, 후광 없음. 구도가 바뀐 3장은 건너뜀.
  - **실제 비교(사용자 승인 FLUX 8·Gemma 8, 모두 200, 약 930뉴런 중 FLUX는 추정)**
    - 흰 벽: 보강 프롬프트 2/2가 따뜻한 기운 없이 흰색이다. 지금 프롬프트는 1/2가 베이지 쪽(3단계는 4/4). 다만 면 평균 ΔE 중앙값은 −7%다(렌더보다 살짝 차가운 중립).
    - 베이지 벽: 두 프롬프트 모두 크림 회색으로 뺐고 보강이 조금 낫다(−16%). 보정(B)이 렌더의 베이지로 되돌린다.
    - 제품 유지: 지금 16/16, 보강 15/16(욕조 1회 변형, Gemma가 잡음).
    - 프롬프트 채택은 수치 기준이 애매해 사용자에게 물었고 "보강 프롬프트 유지"로 결정했다.
- **검증**
  - render-realism 45장·room-viewer-render 9장 픽셀 차 0(기존 렌더 불변)
  - flux-grounding 통과
  - 단위: 색 검사·보정 9개, 프롬프트
  - e2e(모의): 보정 표시·원본 전환·경고·다운로드 이름·390px·구도 변경 안내
  - 전체 vitest·typecheck·lint는 [검증 기록](verification.md)에 있다.
- **남은 한계**
  - 베이지가 빠지는 것은 모델에서 해결되지 않았다. 보정이 되돌리지만 구도가 바뀐 결과는 못 한다.
  - 경고·정렬 기준은 결과 18장으로 정했다.
  - 면 평균만 맞춘다(면 안의 얼룩진 색 변화, 새로 그린 소품).
  - 3D 편집기 캡처 경로는 e2e로 확인하지 않았다. 렌더러 메서드는 브라우저 스크립트로 확인했다.
