# 브라우저에서 제품 3방향 이미지 생성

## 목적과 흐름

배경 제거한 단일 제품 사진으로 제품 형태를 한 번 복원하고, 그 복원 결과에서 **왼쪽·정면·오른쪽 세 장을 모두 새로 렌더링**한다. 원본 사진과 새 사진을 섞거나 사진을 좌우 반전하는 방식이 아니다. 생성·추론은 사용자 브라우저에서 실행한다.

1. 자재 등록/수정의 제품 방향 사진에서 **AI 배경 제거 테스트**를 실행한다.
2. 결과 창의 **3방향 이미지 만들기**를 누른다. 이때 배경 제거 결과 Blob을 그대로 전달하며 원본을 덮어쓰거나 배경 제거 모델을 다시 실행하지 않는다.
3. **3방향 생성 시작**을 누른다. 방향을 직접 고를 필요 없이 입력에서 복원한 형태로 정면을 먼저 추정한다. 이미 투명한 방향 사진에는 **AI 3방향 생성** 버튼으로 직접 들어갈 수 있다.
4. 세 결과를 비교하고 확대·배경색 전환으로 확인한다. 결과는 정면·왼쪽·오른쪽 순서다. 필요한 경우 **정면 각도 추가 보정**으로 자동 정면에 1도씩 보정을 더한다. 이 보정은 같은 복원 형태를 다시 렌더링하며 AI 추론·모델 다운로드를 반복하지 않는다. 각 PNG를 내려받거나 **3방향 모두 적용**을 누른다.
5. 세 PNG 자산이 모두 저장된 뒤 편집 중 자재의 해당 방향을 한 번에 교체한다. 기타 방향과 원본 자산은 유지한다. **자재 등록/새 버전 저장**으로 최종 저장한다.

생성된 세 장은 같은 제품 형상·색상과 공통 카메라 크기를 사용한다. PNG는 배경이 투명하며 해상도는 각 768×768이다. 원본 사진 해상도와 512×512 AI 분석 해상도는 다르다. 생성된 PNG에 `ai-multiview` 메타데이터와 원본 자산 참조를 기록한다.

## 실행 및 자원 관리

- 투명 배경과 입력 크기, 실행 환경을 먼저 확인한다. 투명 배경이 없는 사진은 배경 제거를 먼저 실행하도록 안내한다.
- WebGPU와 `shader-f16`을 지원하면 GPU를 우선 사용한다. GPU 지원 확인·세션 생성·추론이 실패하면 기존 Worker를 종료하고 새 Worker에서 동일 FP16 ONNX 파일을 CPU/WASM으로 한 번 재시도한다. CPU 전용 별도 모델을 다운로드하지 않는다. 입력 오류와 네트워크 실패에는 CPU 재시도를 하지 않는다.
- 브라우저 모델 다운로드와 디코딩, GPU 모델 생성에 상당한 메모리가 필요하다. 공식 Python 기본 실행은 약 6GB VRAM을 안내하지만, 이 수치를 브라우저의 보장 조건으로 사용하지 않는다. 실제 브라우저 메모리 부족은 명확한 오류로 알린다. CPU/WASM 진단에서는 약 4GB RSS와 160초의 encoder/backbone 추론이 관찰되었으므로 저사양에서 빠른 처리를 보장하지 않는다.
- Worker에서 512×512 RGB 입력 → ViT 특징 → triplane → 160³ 표면 격자 및 색상 추론을 수행한다. encoder/backbone 세션을 순차 해제하고, 마지막 표면 메시지를 보낸 뒤 Worker를 종료한다.
- GPU 세션은 ORT 1.29의 `storageBufferCacheMode: simple`, `defaultBufferCacheMode: simple`을 사용한다. `disabled`는 실제 Chrome에서 해제된 버퍼 제출 오류가 재현되어 사용하지 않는다. 기본 bucket 모드보다 과도한 버퍼 보관을 줄인다.
- 실제 backbone 출력명은 `triplane`이다. 모델 카드의 일부 예시 이름과 달라 실제 고정 버전의 그래프를 확인했다.
- 밀도 출력은 ONNX에 이미 포함된 `exp(raw−1)`이며 threshold 25로 표면을 추출한다. 격자 선형 보간만으로 생기는 층과 색상 줄무늬를 줄이기 위해, 공유 정점의 원래 격자 경계에서 실제 decoder 밀도를 7회 이분 탐색하고 최종 표면 좌표에서 색을 조회한다. 색 필터·모델 변경·추가 가중치 다운로드는 없다. 원본 RGB와 단순 알파 변형으로 다른 시점을 흉내내지 않는다.
- 주 스레드의 Three.js 렌더러는 투명 PNG 세 장을 만들고 GPU·Canvas 자원을 해제한다. 취소와 늦은 응답은 실행 ID 및 Worker 참조로 구분한다.
- 로컬 모드에서 사진·생성 결과를 외부로 전송하지 않는다. 명시적 적용 시에만 기존 저장소 어댑터로 자산을 저장한다. Supabase 실제 연결/배포는 별도 검증 대상이다.

## 자동 정면 정렬

모델 가중치와 AI 추론 횟수는 그대로다. 표면 색상 조회가 끝나고 모델 세션을 해제한 뒤, 같은 Worker에서 `estimateFrontOrientation`을 실행한다. 메시의 면적에 비례한 12,000개 표본을 만들고 수직 대칭면을 탐색한다. 반사한 표면과 실제 표면의 거리, 제한된 색상 차이를 비교하며 대칭면의 중심 위치도 함께 보정한다. 180도 앞뒤 중 원본 카메라가 보는 쪽을 택한다. 좌우 대칭만으로 제품의 의미상 앞뒤를 알아내는 것은 아니므로 후면 전용 입력에는 한계가 있다.

Three.js는 추정된 정면 PNG를 먼저 만들고, 동일한 형태·색상·화면 크기에서 그 정면의 ±35도로 좌우 PNG를 만든다. 생성한 정면 이미지를 AI에 재입력하지 않으므로 두 번의 복원으로 외형이 더 변하지 않는다. 자동 각도 결과는 작은 메시와 함께 결과 창이 열린 동안만 보관하고, 추가 보정에는 렌더러만 다시 실행한다. 입력 방향 레이블은 이전 호출자와의 호환을 위해 타입에 남아 있지만 각도 결정에는 쓰이지 않는다.

실제 사진·알려진 각도의 입력·모호한 형태 및 실행 결과는 [자동 정면 정렬 검증](front-alignment-validation.md)을 참고한다.

## 알려진 한계

한 장에 보이지 않는 뒷부분은 모델의 추정이다. 제품 도면이나 실제 촬영 사진을 대체하지 않는다. 제품 하나가 크게 보이고 배경 제거 후 다른 물건이 남지 않은 사진이 적합하다. 같이 남은 물건도 형태로 복원될 수 있으며 전체가 투명해진 입력은 오류로 중단한다. 구멍, 얇은 수도꼭지, 반사, 각인과 미세 무늬가 단순화되거나 달라질 수 있다. 정면은 복원한 형태의 좌우 대칭에서 추정하며, 사용자의 정면/좌/우 선택을 고정 각도로 치환하지 않는다. 좌우 대칭이 약한 제품·원통처럼 여러 방향이 같은 제품·정확히 측면이나 뒷면만 찍은 사진은 의미상 정면을 확정할 수 없다. 대칭 점수와 경쟁 축 차이, 원본 카메라와의 방향 차이로 모호한 결과를 표시한다. 이 값은 학습 모델의 확률이 아니다. 필요하면 정면 각도 추가 보정(-180~180도, 1도 간격)으로 세 장을 함께 맞춘다. 작은 CPU 메시만 결과 창이 열려 있는 동안 보관하고 닫을 때 버리므로 GPU 세션이나 모델 가중치를 유지하지 않는다. 생성 결과를 확인한 뒤 적용해야 한다.

## 검증

형상 보간·축·렌더러 및 입력 전처리 단위 테스트를 추가했다. 실제 모델 추론과 UI 검증의 최신 결과는 별도 검증 기록에 정리한다. 2026-09-12 표면 정밀화의 실제 전후 결과와 남은 한계는 [표면 줄무늬 품질 검증](multiview-quality-validation.md)에 기록했다. 합성 형상 및 모의 Worker 검사는 실제 AI 품질 검증으로 계산하지 않는다.
