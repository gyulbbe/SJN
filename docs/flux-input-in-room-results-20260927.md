- **사용자 승인(2026-09-27)**

  - 사용자 결정(비교 뒤): 알림은 **큰 물건 + 멀리 떨어진 같은 제품**만 보이고, **좌우 가장자리에서 잘린 제품**은 "안 보임"을 경고하지 않는다.

  - 그래서 정답표와 확인 호출은 새 결과 8장과 사용자 사례 1장만 대상이다.
  - 기존 19장은 문서 기록만 참고했다.

## 원인 확인

- **사용자 사례**(`report/user-example-before-after.jpg`): 입력은 벽 구조 없는 기본 방의 2D 합성(옛 구도)이다. 방 상자 둘레가 회색 여백이고 천장이 열려 있다.
- **결과에서 바뀐 것**
  - 여백이 바깥 벽으로 바뀌었다.
  - 가운데에 천장까지 닿는 유리 칸막이가 생겼다.
  - 왼벽의 가는 핸드 샤워가 사라지고, 오른벽에 샤워 세트(레인 샤워·핸드 샤워·수전·토수구)와 유리 선반이 생겼다.
  - 이 사례 파일에서는 뒷벽 타일 띠를 찾지 못했다.
- **입력 경로:** 편집기 AI 캡처는 벽 구조(`wallFeatures`)가 있을 때만 3D 렌더러를 쓰고, 나머지는 2D 합성(여백 있음)을 썼다. 비교 결과(아래)에서 옛 구도는 3장 모두 여백을 벽으로 채웠다. 방 안 입력은 6장 모두 벽 조각을 만들지 않았다.

## 작업 1: 방 안 시점 입력

### 바꾼 것

- **입력:** 방(`scene.room`)이 있고 Before와 크기가 같은 모든 프로젝트(기본 방, 벽 구조, 사진 비교 공간)는 `RoomViewerRenderer`로 방 안 시점을 한 장 렌더한다.
  - 방이 없는 옛 사진 전용 장면만 2D 합성을 그대로 쓴다([view](../src/lib/ai-export/view.ts) `fluxRoom`).
  - 겹쳐 찍기·사진 효과는 넣지 않는다.
  - 사진 조명 맞춤(`lighting`)은 그대로 곱한다.
- **시점:** AI 변환 창의 "AI 입력 시점"
  - 선택지: 방 안 · 가운데(기본) / 왼쪽 모서리 / 오른쪽 모서리
  - 공간 둘러보기에 방 안 시점을 저장해 두었으면 "저장한 방 안 시점"이 추가되고 처음부터 선택된다.
  - 시점을 바꾸면 비교 원본과 결과를 새로 시작한다(바꾸기 전에 저장하라고 알린다).
  - 2026-09-28에 이 선택지를 없애고, 앞쪽 가운데 카메라를 3D 미리보기에서 돌리는 방식으로 바꿨다([입력 시점](flux-export.md#입력-시점)).
- **AI 입력 구도(사용자 결정):** 프리셋의 서는 자리와 방향은 그대로다. 렌즈 90°, 눈높이 1.2m, 시프트 0을 쓴다(`FLUX_EYE_*`).
  - 공간 둘러보기의 방 안 시점(74°·1.5m·아래로 −0.2)은 기본 방(2.4m)에서 가운데 시점에 왼벽 세면대가 들어오지 않았다. 천장은 0%, 바닥은 2% 이하만 보였다.
  - AI 구도에서는 세 프리셋 모두 설비 3개가 들어오고 천장이 6~8% 보인다.
  - 저장한 방 안 시점은 저장한 그대로 쓴다.
- **한 시점으로 맞춤:** 원본 칸 그림, FLUX 입력, 설비 상자(`fixtureBounds`), 면 마스크(`regionMask`), 프롬프트 위치, 색 검사·보정이 모두 같은 카메라다(브라우저 검사에서 설비 픽셀 100%가 상자 안).
- **천장 문장**
  - 장면 계약에 `ceiling: { color, light: 'flat-panel' }`을 더했다(선택, 엄격한 스키마). 이전 형식도 받는다.
  - 프롬프트에 "The ceiling is plain white (#f3f2ee) paint with one flat square light panel."을 타일 문장 뒤, 설비 문장 앞에 넣는다.
  - 마스크에서 천장이 1% 이상 보일 때만 보낸다(`visibleCeiling`). 그림에 없는 것을 글로 말하지 않기 위해서다.
- **렌더러:** 캡처마다 새로 만들고 캡처 뒤 해제한다. 방 안 카메라는 맞춤 범위를 쓰지 않아 다른 시안은 준비하지 않는다. 편집 화면·시안 미리보기·일반 내보내기·공간 둘러보기 코드는 바꾸지 않았다.

### 사진 시점(source-photo)은 넣지 않았다

`tests/flux-input-in-room-browser.ts`로 사진 카메라 두 가지를 렌더했다(`payload/source-*-capture.png`).

- **사진 비교 공간의 3D 렌더:** 천장을 그리지 않는다. 궤도 시점을 가리지 않고, 저장된 사진 시점을 바이트 그대로 유지하려는 설계다.
- **문가에 선 카메라**(방 밖 25cm): 화면 위쪽 20% 줄의 9.6%가 빈 배경이었다(열린 천장).
- **방 안 카메라**(5° 아래): 빈 곳은 0.4%였지만, 사진처럼 천장을 담는 구도면 열린 천장이 된다.
- 여백·열린 천장을 없애는 것이 목적이므로 AI 입력 선택지에 넣지 않았다. 사진 비교 공간도 방 안 프리셋을 쓴다.

## 실제 비교 (FLUX 8, Gemma 9)

  - 왼벽 벽걸이 세면대·핸드 샤워, 뒤 오른쪽 바닥 변기(표준 모형)

  - 확인은 앱의 `fluxCheckPayload`·`readFluxCheckCompletion`을 썼다.

### 작업 1 판정

| 기준                         | 옛 구도(3장)               | 방 안(6장)                 | 판정          |
| ---------------------------- | -------------------------- | -------------------------- | ------------- |
| 새로 생긴 구조·큰 물건(장당) | 2.0(벽 조각 3/3, 유리 3/3) | 0.5(벽 조각 0/6, 유리 3/6) | 통과(4분의 1) |
| 구도 정렬 0.4 이상           | 0.44·0.50(사례 0.52)       | 0.59~0.63(아래 변경 뒤)    | 통과          |
| 제품 유지                    | 3/3·3/3(사례는 샤워 이동)  | 6장 모두 3/3               | 통과          |

- **구도 정렬:** 처음에는 방 안 6장이 0.21~0.32로 모두 기준 미달이었다. 그래서 색 보정이 전부 건너뛰어졌다.
  - 원인: 테라초 반점·줄눈이 입력 윤곽의 대부분인데, 모델이 무늬를 새로 깔아 맞지 않았다.
  - 고침: `framing`은 기존 윤곽과 **4분의 1 해상도 5×5 흐린 윤곽** 중 높은 점수를 쓴다([color](../src/lib/ai-export/color.ts) `coarseEdges`).
  - 효과: 방 안 6장은 0.59~~0.63이 됐다. 같은 결과를 15% 확대한 것은 0.22~~0.37, 12% 줄여 회색 테두리를 붙인 것은 0.28~0.35로 계속 걸렸다.
  - 기존 방식에서 맞던 결과는 그대로 맞는다(높은 쪽을 쓰므로).
- **보정:** 방 안 6장의 면 색 변화(명도 뺀 ΔE)는 2.6~5.8이었다. 보정 뒤 남은 차이는 0.49 이하다. 경고 기준(6)은 넘지 않았다.
- **"빈 벽" 문장:** 큰 추가는 0.5(가운데 plain 0.5와 같음), 작은 추가는 1→3개로 효과가 없어 넣지 않았다. 코드에서도 뺐다.

### 작업 2 판정 (Gemma 확인 9회)

- **Gemma 경향:** 목록에 있는 제품도 extras로 되풀이했다. 예: 변기를 "뒷벽", 샤워를 "왼벽"으로 적었다. 앱의 읽기 규칙([notices](../src/lib/ai-export/notices.ts) `readFluxCheck`)이 걸렀다.
  - 같은 종류가 제자리나 이웃 벽에 있으면 그 제품으로 본다.
  - 바닥 제품은 천장만 아니면 그 제품이다.
- **큰 추가 물건:** 정답 9개 중 5개를 잡았다(56%). 기준(90%)에는 못 미쳤다.
  - 유리 칸막이는 6개 중 5개를 잡았다. 놓친 1개는 옆면으로 거의 선만 보이는 것이다.
  - 벽 조각(여백→바깥 벽) 3개는 하나도 잡지 못했다. 모델은 바깥 벽을 방의 벽으로 본다. 방 안 입력에서는 여백이 없어 이 경우가 생기지 않았다.
  - 큰 물건 거짓 알림은 0개다.
- **작은 추가 물건:** 13개 중 4개를 잡았다. 틀린 것도 4개였다(결정 전 규칙: 작은 물건도 보이고, 이웃 벽을 따로 보지 않음).
  - 유리 반사를 거울로 2번 봤다.
  - 유리 고정 막대를 수건걸이로 봤다.
  - 모서리 시점에서 왼벽 샤워를 "뒷벽"으로 적었다.
- **사용자 결정으로 채택한 알림**
  - 큰 물건(유리 칸막이·창문·문·벽 조각)
  - 배치한 제품과 같은 종류가 마주 보는 벽·천장·가운데에 있는 경우(하나 더 생김)
  - 제품이 제자리에서 안 보이고 먼 곳에 있으면 "옮겨졌을 수 있어요"
  - 나머지 작은 물건은 응답에만 남기고 화면에 보이지 않는다.
- **이 9장에서 채택 규칙의 알림**
  - 사용자 사례: "배치하지 않은 물건이 생겼을 수 있어요: 유리 칸막이(가운데), 샤워기(오른쪽 벽)"
  - 옛 구도 2장, 오른쪽 모서리 777001, 빈 벽 424242: 유리 칸막이
  - 가운데 424242: 알림 없음(희미한 유리를 놓침)
  - 나머지 3장: 알림 없음(정답과 같음)
  - 거짓 알림은 0개다.
- **잘린 제품:** 가운데 777001에서 화면 왼쪽 끝에 잘린 세면대를 Gemma가 "없음"으로 답했다(유일한 제품 거짓 경고).
  - 사용자 결정으로, 상자가 좌우 끝(0.5% 안)에 닿은 제품의 "없음"은 경고하지 않는다.
  - 아래 끝만 잘린 제품은 그대로 판단한다.
- **타일 배열:** 방 안 17개 벽 답은 모두 "그대로"였다. 거짓은 0이지만, 실제로 바뀐 오른쪽 모서리 424242의 두 벽을 놓쳤다.
  - 옛 구도에서는 바깥 벽이 붙은 벽 5개를 "다름"으로 답했다.
  - 믿을 만하지 않아 화면에 넣지 않고, 응답에만 남긴다(`FLUX_SHOW_TILE_NOTICE = false`).
- **사용자 사례의 "왼쪽→오른쪽"**
  - Gemma는 왼벽 상자 안에서 샤워가 여전히 보인다고 답했다. 그래서 "옮겨짐"이 아니라 "오른쪽 벽에 샤워기가 생김"으로 알린다.
  - 제품이 제자리에서 "없음"이고 먼 벽에서 보이면 "샤워가 왼쪽 벽에서 오른쪽 벽으로 옮겨졌을 수 있어요."로 알린다(단위·e2e).

### 실제 사용량

- **FLUX 8회:** 응답 8.6~23.6초이고 usage는 없다. 공식 계수 추정 회당 약 110뉴런, 약 880뉴런이다.
- **Gemma 9회:** 입력 8,455·출력 1,209 토큰이다. 공식 계수(입력 100만당 9,091, 출력 100만당 27,273)로 **109.8뉴런, 회당 12.2뉴런**이다.
  - 기존 6.2~6.7뉴런에서 늘었다. 질문이 약 380토큰 길어졌고, 답에 extras·walls가 더해졌다.
  - 응답 시간은 2.0~5.6초, 중앙값 3.0초다.
- **합계:** 약 990뉴런이다. 승인 추정 안이고 하루 무료 10,000뉴런 안이다.

## 확인 확장 (코드)

- **요청:** `scene.fixtures[]`에 선택 `face`(바닥·왼벽·뒷벽·오른벽), 선택 `walls`(보이는 벽, 겹침 금지)를 더했다. 벽은 마스크에서 프레임의 2% 이상인 벽이다(`visibleWalls`). 버전은 1 그대로이고 이전 요청도 받는다.
- **질문(`flux-fixture-check-v2`):** 서버가 영어로 쓴다.
  - 제품마다 "on the left wall"을 붙인다.
  - extras에 목록 밖 물건을 최대 8개 적게 한다. 종류는 창문·문·유리 칸막이·벽 조각·선반·수건걸이·휴지걸이·샤워기·물 내림 버튼·거울·수납장·욕조·변기·세면대·기타이고, 위치는 왼벽·뒷벽·오른벽·바닥·천장·가운데다.
  - 벽마다 `uniformTiles`(yes/no/unsure)를 묻는다.
  - 위치에 "가운데"(방에 따로 선 물건)를 더했다. 유리 칸막이를 "바닥"으로 적는 것보다 알림 문구가 자연스럽다.
- **응답:** 엄격한 JSON 스키마다.
  - extras·walls는 있으면 같은 규칙으로 검사한다. 모르는 단어, 9개 이상, 묻지 않은 벽, 겹친 벽은 502다.
  - extras·walls가 없는 응답(v1 모양)도 제품 답만으로 읽는다.
  - 클라이언트는 이전 서버 응답(없음)을 "확인하지 않음"으로 처리한다.
- **규칙 유지:** 한 클릭에 FLUX 1 + 확인 1, 동일 출처·로그인, `sjn-gateway`, 재시도 1회 제한, 진단에는 개수(제품·벽)와 크기만 남긴다.
- **화면:** 결과 아래 빨간 상자 하나에 중요한 순서로 보인다.
  1. 배치한 제품이 바뀌었을 수 있어요(옮겨짐, 안 보임)
  2. 배치하지 않은 물건이 생겼을 수 있어요: …
  3. (타일 배열, 지금은 끔)
  4. 색 경고(AI 원본 색을 볼 때)
  - 끝에 "다시 만들어 보세요. 자동으로 다시 만들지는 않아요."를 한 번 붙인다. 색 경고만 있으면 붙이지 않는다. 색은 보정되기 때문이다.
  - 그 아래 회색 글로 색 보정 안내, 구도 변경 안내, "AI 제품 확인: 배치한 제품 N개가 모두 보여요. 배치하지 않은 큰 물건도 보이지 않아요.", 확인 실패를 보인다.
  - 390px에서 가로 넘침이 없다(e2e).

## 남은 한계

- **작은 물건:** 휴지걸이·천장 레인 샤워 같은 작은 추가는 대부분 알리지 않는다. 잡은 것도 절반은 틀렸다.
- **희미한 유리·바깥 벽:** 옆면으로 거의 선만 보이는 유리 칸막이와, 옛 구도에서 여백이 된 바깥 벽은 Gemma가 잡지 못했다. 옛 구도는 방이 없는 옛 장면에만 남는다.
- **타일:** 무늬·명도가 바뀌는 것(테라초 → 매끈한 밝은 회색)은 막지 못한다. 색 보정은 색상만 되돌리고 어두운 타일의 명도는 두기 때문에, 보정본은 밝은 따뜻한 회색이 된다. 타일 배열 판정은 화면에 넣지 않았다.
- **잘린 제품:** 좁은 욕실의 방 안 구도는 앞쪽 제품이 가장자리에서 잘린다. 좌우 끝에 닿은 제품은 사라져도 알리지 않는다.
- **표본이 작다:** 결과 8장과 사례 1장이다. 기존 19장은 이 PC에 없어 확인하지 못했다. 정렬 기준(0.4)은 새 방식으로 기존 결과를 다시 재 보지 않았다.
- **도기 모양:** 결과의 변기·세면대 모양은 표준 모형과 조금 다르다(탱크·볼 형태).
