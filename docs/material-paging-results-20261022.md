# 자재 목록 페이징 결과 · 2026-10-22

자재 목록을 한 번에 다 받던 화면 다섯 곳이 이제 한 쪽(48개)씩 받는다. 공개 `/materials`, 편집기 자재 서랍, 관리자 자재, 관리자 프로젝트 서랍, 게스트 서랍이 해당한다. 검색·종류·분류도 서버가 거르고, 분류 목록과 결과 개수는 전체 기준으로 첫 쪽과 함께 온다. 이미지는 화면에 보이는 카드만 받는다. 장면에 쓴 자재는 묶음 한 번으로 받는다. D1이 읽는 행은 쪽 크기를 따르고, 자재 수에는 비례하지 않는다.

- **원격 D1:** 쓰지 않았다. 첫 쪽 이미지 크기를 재려고 사용자 승인으로 읽기 전용 SELECT를 1회 실행했다(144행, 9절).
- **0009:** 로컬 개발 DB와 테스트 DB에 적용했다. **원격 `sjn`에는 2026-10-23 사용자가 적용했다**(워크트리의 `migrations list`가 `No migrations to apply`, 4절).
- **배포:** 하지 않았다.

## 1. 사용자 결정

- Q1 방식: 서버가 쪽을 나누고 필터·검색도 서버에서 한다. 목록용 요약을 migration으로 더한다. 응답 캐시는 두지 않는다.
- Q2 넘기기: 아래로 내리면 자동으로 더 불러온다. "더 보기" 버튼도 둔다.
- Q3 쪽 크기: 48개. 서버 최대값도 48이다.
- 목록용 작은 이미지: 첫 쪽 이미지 합계가 6.0MB로 5MB를 넘었다. **다음 작업에서 두 가지를 모두 만들기로 했다.** 등록할 때 만들기와 기존 약 930개 일괄 생성이다(9절).

## 3. API 계약

### 공통 질의 (`src/lib/catalog/paging.ts`)

| 값 | 뜻 |
| --- | --- |
| `category` | 종류. `'fixtures'`는 타일이 아닌 모든 종류(편집기 위생도기 탭). 위생도기 탭의 종류 칩을 고르면 그 종류 하나다(2026-10-24, `editorTabQuery(tab, kind)`) |
| `usage` | `wall`·`floor`. `category: 'tile'`과 함께 쓰며 그 용도 또는 `both`인 타일을 고른다(편집기 벽·바닥 탭) |
| `q` | 검색어, 100자 이하. 화면마다 비교 대상이 지금과 같다(5절) |
| `facets` | `{size,color,finish}`, 그룹당 50개 이하. 그룹 안은 OR, 그룹 사이는 AND. 범위에 없는 값은 버린다(`effectiveFacets`와 같음) |
| `options` | 첫 쪽에 범위의 분류 목록을 함께 달라는 표시 |
| `cursor` | 다음 쪽. 받은 그대로 다시 보낸다 |
| `limit` | 1~48, 기본 48 |

**응답** `{ items, nextCursor, total?, facets?, counts? }`
- `total`: 첫 쪽에만 있다. 조건에 맞는 전체 개수다.
- `facets`: 첫 쪽이고 `options`가 있을 때만 있다.
- `counts`: 관리자 자재의 첫 쪽에만 있다. 범위 탭 개수와 사용 가능한 자재 수다.

### 경로

| 경로 | 범위 | 항목 |
| --- | --- | --- |
| `GET /api/catalog/materials?…` | 공개(공유·활성·catalog·reconstruction 키 없음, 예시 자재 포함). 검색 대상은 이름·브랜드·코드·하위분류·색·재질·마감 | 공개 카드. 이전 `PublicMaterial`에서 `pricing`을 뺐다. 상세 창이 쓰는 설명과 이미지는 그대로다. 응답의 `catalog`(옵션 118행)는 쓰는 곳이 없어 뺐다 |
| `GET /api/catalog/placement?…` | 게스트 서랍. 공개 범위에서 예시 자재를 빼고, 검색 대상은 이름·브랜드·코드. 표시 이미지가 하나라도 공개되지 않은 자재는 그 쪽에서 빠진다. 그래서 쪽이 48개보다 짧을 수 있다 | `{ placements, nextCursor, total?, facets? }` |
| `GET /api/catalog/placement?ids=a,b` | 쓴 자재 확인(48개까지) | 그 자재들의 현재 배치 |
| `GET /api/catalog/placement?materialId=` | 이전과 같음 | 배치 한 건 |
| `POST /api/d1/materials` `{operation:'page', query, view?, scope?, active?}` | `view: 'picker'`는 편집기 서랍(내 것 또는 공유, 활성, 예시·재구성 모형 제외, 검색은 이름·브랜드·코드). `view: 'library'`는 관리자 자재(`scope` 전체·내·공용, `active`, 검색은 이름·브랜드·코드·색·마감) | `MaterialCard`(`src/lib/catalog/cards.ts`) |
| `POST /api/admin/project-materials` 같은 작업 | 관리자 프로젝트 서랍(picker만) | `MaterialCard` |
| `{operation:'getVersions', ids(≤100), withCurrent?}` | `getVersion`과 같은 가시성(`visibleVersionsQuery`, `json_each` 1회) | `{ versions, current }`. `current`는 그 자재들의 현재 버전이다(사용량 패널의 최신 가격 비교). 관리자 프로젝트에서 현재 버전을 볼 수 없으면 그 버전 자신을 준다 |
| `{operation:'find', match:{code, reconstruction}}` | 옛 전체 목록에서 `.find`하던 것과 같음 | 버전 또는 `null` |

### 커서

- 커서는 base64url JSON이다. 질의의 지문(종류·용도·검색어·분류, 화면 종류, 범위·활성, 관리자 프로젝트), 마지막 항목의 `(updated_at, material_id)`, 관리자 프로젝트의 무리 번호, 적용한 분류, 분류 출발 그룹을 담는다.
- 조건이 다른 질의에 쓰면 400이다(`users.ts`와 같다). 길이 2,048자 초과나 위조된 값도 400이다.
- 정렬은 `updated_at DESC, material_id DESC`다. 옛 목록은 같은 시각끼리의 순서를 정하지 않았다. **2026-10-27부터는 목록마다 순서를 고르고(기본 우선순위), 커서는 그 순서의 값을 담는다**([목록 순서 결과](material-order-results-20261027.md)).
- **쪽 사이에 수정된 자재**(새 버전, 활성 전환)는 `updated_at`이 바뀌어 맨 앞으로 간다. 이미 받은 쪽보다 앞이라 다음 쪽에는 나오지 않고, 처음부터 다시 받으면 맨 앞에 보인다. 같은 이유로 이미 받은 자재가 다음 쪽에 다시 나오지는 않는다.

## 4. migration 0009 (`migrations/d1/0009_material_list.sql`)

### 요약을 둔 곳: 새 표 3개와 트리거

| 표 | 내용 |
| --- | --- |
| `d1_material_list` | 버전마다 한 행. 자재 상태 사본(`owner_id, scope, purpose, active, updated_at, is_current`)과 payload에서 뽑은 `category, usage, lane, code`, 검색 열 3개(`lower()`), `class`를 둔다 |
| `d1_material_list_facets` | 버전의 분류 값 한 개가 한 행. 정렬·거르기용 상태 사본을 함께 둔다 |
| `d1_material_list_counts` | 현재 버전이면서 공유인 자재 수. `(active, lane, category, class, facet, value)`별로 세며, `facet=''` 행은 자재 수다. 0이 된 행은 지우지 않는다(목록은 `n>0`만 읽음) |

- `lane`: 타일이면 용도(`wall`/`floor`/`both`, 용도가 없으면 `tile`), 제품이면 `fixture`다.
- `class`는 화면마다 다른 가시성을 한 숫자로 담는다.
  - 1: `purpose='catalog'`
  - 2·4: reconstruction(0 없음, 1 JSON null, 2 다른 거짓 값, 3 참 값)의 2배
  - 8: 공유 자재인 예시 4종(`isBuiltInExampleMaterial`)
  - 화면별 허용 값: 공개 {1, 9}, 게스트 {1}, 회원·관리자 자재 {0..5}, 관리자 프로젝트 서랍 {1, 3}

**새 열이 아니라 새 표로 둔 이유**
- 목록은 `m.updated_at` 순서, `active`·`scope`, 버전의 종류를 함께 걸러야 한다. 이 값들이 두 표에 나뉘면 인덱스 하나로 쪽을 넘길 수 없다.
- `d1_materials`에 열을 더하면 버전마다 다른 값(종류·검색·분류)과 관리자 프로젝트가 읽는 옛 버전을 담지 못한다.

**batch 문장이 아니라 트리거인 이유**
- `d1_materials`·`d1_material_versions`에 쓰는 모든 경로에서 같은 트랜잭션으로 돈다. 저장, 새 버전, 활성 변경, 데이터 수정, 시험용 SQL이 모두 해당한다.
- **원격 migration을 적용하고 새 코드를 배포하기 전까지 옛 코드가 저장해도 요약이 맞는다.**

**트리거**(본문에는 CTE를 쓰지 않음)
- 버전 INSERT: 요약 행과 분류 행을 넣고 counts를 +1 한다.
- 버전 payload UPDATE: 데이터 수정 때만 일어난다. 다시 만들고 counts를 맞춘다.
- 자재 UPDATE(`current_version_id`, `active`, `updated_at`, `scope`, `owner_id`, `purpose`)
  1. 옛 상태로 −1 한다.
  2. 그 자재의 모든 버전 행과 분류 행의 사본을 고친다.
  3. 새 상태로 +1 한다.
- 새 버전은 자재 UPDATE 뒤에 버전 INSERT 순서로 저장된다. 그래서 −1은 옛 버전에, +1은 새 버전을 넣을 때 일어난다.
- 기존 행 채우기와 트리거 3개는 같은 SELECT를 쓴다. 이것을 시험으로 확인한다(7절).

**분류 나누기**(`facetValues`와 같음)
- 색·마감은 `json_each('['||replace(json_quote(text),'·','","')||']')`로 나눈다.
- 앞뒤 공백은 `String.prototype.trim`이 지우는 문자 목록으로 `trim(value, …)`한다. NBSP·탭·전각 공백이 포함된다.
- 크기는 0보다 큰 값을 `'X'`로 잇는다. 타일은 2개, 제품은 3개다.

**인덱스**
- `d1_list_lane(lane, updated_at DESC, material_id DESC, class) WHERE is_current=1 AND scope='shared' AND active=1`
- `d1_list_category(active, category, …)`, `d1_list_recent(active, …)`: 같은 부분 조건, `active=1` 조건 없음
- `d1_list_personal(owner_id, …) WHERE is_current=1 AND scope='personal'`
- `d1_list_material(material_id)`, `d1_list_code(code)`
- `d1_list_facet_order(active, facet, value, updated_at DESC, material_id DESC, lane, category, class) WHERE is_current=1 AND scope='shared'`

**준비 검사:** `checkD1Storage`에 새 표 3개와 열 확인(`LIMIT 0`)을 더했다. 메타 버전은 올리지 않았다. 올리면 원격 적용과 배포 사이에 옛 코드의 준비 검사가 실패한다.

## 5. 같은 결과 (권한·공개 범위는 바꾸지 않음)

`tests/d1-material-paging-equivalence.test.ts`가 비교를 맡는다.
- 옛 전체 목록 SQL과 옛 브라우저 거르기의 고정 사본(`tests/helpers/legacy-material-lists.ts`)을 쓴다.
- 이 사본과 새 쪽들을 이어 붙인 결과를 같은 Miniflare D1에서 나란히 비교한다. 쪽을 7개로 줄여 커서를 반드시 거친다.

**무작위 카탈로그 요소**
- 공유·개인·프로젝트용·비활성 자재
- 예시 자재, 옛 버전
- `·`로 이은 색·마감, 같은 `updated_at`
- reconstruction 없음·객체·null·false
- 없거나 공개되지 않은 이미지
- 관리자 프로젝트 참조

**비교 항목**
- 회원 3명의 편집기 서랍: 탭 × 검색 × 분류
- 관리자 자재: 범위 × 활성 × 종류 × 검색, 탭 개수
- 관리자 프로젝트 2개 × 관리자 2명의 서랍
- 공개 목록: 종류 × 검색(전각 포함) × 분류
- 게스트 서랍
- 항목 순서, 카드 내용, `total`, 분류 목록, `find`, `getVersions`(가시성과 `current`)

**결과**
- 평소 실행은 seed 1개와 표본 조합이다.
- 기록용 증명은 `SJN_EQ_SEEDS=6`(모든 조합)이다: **6개 seed 모두 불일치 0**(2026-10-23, 1,220초). seed마다 카탈로그 30~60개, 질의 수백 개를 쪽 7개 단위로 비교했다. 처음 실행에서 seed 2개가 게스트 단계에서 멈췄는데, 원인은 시험 생성기였다. 공개 자재에 `usage`가 없는 버전(저장 스키마상 생기지 않음)을 만들었고, 옛 전체 배치 목록도 이 데이터에서는 500으로 실패한다. 그래서 `usage` 없는 버전은 개인 자재에만 만들도록 고쳤다.

**지금과 다른 점**(문서화한 차이)
1. **검색 본문의 대소문자:** 저장된 검색 열은 SQL `lower()`라 ASCII만 소문자로 바꾼다. 검색어 쪽은 화면마다 하던 대로 정규화한다(공개는 NFKC + trim + 소문자, 편집기는 소문자, 관리자는 trim + ko-KR 소문자). 그래서 **자재 이름 자체에** 전각 문자나 ASCII 밖 대문자(예: `Ä`)가 있으면 지금과 다르게 걸릴 수 있다. 지금 데이터는 한글·ASCII라 영향이 없다.
2. **게스트 분류 목록:** 공개 요약에서 오므로 이미지를 보지 않는다. 표시 이미지가 빠져 서랍에서 제외되는 자재에만 있는 값이 목록에 보일 수 있다. 항목 자체는 정확히 빠진다. 불변식 2(공개 버전의 표시 이미지는 모두 참조됨)상 실제로는 없다.
3. **관리자 프로젝트의 옛 버전:** 현재 버전을 볼 수 없는 자재에 프로젝트가 참조한 옛 버전이 둘 이상 있으면, 옛 SQL은 그중 아무거나 보였다. 지금은 번호가 큰 버전을 고른다.
4. **같은 시각 정렬:** 옛 목록은 같은 `updated_at`의 순서를 정하지 않았다. 지금은 `material_id DESC`다.
5. **크기 표기:** 숫자를 SQL이 글자로 바꾼다. 소수 15자리를 넘는 값(예: `0.1+0.2`)은 JS 표기와 다를 수 있다. 저장되는 규격은 정수나 짧은 소수다.

## 6. 검색: 범위 안 비교와 FTS5 비교

| --- | --- | --- |

FTS5는 맞는 항목이 적을 때 적게 읽지만, 흔한 말은 결국 맞는 항목 수만큼 읽는다. 2글자 검색어에는 답을 못 한다.

**결정:** 범위 안 비교를 쓴다. 검색 첫 쪽은 기준(쪽 크기 비례)의 예외로 남는다. 범위 후보를 한 번 읽는데, 행이 가벼운 요약 행이고 payload는 읽지 않는다. 검색어 입력은 250ms 늦춰 보낸다.

## 9. 이미지

- **보이는 카드만:** 공개 목록은 IntersectionObserver(여유 0px)로 화면에 들어온 카드에만 `src`를 붙인다. 브라우저의 `loading="lazy"`는 화면 아래 먼 곳까지 미리 받아서 쓰지 않는다. 편집기 서랍과 관리자 자재는 `AssetImage lazy`로 같은 일을 한다.
- **같은 자산 메타 합치기:** cloud·관리자 프로젝트 저장소의 `assets.get`이 같은 id의 **진행 중** 요청만 함께 쓴다(`src/lib/repositories/batches.ts`). 편집기를 열 때 같은 이미지를 여러 곳이 동시에 묻던 것을 합친다. D1 결과 문서의 제안 1 가운데 "진행 중"만 택했다. 끝난 결과는 다시 쓰지 않으므로 다음 읽기는 늘 서버에 권한을 묻고, **권한 반영은 늦어지지 않는다**. "방금 끝난" 결과까지 몇 초 다시 쓰면, 같은 제품 사진을 다시 고를 때 서버 확인 없이 열려 지연 취소가 무의미해지는 것을 e2e(`editor.spec.ts`)가 보여 줘서 넣지 않았다(`tests/cloud-asset-client.test.ts`).
- **첫 쪽 크기(원격 측정, 사용자 승인):** 공개 목록 최신 48개의 카드 이미지는 합계 6,045,231바이트다. 평균 126KB, 가장 큰 것 404KB, 평균 594×975px다. 읽은 행은 144행이다.
  - 화면에 보이는 카드만 받으므로 처음 열 때는 약 10~16장(1.3~2MB)이다.
  - 목록용 작은 이미지(긴 변 256px)는 다음 작업에서 만들었다. 등록할 때 생성과 기존 자재 일괄 생성(관리자 버튼)이다([결과](list-thumbnails-results-20261023.md)).
