# 자재 이미지 등록·표시 정책

상품 소개 이미지(여러 장)는 없다. 제품은 방향별 **제품 이미지**(정면·왼쪽·오른쪽·뒤, 최대 4장)를 올리고, 목록에 보일 **대표 이미지**를 한 장 더 올릴 수 있다(선택, 2026-10-08). 타일은 **타일 텍스처**만 올린다. 위·아래 방향은 2026-10-08에 목록에서 없앴다(아래 "제품 각도 이름", "기존 자료").

## 이미지 올리기: 한 장 / 여러 장

모든 사진 입력은 버튼으로 고르거나 파일을 끌어 놓을 수 있다. 끄는 동안 받을 수 있는 영역에 초록 점선과 안내 문구가 보인다. 형식은 JPG·PNG·WebP, 한 장에 25MB까지다. 클릭 선택과 끌어 놓기는 같은 검사(`src/lib/file-drop.ts`)를 거친다. 올릴 수 없는 곳에 떨어뜨려도 브라우저가 파일을 열며 페이지를 떠나지 않는다.

| 위치                                                 | 장수    | 여러 장을 넣으면                                                                                                         |
| ---------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------ |
| 홈 시작 카드(사진으로 비교 공간 만들기)              | 한 장   | 받지 않고 "사진은 한 장만 올릴 수 있어요"라고 안내한다                                                                   |
| 홈 **기존 사진 위에 직접 편집하기** 줄               | 한 장   | 같음. 한 장이면 비교 창 없이 사진 위 편집을 시작한다                                                                     |
| 비교 공간 만들기 창의 **기존 공간 사진**             | 한 장   | 같음. 기존에 고른 사진을 유지한다                                                                                        |
| 사진 재구성 테스트 페이지의 **테스트할 사진**        | 한 장   | 같음                                                                                                                     |
| 자재 폼 **+ 타일 텍스처 올리기** 줄과 텍스처 목록    | 여러 장 | 모두 추가한다. 이미지가 아닌 파일·25MB 초과는 빼고 몇 개를 뺐는지 알려 준다. 목록 합계 100장까지                         |
| 자재 폼 **+ 제품 이미지 올리기** 줄과 제품 사진 목록 | 여러 장 | 위와 같다. 첫 장은 '정면', 이후는 아직 안 쓴 첫 방향(왼쪽·오른쪽·뒤 순서)이 붙는다. 방향마다 한 장, 최대 4장이다 |
| 자재 폼 **+ 대표 이미지 올리기(선택)** (제품만)       | 한 장   | JPG·PNG·WebP, 25MB 이하, 배경 제거·기준점 없음(연출 사진도 된다). 올리면 미리보기가 나오고 "대표 이미지 지우기"로 비운다 |

게스트 화면에서 사진을 끌어 놓으면 지금처럼 로그인 안내만 열린다.

## 휴대폰 사진: Ultra HDR·모션 포토·HEIC (2026-09-27)

요즘 휴대폰 JPEG에는 그림이 둘 이상 들어 있다. Android Ultra HDR와 iPhone HDR은 기본 이미지 뒤에 HDR 게인 맵 JPEG을 붙이고 APP2 `MPF`로 그 목록을 남긴다. 모션 포토는 JPEG 뒤에 짧은 영상을 붙인다. 서버 검사가 이런 파일을 "손상된 이미지"로 거부해, 이전에는 모든 사진 입력에서 올라가지 않았다.

- **가져올 때 첫 이미지만 남긴다.** 위 표의 모든 입력과 "사진 다시 분석"은 공통 `importImage`를 거친다. JPEG은 [jpeg-container](../src/lib/jpeg-container.ts)로 정리해 저장한다.
  - 첫 EOI 뒤(게인 맵 JPEG, 영상, Samsung 꼬리)를 버린다. 그것을 가리키는 세그먼트만 뺀다: MPF, ISO 21496-1 게인 맵 표지, 컨테이너를 설명하는 XMP(`Container:Directory`, `MotionPhoto`, `hdrgm:` 등).
  - 나머지 바이트는 그대로다(재인코딩 없음). EXIF 방향, ICC(Display P3 포함), 일반 XMP가 남고, 기본 이미지는 같은 픽셀로 디코딩된다.
  - 정리는 조용히 한다. 자산에 "게인 맵 제거" 같은 표시는 남기지 않는다. 기본 이미지가 바이트 그대로이고, 앱은 HDR 표시를 쓰지 않으며, 자산 저장 형식을 바꿀 이유가 없기 때문이다.
  - 정리한 결과는 서버와 같은 검사(`validateD1Image`)로 다시 확인한다. 구조가 손상된 JPG(끝이 잘림 등)는 저장 전에 "이 JPG의 구조가 손상돼 열 수 없어요…"로 막는다.
- **서버 검사는 약해지지 않았다.** [images](../src/lib/d1/images.ts)는 모든 스캔을 지나 첫 EOI가 파일 끝인지, MPF가 없는지 본다. 이전에는 첫 스캔에서 멈추고 끝 두 바이트만 봐서, 끝이 FFD9인 두 번째 JPEG이 MPF 없이 붙으면 통과했다. 지금은 이것도 거부한다.
  - 거부 문구는 "JPEG 뒤에 HDR·움직이는 사진 같은 다른 자료가 붙어 있어요. 페이지를 새로고침한 뒤 다시 올려 주세요."다. 정상 경로에서는 화면이 먼저 정리하므로, 이전 화면 코드로 올린 경우 같은 예외에서만 보인다.
  - 이미 저장된 자산은 다시 검사하지 않아 그대로 읽힌다.
- **HEIC/HEIF는 받지 않는다.** Chrome 등 대부분의 브라우저가 디코딩하지 못하기 때문이다. 고르거나 끌어 놓을 때, 또는 확장자만 `.jpg`로 바꾼 HEIC면 "HEIC 사진은 아직 올릴 수 없어요. JPG로 저장해 다시 올려 주세요(아이폰은 카메라 설정의 '호환성 우선')."라고 안내한다. 변환 기능은 없다.
- **저장소는 D1/R2 한 경로다.** 로컬(IndexedDB) 저장 모드는 없다. IndexedDB는 서버 저장이 성공한 뒤의 캐시와 복구본만 두므로, 화면과 서버가 같은 결과를 본다.
- 검증: 실제 Android Ultra HDR 사진 5장(저장소 `.codex-remote-attachments/…/1~5-Photo-*.jpg`)과 규격대로 만든 iPhone·Google·Samsung 형식 시험 파일을 썼다(실물 없음). 결과는 [검증 기록](verification.md)에 있다.

## 목록에 사용할 사진

- 제품: **대표 이미지**(자재 버전의 `coverAssetId`)가 있으면 그것을, 없으면 이름이 **정면**인 사진을 쓴다. 정면 사진이 없으면 등록 순서상 첫 방향 사진을 쓴다. 위·아래로 저장돼 있던 사진은 어디서도 쓰지 않는다. 도우미는 한 곳이다(`getMaterialImageAssetId`, [material-images.ts](../src/lib/material-images.ts)).
- 옛 이름은 읽을 때만 새 목록으로 바꿔 읽는다(`front`·`frontal`→정면, 오른쪽 측면·사선→오른쪽 등, 아래 "기존 자료"). 앞뒤 공백·영문 대소문자는 무시한다.
- 타일: 첫 렌더링 텍스처를 사용한다.
- 같은 규칙을 자재 라이브러리 카드, 상세 보기 큰 이미지, 편집기 자재 목록, 자재 수량·금액의 작은 이미지에 공통 적용한다.
- 사진 이름을 바꾸거나 사진을 삭제하면 규칙에 따라 표시 이미지가 달라진다. 대표 이미지는 새 필드나 마이그레이션 없이, 예전에 쓰던 `coverAssetId`를 다시 쓴다(프로젝트 문서와 `.strict()` 스키마에는 들어가지 않는다). 방 화면에는 쓰지 않는다. 타일에는 없다(저장할 때 지운다). 옛 대표·소개 이미지 ID가 남은 제품 자재는 이제 그 대표 이미지가 목록에 보인다.

## 제품 크기와 깊이

제품(타일이 아닌 분류)의 규격은 **가로·깊이·높이(mm)**이고 깊이 칸은 필수 입력이다. 360° 입체 제품의 앞뒤 비율을 맞추려던 "깊이를 꼭 입력해 주세요(10~5000mm)" 안내와 크기 맞추기는 360° 입체화와 함께 없앴다([제거 기록](product3d-removal.md)). 평면 사진 제품은 가로·높이로 배치하며 깊이는 자재 정보로 저장된다.

새 자재 등록 창은 타일 기본값(600×600×9mm)으로 열린다. 크기 칸을 직접 고치기 전까지는 카테고리를 바꾸면 크기가 그 종류의 표준 모형 기본값(`RECONSTRUCTION_DEFAULTS`·`reconstructionDefaults`)으로 바뀐다(2026-10-14). 예: 변기 400×750×680, 욕조 1500×600×750, 세면대는 설치 방식이 바닥이면 받침대형 600×800×480·그 밖에는 벽걸이 600×320×450. 수전은 표준 모형이 없어 크기를 그대로 둔다. 기존 자재를 고칠 때와 크기를 한 번이라도 입력한 뒤에는 바꾸지 않는다. 설치 방식은 따라 바뀌지 않는다. 전에는 크기가 그대로 남아, 변기의 AI 방향 사진 가이드가 깊이 9mm로 그려졌다.

## 제품 각도 이름

사진마다 **촬영 방향** 목록이 보인다. 이름은 입력하지 않고 정면·왼쪽·오른쪽·위·아래·뒤 중에서만 고른다. 이미 쓰는 방향은 비활성("사용 중")이고, 한 자재는 방향마다 한 장 최대 6장이다. 이름은 **그 사진에서 제품이 바라보는 방향**이며(방을 정면에서 볼 때: 정면=앞, 오른쪽=오른쪽 벽 쪽, 왼쪽=왼쪽 벽 쪽, 뒤=뒤 벽 쪽, 위·아래=위·아래에서 찍은 사진), 2D 편집기·3D 방·AI 변환이 이 이름에서 방향을 정한다([방 크기](room-dimensions.md)). `사선`과 `원본 사진 방향`은 목록에서 없앴다.

**옛 360° 자재(2026-10-04).** 360° 입체화로 저장한 각도(`views[].product3d`가 있는 각도)도 읽을 수 있다. 각도의 사진(`assetId`)은 저장 당시 자세로 캡처한 1024px 투명 PNG이고, 지금은 그 사진을 다른 각도처럼 평면 사진으로 보여 준다(목록·자재 패널·2D 편집기·3D 방·AI 변환 입력). 메시와 입력 사진 자산은 참조만 남고 열지 않는다. 자세한 내용과 데이터 정리 방법은 [제거 기록](product3d-removal.md)에 있다.

## 기존 자료

- **옛 각도 이름(2026-10-01):** 이름 목록을 닫으면서 이전에 저장한 이름을 읽을 때만 바꿔 읽는다. 저장된 값은 새로 저장하기 전까지 그대로다.
  - 오른쪽 측면·오른쪽 사선→오른쪽, 왼쪽 측면·왼쪽 사선→왼쪽, 뒤에서·뒷면·후면→뒤, `front`·`left`·`right`·`back`→같은 이름.
  - 목록에도 옛 이름에도 없는 이름(`사선`, `원본 사진 방향`, 직접 입력한 이름)은 정면으로 읽는다. 자재 수정 화면이 "이전에 저장한 이름 ‘X’을 읽을 수 없어 ‘정면’으로 보여 줘요. 방향을 다시 골라 주세요."로 알리고, 다시 고르기 전까지 그 마커(`directionWas`)가 남는다.
  - 읽기는 서버(D1 읽기 경로, 공개 카탈로그)에서 한다. 쓰기는 엄격하다(목록의 이름 4개, 중복 불가, 최대 4장).

기존 자재 버전에 남아 있는 대표·상품 소개 이미지 ID는 읽을 수 있다. 배치 사진이나 타일 텍스처가 있는 새 버전을 저장할 때 이전 대표 설정을 저장 상태에서 정리한다. 배치 이미지가 없는 예전 자재는 기존 이미지를 표시할 수 있도록 호환한다.

**방향별 사진이 화면마다 쓰이는 방식**(2026-10-05). 공간 둘러보기와 AI 입력 시점은 정면·오른쪽·뒤·왼쪽 네 방향(90°)으로만 보고, 제품은 그 방향에서 보이는 사진 한 장이 카메라를 보는 평면으로 보인다. 제품이 놓인 방향은 고른 사진의 이름이고, 카메라 방위 θ에서는 `base − θ`의 이름을 가진 사진을 쓴다(오른쪽 사진을 고른 변기를 오른쪽에서 보면 변기가 카메라를 보므로 정면 사진). 그 방향의 사진이 없으면 등록된 사진 중 가장 가까운 것을 쓰고(좌우를 뒤집어 쓰지 않는다) "뒤 화면: 변기의 ‘뒤’ 사진이 없어 ‘정면’ 사진을 썼어요. …"라고 알린다. 위·아래 사진은 이 네 화면에서 쓰지 않는다(등록·삭제는 그대로). 사진의 크기는 보이는 쪽으로 정한다: 정면·뒤 사진은 가로×높이, 왼쪽·오른쪽 사진은 **깊이×높이**에 보이는 영역을 맞춘다. 그래서 옆 사진을 올릴 때는 자재에 깊이를 등록하는 것이 좋고, 깊이가 없으면 가로로 그리고 알린다. 방향별 사진이 많을수록 시점마다 자연스럽다. 자세한 규칙은 [방 크기](room-dimensions.md)의 **네 방향 시점**이다.

새 제품을 **방(공간)에 처음 놓을 때**는 **면 먼저, 각도 나중**으로 사진을 고른다(2026-10-04). 놓을 면(바닥이면 `floor`, 아니면 선택한 벽이고 없으면 처음 만나는 벽)을 정한 뒤, 그 면에 어울리는 이름의 사진이 있으면 그 사진으로 놓는다(왼쪽 벽 → 오른쪽, 오른쪽 벽 → 왼쪽, 정면 벽 → 정면, `getPlacementViewIndex`). 어울리는 사진이 없으면 예전 순서(정면 → 첫 사진)로 놓고 "‘오른쪽’ 각도 사진이 없어 ‘정면’ 사진으로 놓았어요."라고 알린다. 속성 패널에는 이어서 "이 제품에는 ‘오른쪽’ 각도 사진이 없어요. 자재 편집에서 방향별 사진을 추가하면 바꿀 수 있어요."가 남는다(같은 안내를 두 번 하지 않도록, 처음 알림은 사실만 말한다). 바닥은 아무 이름이나 어울리므로 지금처럼 정면 우선이다. 이미 놓인 제품을 카탈로그에서 교체할 때는 이전 제품의 면을 따른다. 방이 없는 옛 2D 장면은 면이 없어 정면 우선 그대로다. 목록·자재 패널의 대표 사진 정책(`getPreferredProductViewIndex`, 정면 우선)은 바뀌지 않았다. 직접 등록한 변기·세면대·욕조는 제품 속성의 **표준 모형으로 보기**를 켜면 위·옆에서도 입체로 보이는 표준 모형으로 바뀐다(기본은 꺼짐, 켜는 동안 각도 썸네일은 숨고 `viewIndex`는 그대로이며 끄면 그 사진으로 돌아온다, [방 크기](room-dimensions.md)). 이미 공간에 배치된 제품의 `viewIndex`는 표시용 썸네일 정책 때문에 바꾸지 않는다. 기존 프로젝트의 불변 상품 버전과 사진도 그대로 유지한다. 각도 변경은 제품 속성의 사진 썸네일로 수행한다. 제품 속성에서 **설치 면을 바꿀 때**는, 지금 보이는 사진이 새 벽에 어울리지 않고 어울리는 사진이 있으면 면과 사진이 **한 번에**(실행 취소 한 번으로 함께 되돌아가게) 바뀌고 "각도를 ‘오른쪽’으로 바꿨어요."가 보인다. 면을 바꾸는 순간에만 그렇고, 사용자가 썸네일로 직접 고른 각도는 면이 그대로인 동안 바뀌지 않으며(어울리지 않으면 경고와 **맞는 각도로 바꾸기**만 보인다), 바닥으로 바꿀 때·잠긴 제품·편집 중 초안·표준 모형은 사진을 건드리지 않는다.

## AI로 방향 사진 만들기 (2026-10-13)

자재 폼(관리자 자재 등록·수정, 편집기의 신규 자재 등록)에서 **욕조·변기·세면대**는 제품 사진 1~3장으로 정면·왼쪽·오른쪽·뒤 사진을 AI(FLUX.2 klein 4B)로 만들어 방향 칸에 넣을 수 있다. 직접 방향 사진을 올리는 방법은 그대로다. 시험 근거와 실제 호출 결과는 [방향 사진 결과](direction-photo-results-20261013.md)에 있다.

- **흐름:**
  1. 제품 이미지 칸 위의 접힌 "AI로 방향 사진 만들기"를 연다.
  2. 참고 사진 1~3장(어느 각도든, 연출 사진도 된다)을 올리면 브라우저에서 배경을 지워(BiRefNet) 흰 바탕 미리보기를 보인다.
  3. 모양을 고르면 4방향 가이드 그림이 한 줄로 보인다(변기는 몸통·뚜껑, 투피스면 아래 모양, 그리고 몸통 색·시트 색). 모양·크기·설치 방식을 바꾸면 바로 다시 그린다. 변기 몸통이 일체형·비데 일체형이면 참고 사진마다 "찍은 각도"도 고른다.
  4. 방향마다 만드는지(또는 왼쪽 반전·만들지 않음), 방 화면에서 작아지는 정도, 예상 AI 요청 수와 뉴런(추정)이 보인다.
  5. "방향 사진 만들기"를 누르면 "만드는 중 n/N"과 "만들기 취소"가 보인다. 실패하면 서버의 문구(한도·로그인 등)를 그대로 보인다.
  6. 방향마다 후보 2장 중 하나를 고른다. "{방향} 다시 만들기"는 그 방향만 새 seed로 다시 만든다. 변기의 왼쪽·오른쪽은 가이드와 윤곽이 더 겹치는 후보를 앞에 두고 "가이드와 윤곽이 더 비슷한 후보(옆모습이 덜 돌아간 쪽)를 앞에 두었어요."를 보인다(2026-10-21, 브라우저에서 재고 AI·저장 없음, [candidate-order](../src/lib/direction-photo/candidate-order.ts)). Cloudflare 답에서 옆모습이 다른 후보 쌍 15개 모두 겹침이 큰 쪽이 더 옆모습이었다([옆모습 결과](toilet-side-view-results-20261021.md)).
  7. "고른 사진 넣기"는 고른 사진의 배경을 지우고 기준점을 잡아 그 방향 칸에 넣는다(그 방향 사진이 있으면 바꾼다).
  8. 사용자가 확인하고 "자재 등록"을 누른다. 자동 저장은 없다.
- **만드는 방향:** 정면·왼쪽은 늘 만든다. "좌우 대칭 제품"(기본 켬)이면 오른쪽은 고른 왼쪽 사진을 좌우 반전해 쓴다(로고·글자가 있으면 끄라고 안내하고, 끄면 오른쪽도 만든다). 뒤는 바닥형·매립형만 만들고 벽걸이형은 만들지 않는다(벽에 붙는 쪽은 방 화면에 보이지 않는다). 변기는 바닥형이어도 뒤를 만들지 않는다(벽에 붙여 설치하고, 2026-10-14~15 시험에서 뒤 답 19장 중 17장이 앞모습이나 앞쪽 사선이었다). 벽걸이 변기는 가이드가 없어 막는다(`planDirections`, [plan](../src/lib/direction-photo/plan.ts)).
- **가이드 그림**([guide-render](../src/lib/direction-photo/guide-render.ts), [guide-geometry](../src/lib/direction-photo/guide-geometry.ts)):
  - 그 종류의 표준 모형(`createTemplateModel`)을 등록 크기(가로·높이·깊이) 그대로, 무광 회색, 약 10° 위에서 직교 투영으로 그린다. 흰 바탕 가운데에 여백 약 5%를 두고, 바닥 제품만 옅은 접지 그림자를 넣는다. 크기는 긴 변 496px, 다른 변은 16px 단위(최소 128)다.
  - 모양: 욕조 타원형 독립 욕조(기본)·사각 욕조(벽에 붙이는, 기존 표준 모형), 세면대 벽걸이/받침대 × 둥근/사각 그릇(벽걸이형이면 벽걸이·둥근, 아니면 받침대·둥근이 기본). 타원형 독립 욕조는 2026-10-13 시험 렌더러의 모양을 표준 모형의 인자(`bathShape: 'oval'`)로 넣은 것이다.
  - 변기(2026-10-15): **몸통** 투피스(물탱크가 따로 올라감, 기본, 기존 표준 모형)·일체형(치마형 몸통과 바닥부터 솟은 물탱크가 한 덩어리)·비데 일체형(물탱크 없는 낮은 사각 몸통, 뒤쪽에 앞으로 낮게 기운 비데 덮개) × **뚜껑** 닫힘(기본)·열림·시트만(뚜껑 없음). 비데 일체형에는 열림이 없다(열린 뚜껑이 덮개 위로 솟는다). 일체형·비데 일체형 몸통은 표준 모형의 인자(`toiletBody`)이고 레버는 그리지 않는다(제품마다 자리가 달라 사진에서 온다). 모델은 가이드의 모양을 거의 그대로 그리기 때문에, 투피스 가이드는 곰 변기(일체형)·스마트 변기(비데 일체형)를 투피스로 바꿔 그렸다([결과](direction-photo-results-20261013.md) 4절).
  - 투피스 **아래 모양**(2026-10-18): 받침이 드러남(기본, 지금과 같음)·치마형(물탱크 아래 몸통이 매끈하게 바닥까지, 표준 모형 인자 `toiletSkirt`). 치마형 투피스(t5)는 받침 가이드로 6장 모두 받침 기둥이 됐고 치마형 가이드로 6장 모두 치마형이 됐다. 프롬프트는 바뀌지 않는다([양변기 결과](toilet-direction-photo-results-20261018.md)).
  - 변기의 몸통·뚜껑·아래 모양·색, 몸통별 문장, 뒤를 만들지 않는 규칙, 폼 라벨은 자재별 모듈 [categories/toilet.ts](../src/lib/direction-photo/categories/toilet.ts)에 있다. 다음 자재도 같은 틀(`categories/<자재>.ts`)로 나눈다. 욕조·세면대는 아직 옮기지 않았다.
  - 새 모양은 모두 가이드에서만 쓰고 저장하지 않는다(프로젝트 스키마 변경 없음).
  - 카메라: 모형의 앞은 +z다. 카메라 방위는 방향 각도의 반대다(정면 0°, 왼쪽 +90°(+x), 오른쪽 −90°, 뒤 180°). 그래서 왼쪽 가이드는 앞이 화면 왼쪽을 향하고 제품의 왼쪽 옆면이 보인다. 방이 그 이름의 사진을 정면 카메라로 보는 모습과 같은지를 단위 테스트가 좌표로 확인한다.
  - 크기가 비어 있으면 가이드를 그리지 않고 "가로·높이·깊이를 넣어 주세요"를 보이며 만들기를 막는다.
  - 크기가 라우트 범위(반올림해 10~10,000mm, `directionPhotoSizeOk`) 밖이어도 가이드를 그리지 않고 지금 크기와 함께 고쳐 달라고 안내하며 만들기를 막는다. 자재 등록 창은 타일 기본값(600×600×9mm)으로 열리고 카테고리를 바꿔도 크기가 그대로라, 고치기 전에는 깊이 9mm짜리 얇은 가이드를 그리고 요청 6회가 모두 서버 검사에서 "제품 정보 형식이 올바르지 않아요"로 거절됐다(추론 전 거절이라 사용량은 없음, 2026-10-14 변기에서 발견). 가이드 아래에는 그린 크기("가로 W × 높이 H × 깊이 Dmm로 그렸어요")를 적는다. 새 자재는 카테고리를 바꾸면 크기도 그 종류의 기본값으로 바뀐다([제품 크기와 깊이](#제품-크기와-깊이)).
- **방 화면에서 작아지는 정도:** 방은 사진의 보이는 영역을 비율대로 등록 크기 안에 맞춘다(정면·뒤 가로×높이, 옆 깊이×높이, `photoPlaneSize`). 10° 위에서 본 사진은 윗면만큼 키가 커서 제품이 그만큼 작게 그려진다(`planeShare`). 가이드 아래에 방향마다 적는다. 1700×560×750 타원 욕조는 정면·뒤 약 16%, 짧은 끝 약 33% 작아진다. 화면에 "윗면이 보이는 만큼 방 화면에서는 조금 작게 보여요."를 보인다.
- **프롬프트:** 서버가 enum·숫자만으로 쓴다. 자유 입력은 없다([prompt](../src/lib/direction-photo/prompt.ts), 문장 목록은 [결과](direction-photo-results-20261013.md)). 순서: image 0이 모양·윤곽·비율·카메라·크기·위치를 정한다는 문장(변기는 몸통·뚜껑 이름) → 카테고리별 앞 정의 → 방향 문장 → 그 시점에서 안 보이는 것(그리지 말 것) → 크기 → images 1–n은 재질·색·작은 세부에만 쓰라는 문장 → (변기에 색을 골랐을 때만) 색 문장 → (일체형·비데 일체형 변기만) 사진 각도 문장 → 순백 배경(#FFFFFF) 스튜디오 사진 → (변기의 왼쪽·오른쪽만) 옆 평면도 문장.
- **변기 몸통별 문장(2026-10-18):** 비데 일체형은 물탱크라는 말을 쓰지 않는다. 앞 정의는 "Its front is the bowl end, where a seated person's legs go; the seat unit at the back is its back. It has no water tank."이고, 방향 문장은 정면 "the low seat unit is behind it", 옆 "the seat unit is on the right/left"다. 전에는 몸통과 상관없이 "the tank …"라고 써서 비데 일체형 18장 중 10장에 물탱크가 그려졌고, 바꾼 뒤 22장 중 1장이었다. 투피스·일체형 문장은 그대로다.
- **변기 색(2026-10-18):** 몸통 색(사진대로(기본)·흰색·아이보리·회색·검정)과 시트·뚜껑 색(사진대로(기본)·몸통과 같음·흰색·회색·검정·파랑·분홍)을 고를 수 있다. 사진대로면 아무 문장도 보내지 않는다. 고르면 "The body, the seat and the lid are black.", "The body is white; the seat and the lid are blue."처럼 쓴다(시트만이면 "the seat"). 사진만으로는 검정 몸통이 6장 중 5장 흰색·회색, 1장 진회색으로 바뀌었고, 문장을 넣으니 8장 모두 맞았다. 화면은 흰색이 아닌 변기에 색을 고르라고 안내한다. 아이보리·회색·분홍과 투피스는 시험하지 않았다.
- **변기 옆 평면도 문장(2026-10-21):** 변기의 왼쪽·오른쪽 프롬프트 끝에 "Draw it as an orthographic side elevation, like a product drawing: no perspective, no turn toward the camera, the outline exactly that of image 0."를 붙인다(`toiletSideSentence`, 몸통 상관없이). 사진에 보이는 옆면(사진과 가까운 쪽)이 사진의 사선을 따라가던 문제를 줄인다. Cloudflare에서 곰 변기 가까운 쪽은 옆·살짝·사선 0·2·2가 2·2·0, 비데 일체형은 2·2·0이 3·1·0이 됐고, 먼 쪽은 그대로 옆이었다. 로컬 FLUX로 7개 제품 양쪽에서도 옆이 크게 늘었다. 곰 변기 레버는 4장 중 4장에서 2장으로 줄었다. 정면·욕조·세면대 문장은 그대로다([넓게 찾기 결과](direction-photo-explore-results-20261021.md)).
- **참고 사진의 찍은 각도(2026-10-15):** 변기 몸통이 일체형·비데 일체형일 때만 사진마다 고른다. 이름은 방향 칸과 같다(사진에서 제품의 앞이 향하는 쪽): 찍은 각도 모름(기본)·정면·정면과 오른쪽 사이·정면과 왼쪽 사이·오른쪽·왼쪽. 서버는 "Image 1 was taken from the front right of the product, from above: that is not the view to make. Turn the product to the view of image 0 and do not copy …"처럼 쓰고, 모름이면 "from another angle"로 쓴다. 만들 방향과 같은 각도의 사진이면 "가까운 시점이지만 image 0을 그대로 지켜라"로 쓴다(`photoAngleSentence`). 가이드가 제품과 비슷하면 모델이 사진의 각도를 베꼈고(12장 중 10장), 이 문장이 정면·옆 시점을 되살렸다. 욕조는 이 문장이 오히려 좁은 끝 시점을 잃게 해서(같은 seed 4장 모두) 욕조·세면대·투피스 변기에는 묻지도 보내지도 않는다.
- **배경 제거:** 참고 사진(올릴 때)과 고른 AI 사진(넣을 때)에 자동으로 적용한다(BiRefNet, 이 브라우저에서, 처음 한 번 모델 약 94MB). 직접 올리는 방향 사진은 지금처럼 사진마다 "AI 배경 제거 테스트"로 한다.
- **기준점:** 배경을 지운 사진의 불투명 윤곽(알파 128 이상)에서 바닥 제품은 아래 가장자리 가운데, 벽 제품은 가운데로 잡는다(`anchorFromAlpha`). 반전한 오른쪽은 반전한 윤곽에서 다시 잡는다.
- **대표 이미지:** 참고 사진을 올리면 "첫 참고 사진을 대표 이미지로 쓰기"가 보인다. 대표 이미지가 없으면 켜져 있고, 있으면 꺼져 있다. 켜면 넣을 때 첫 참고 사진 원본을 대표 이미지로 올린다.
- **저장:** 고른 사진은 새 제품 자산(`ai-alpha`, 투명 PNG)으로 저장되고 그 방향 칸만 바뀐다. 자재 버전 형식·저장 스키마는 그대로다.
- **권한·한도:** 서버 라우트는 로그인한 회원만 받는다(동일 출처 검사, [FLUX 변환](flux-export.md)의 **자재 방향 사진**). 자재 폼은 관리자에게만 보인다. 한도는 기존 AI 변환과 같은 Cloudflare 계정 한도다. 401·402·403·429·503을 받으면 남은 요청을 보내지 않고 같은 문구로 실패 처리한다. 자동 재시도는 없다.
- **비용(추정):** 호출 한 번은 (가이드 1 + 사진 n) × 5.37 + 출력 타일 × 26.05 뉴런이다(공식 요금표). 1700×560×750 욕조·대칭이면 정면 2·왼쪽 2·뒤 2 = 6회, 사진 1장이면 약 480, 2장이면 약 510뉴런이다(하루 무료 10,000뉴런).
- **한계:** AI 사진은 실제 제품과 다를 수 있다(화면에 "AI로 만든 사진은 실제 제품과 다를 수 있어요. 실제 제품과 비교해 확인하세요."). 가이드는 일반 모양이라 제품만의 모양은 사진에서만 온다. 같은 조건에서도 결과가 흔들려 후보를 고르게 했다. 모델이 문장을 따를지는 보장되지 않는다. 구현 뒤 실제 호출(2026-10-14, 욕조, 8회)에서 정면·뒤 4장은 가이드를 따랐지만 짧은 끝(왼쪽)은 4장 중 2장만 가이드의 비율을 지켰다(시험은 4장 모두). 변기 시험(2026-10-14~15)에서 일체형·비데 일체형 가이드와 사진 각도로 몸통 모양과 정면·옆 시점은 좋아졌지만, 곰 귀 같은 작은 모양 특징은 거의 나오지 않았고, 탱크 앞면 무늬(곰 얼굴)는 문장으로 시켜도 4장 중 2장만 맞아 넣지 않았으며, 비데 일체형의 뒤쪽 덮개를 물탱크처럼 그리는 일은 2026-10-18 몸통별 문장으로 거의 사라졌다(22장 중 1장). 일체형 사진이 오른쪽 옆에 가까운 각도면 오른쪽 방향이 사진의 사선을 따라간다(t1·t4 4장 모두, 문장·찍은 각도로도 고치지 못함). 2026-10-21 시험에서 원인은 사진에 보이는 옆면, 즉 사진과 가까운 쪽이었다(Cloudflare 가까운 쪽 옆 1/8, 먼 쪽 6/8). 후보 순서는 고르기를 도울 뿐, 두 후보가 다 돌아가 있으면 그대로다. 옆 평면도 문장(같은 날 넣음)으로 가까운 쪽 사선이 줄었지만 Cloudflare 확인은 곰·비데 일체형 몇 장뿐이고, 투피스는 로컬로만 봤다. 화면의 뉴런 추정은 실제보다 낮게 나온 것으로 보인다(2026-10-15에 추정 약 6,400, 2026-10-18에 약 5,070뉴런에서 하루 10,000 한도에 걸림). 벽걸이 변기·거울·수납장은 아직 없다.

## 외부 AI용 프롬프트 복사 (2026-10-12)

처음 이름은 "AI로 방향별 사진 만들기"였다. 2026-10-13에 앱이 직접 만드는 기능("AI로 방향 사진 만들기")이 생겨 헷갈리지 않게 이름만 바꿨다. 동작은 같다.

갖고 있는 제품 사진 한 장(카탈로그의 사선 사진, 위에서 찍은 사진, 연출 사진)으로 외부 이미지 생성 AI에서 정면·왼쪽·오른쪽·뒤 사진을 만들 때 쓸 **프롬프트를 자재 폼에서 복사**한다. 앱은 AI를 부르지 않고 문구만 만든다(외부 서비스 연동·자동 등록 없음).

- **어디에:** 자재 폼(관리자 자재 등록·수정, 편집기의 신규 자재 등록)의 제품 이미지 칸 위에 접힌 "외부 AI용 프롬프트 복사"(위의 "AI로 방향 사진 만들기" 아래). 펼치면 4방향 탭, 방향마다 읽기 전용 프롬프트 글상자와 "프롬프트 복사", 만드는 순서, 확인 목록, 카테고리별 권장 장수가 보인다. 사진 칸마다 그 칸의 방향으로 "이 방향 프롬프트 복사"가 있다. 화면 설명은 한국어, 복사되는 프롬프트는 영어다(생성 AI가 영어에서 더 일정하다).
- **복사:** `navigator.clipboard.writeText`(`src/lib/clipboard.ts`). 막히면 글상자의 프롬프트 전체를 선택해 두고 직접 복사하라고 알린다. 복사하면 "복사했어요"가 2초 보인다.
- **지켜야 할 제품 특징(선택):** 입력하면 프롬프트에 "Details that must stay the same: …"로 들어간다. 자재에는 저장하지 않는다.
- **프롬프트가 지키는 규칙**([product-photo-prompt.ts](../src/lib/product-photo-prompt.ts), 같은 입력이면 같은 문구):
  - 방향 이름은 사진 속에서 제품이 향하는 쪽이다. 정면은 앞이 카메라, 왼쪽은 앞이 사진의 왼쪽(카메라는 제품의 왼쪽 옆면), 오른쪽은 앞이 사진의 오른쪽(오른쪽 옆면), 뒤는 뒤가 카메라다.
  - 방은 정면·뒤 사진을 가로×높이로, 왼쪽·오른쪽 사진을 깊이×높이로 그린다(`photoPlaneSize`). 그래서 사진 속 제품의 가로 : 높이를 그 비율로 요청한다(소수 한 자리와 mm, 예: 3.0 : 1 (1700 : 560 mm)). 출력 화면 비는 비율이 1.3 이상이면 16:9, 0.77 이하면 3:4, 그 사이는 1:1.
  - 카메라: 바닥형·매립형은 "약 10° 위에서 내려다본다", 벽걸이형은 "제품 가운데 높이에서 정면". 근거는 방 화면 기본 카메라(편집기 가운데 3D 방·공간 둘러보기: 높이 1,200mm, 약 5.3m 앞, 시야각 50°, 기본 방 2400mm)에서 바닥 제품 가운데를 내려다보는 각도가 9~13°(변기 10~12°, 욕조 11~13°, 하부장 9°)이고, 벽 제품은 ±5° 안이라는 계산이다. AI 입력 화면(약 9.2m, 시야각 20°)은 5~7°다.
  - 공통: 첨부 사진은 제품 디자인을 알기 위한 것뿐이고 방은 무시한다. 같은 제품(모양·비율·세부·재질·색), 순백 배경(#FFFFFF), 바닥 질감·벽·소품·글자·워터마크·사람 없음, 아주 옅은 접지 그림자만, 85mm 망원 느낌, 여백 약 5%, 긴 변 2048px 이상.
  - 카테고리별 "제품의 앞": 변기는 앉은 사람의 다리 쪽(물탱크가 뒤), 욕조는 방 쪽 긴 면, 세면대는 사람이 서는 쪽, 하부장은 문·서랍 쪽, 거울은 거울 면, 거울 수납장은 거울 문, 수전은 토수구가 향하는 쪽, 샤워 설비는 사람이 서는 쪽, 벽 선반은 물건을 놓는 쪽, 벽 수납장은 문 쪽, 문·창은 욕실 안에서 보이는 면, 유리 파티션·낮은 칸막이는 욕실의 열린 쪽에서 보이는 면, 샤워 커튼은 방 쪽 면. 그 밖은 "사람이 쓸 때 향하는 쪽".
  - 정면이 아닌 방향은 "첨부 1은 원본, 첨부 2는 먼저 만든 정면 결과이니 디자인·색·조명·크기·카메라 높이를 맞춰라"로 시작한다.
- **안내:** 크기가 비어 있으면 크기·비율 줄을 빼고 "가로·높이·깊이를 먼저 넣으면 비율이 프롬프트에 들어가요"를 보인다. 벽걸이형의 뒤에는 "벽에 거는 제품은 뒤 사진이 거의 필요 없어요"를 보인다(복사는 된다).
- **순서:** 1) 원본 사진 준비 2) 정면 프롬프트를 원본과 함께 AI에 넣기 3) 결과 확인 4) 나머지 방향은 원본과 정면 결과를 함께 넣고 그 방향 프롬프트 5) 한 번에 한 방향씩 6) 결과를 같은 이름의 방향으로 등록.
- **확인 목록:** 같은 제품인가(모양·세부·색), 앞이 사진의 맞는 쪽을 보는가(왼쪽/오른쪽), 비율이 표시된 값과 비슷한가, 배경이 순백이고 소품·글자가 없는가, 가장자리가 잘리지 않았는가.
- **권장 장수:** 변기 정면·왼쪽·오른쪽(필요하면 뒤), 욕조 정면·왼쪽(좌우가 같은 욕조는 왼쪽 사진을 사용자가 좌우 반전해 오른쪽으로 써도 된다), 세면대·거울·거울 수납장 정면, 그 밖 정면.
- "AI로 만든 사진은 실제 제품과 다를 수 있어요. 실제 제품과 비교해 확인하세요."를 함께 보인다.

## 사진 업로드의 파일 읽기 오류

`NotReadableError`는 선택한 파일이 수정·이동됐거나 다른 프로그램의 잠금·권한 문제로 읽히지 않을 때 발생할 수 있다. [W3C File API의 오류 설명](https://www.w3.org/TR/FileAPI/#errorsAndExceptions)을 참고한다. 오류 문구만으로 해당 PC의 정확한 원인은 확정할 수 없다.

사진을 다운로드 폴더에 새 이름으로 저장하고, 편집 중인 프로그램이 있다면 닫은 뒤 업로드에서 파일을 다시 선택한다. 클라우드 폴더의 파일은 먼저 PC에 내려받는다.

공통 `importImage`는 파일을 한 번 읽은 바이트로 검증·디코딩·원본 저장을 진행한다. 원본 디스크 File 참조를 Blob에 재포장하여 계속 사용하는 경로를 제거했다. 첫 읽기부터 실패하면 파일명과 한국어 재선택 안내를 표시하며 저장소에 쓰지 않는다. 첫 읽기 권한 자체를 우회하지는 않는다.

2026-09-12 검증: `tests/image-import.test.ts` 7개는 읽기 1회·메모리 스냅샷 사용·원본 바이트 보존·오류 후 저장소 미접근·재선택을 검사한다. `e2e/upload-read-error.spec.ts` 2개는 실제 브라우저에서 읽기 오류를 주입하고 제품/공간 업로드의 안내·입력 보존·동일 파일 재선택 후 저장을 확인했다. 해당 PC에서 실제 파일을 잠그거나 사용자 원본 파일의 권한을 조사한 결과는 아니다. 기존 `e2e/material-images.spec.ts` 3개도 통과했다. 전체 단위 테스트 512개와 타입·변경 파일 ESLint·Next/vinext 빌드 통과. vinext 이후 Next 라우트 타입을 다시 생성해 검사했다.

## AI 모델 준비 진행률

배경 제거는 모델을 준비하는 동안 [공용 진행 표시](../src/components/model-loading-progress.tsx)로 전체 %·받은 MB·단계를 보인다.

- **배경 제거:** 실행 모듈 → 모델 다운로드(또는 저장된 모델 읽기) → 초기화까지 한 막대로 보이고, 처리·PNG 변환은 기존 문구로 돌아간다. 막대의 접근성 이름은 기존 `모델 다운로드 진행`을 유지한다.
- **캐시와 실패:** 저장된 모델을 읽을 때도 0→100% 이벤트를 보낸다(다운로드 방식은 그대로다). 처음 내려받을 때는 "처음 한 번만 내려받아요" 안내를, 캐시 저장에 실패하면 그 안내를 보인다. GPU 실패 후 CPU 재시도는 %를 되돌리지 않고 남은 구간에서 이어 간다.

2026-09-26 검증: `tests/ai-progress.test.ts` 12개, `e2e/model-loading-progress.spec.ts`(모의 Worker, 모델 다운로드·추론 없음).
