# AI 현장 사진 변환: 빈 방은 AI, 도기는 3D 렌더로 합성

SJN "AI로 현장 사진처럼"(FLUX) 결과에서 도기가 실제 제품과 다르게 바뀌고, 없던 물건(유리 칸막이·샤워기 등)이 생기는 문제를 구조를 바꿔 해결한다. 방식은 "빈 방은 AI가, 도기는 우리가 합성"이다. 먼저 docs/flux-export.md, docs/flux-input-in-room-results-20260927.md, docs/export-realism-stage-3-results-20260927.md를 읽는다.

## 지켜야 할 규칙

- **도기 위치는 3D 렌더가 정한 그대로 둔다(가장 중요).**
  - 도기 레이어는 빈 방 렌더와 같은 `RoomViewerRenderer`·같은 카메라·같은 캡처에서 그린다. 선택한 "AI 입력 시점"(방 안 · 가운데 / 왼쪽 모서리 / 오른쪽 모서리 / 저장한 방 안 시점)을 쓴다.
  - 도기는 픽셀 단위로 3D 렌더 위치에 놓는다. AI 결과를 보고 도기 위치·크기를 옮기거나 맞추지 않는다.
  - AI가 방 구도를 틀었으면 도기를 움직이지 말고 알림으로 알린다.
- 좌표 변환: AI 출력은 `fluxInputLayout`으로 흰 여백을 붙인 496px 입력의 2배다. 최종 결과는 원래 캡처 좌표로 되돌린 뒤 합성한다. 여백 위치와 배율을 정확히 계산하고 테스트로 고정한다.
- 유료 호출:
  - FLUX·Gemma 실제 호출은 사용자 승인 후에만 한다.
  - 1차 실험 예산은 klein 4B 최대 8회(회당 약 110뉴런)와 Gemma 확인 최대 8회다.
  - 9B·dev 모델은 따로 승인받는다(9B 약 1,390뉴런/회).
- 기존 방식(도기를 포함한 렌더를 보내는 방식)은 실험으로 새 방식이 낫다고 확인되고 사용자가 채택할 때까지 그대로 둔다.
- 커밋·푸시는 사용자 승인 후에만 한다(main 푸시 = 운영 자동 배포). dev 서버·typecheck 뒤에는 `git checkout -- next-env.d.ts`.

## 참고할 현재 구조

- 입력 캡처: 편집기 `captureAiInput`(src/components/editor/editor.tsx), 시점은 src/lib/ai-export/view.ts(`fluxView`, `FLUX_EYE_*`).
- 3D 렌더러: src/lib/room-viewer/renderer.ts
  - `fixtures.group`, 면적광 샘플 평균 부드러운 그림자(accumulate.ts, shadow.ts)
  - 면 마스크(region-mask.ts), `fixtureBounds`
- 3D 도기 표현: src/lib/room-viewer/fixtures.ts
  - 입체 데이터가 있는 제품은 저장 메시(`createSavedProductGeometry`)로 그린다.
  - 나머지는 선택한 각도 사진(`material.views[fixture.viewIndex]`)을 평면(`planeGeometry`)으로 그린다.
- 프롬프트·장면·확인: src/lib/ai-export/prompt.ts, scene-contract.ts, check-contract.ts, notices.ts, 색 검사·보정
- 채택하지 않은 이전 "설비 되돌리기" 코드: 커밋 7172b00, c98ef27. 실패 이유는 세 가지였다: 붙인 렌더가 평평하고 밝음, 모델이 그린 설비 윤곽이 겹침, 모델이 옮긴 설비와 정렬 불가.

## 할 일

1. **두 레이어 캡처** (같은 카메라, 한 번의 캡처)
   - ① 빈 방: `fixtures.group`을 숨기고 벽·바닥·천장·타일·천장 조명만 렌더한다. 그림자도 도기 없이 계산한다.
   - ② 도기 레이어: 방을 숨기고 도기만 투명 배경(알파)으로 렌더한다.
   - ③ 도기 그림자 레이어: 도기가 방에 드리우는 그림자만 곱셈용으로 분리한다. 예: "도기 있음 방 렌더 ÷ 도기 없음 방 렌더"의 밝기 비율.
   - 세 장 모두 같은 해상도·같은 픽셀 좌표여야 한다. ②를 ① 위에 그대로 올리면 지금의 3D 렌더와 같아야 한다는 테스트를 만든다.
2. **AI 입력 = ① 빈 방** (+ 실험 B만 도기 자리 표시)
   - 빈 방 모드의 프롬프트에는 도기를 "있다"고 쓰지 않는다. 쓰면 모델이 그린다.
   - 대신 "방에는 설비가 없다. 샤워기·유리 칸막이·수전·선반·가구를 추가하지 말라"와 기존 타일·천장 문장을 쓴다.
   - 실험 B: 도기 자리에 도기 실루엣보다 몇 px 작은 무채색 회색 자리 표시를 둔다. 모델이 "빈 욕실 채우기"를 덜 하는지, 자리 표시 주변에 자연스러운 그림자를 주는지 본다. 자리 표시는 최종 합성에서 ②가 완전히 덮어야 한다.
3. **합성: AI 결과 + ③ 그림자 + ② 도기**
   - AI 결과를 캡처 좌표로 되돌린다.
   - ③을 곱해 도기 그림자를 넣는다.
   - ②를 3D 렌더 위치 그대로 올린다.
   - 가장자리는 1~2px만 부드럽게 한다(위치·크기는 바꾸지 않음).
4. **도기 밝기·색 맞춤** (위치·모양은 그대로, 색·밝기만)
   - 도기 주변 벽·바닥에서 "AI 결과 ÷ ① 입력"의 밝기·색온도 비율을 재서 도기 레이어에 적용한다.
   - 비율 상한을 두어 과하게 바뀌지 않게 한다.
   - 이전 실패인 "평평하고 밝게 떠 보임"이 줄었는지 수치(L* 차이 등)로 확인한다.
5. **각도 자동 선택** (사진 평면으로 그리는 도기만)
   - 도기마다 카메라에서 도기를 보는 방향을 구한다.
   - 그 방향에 가장 가까운 저장 각도 사진을 AI 내보내기 캡처에서만 쓴다. 각도 정보: 입체화 각도의 `product3d.pose`, 또는 이름(정면·측면·사선).
   - 프로젝트에 저장된 `viewIndex`는 바꾸지 않는다.
   - 각도 정보가 없거나 사진 비율이 달라 도기 발자국(가로·높이·기준점)이 바뀌면 사용자가 고른 `viewIndex`를 쓴다. 이 규칙을 테스트로 고정한다.
   - 입체 메시로 그리는 도기는 메시 렌더 그대로 쓴다.
6. **확인·알림**
   - 기존 Gemma 확인의 "추가 물건" 판정은 그대로 쓴다. 대상은 AI 결과, 즉 도기를 붙이기 전의 방이다.
   - 도기 확인(바뀜·옮겨짐)은 새 방식에서는 필요 없으니 새 모드에서 끈다.
   - 방 구도 어긋남 알림을 추가한다. AI 결과와 ①의 벽·바닥 경계(바닥선) 어긋남을 재서 기준을 넘으면 "AI가 방 구도를 바꿔 도기가 떠 보일 수 있어요"라고 알린다. 기존 색 검사의 흐린 윤곽 정렬 척도를 재사용할 수 있다.

## 실험 (승인 후, 4B, 같은 seed 2개)

- 장면: 기본 방(사용자 사례의 테라조 벽·밝은 바닥·벽걸이 세면대·핸드샤워·양변기)과 흰 타일 방. 시점: 방 안 · 가운데 + 모서리 하나.
- 비교: 현재 방식 / 새 방식 A(빈 방) / 새 방식 B(빈 방 + 회색 자리 표시). 호출이 8회를 넘지 않게 조합한다.
- 호출 전에 결과마다 정답표를 적는다: 없던 큰 물건·작은 물건, 도기 일치, 떠 보임.
- 잴 것:
  - 도기 레이어 픽셀이 3D 렌더와 같은가(위치·크기 오차 0px 목표)
  - 없던 물건 개수
  - 도기 주변 L*·색차
  - 바닥선 어긋남
  - 응답 시간·뉴런
- 채택 기준(사용자와 확정):
  - 도기 위치·모양 100% 유지
  - 큰 추가 물건이 현재 방식보다 적음
  - 떠 보임이 눈에 띄지 않음

## 검증

- 단위 테스트: 좌표 변환(여백·2배), 레이어 합성 = 기존 렌더, 각도 선택 규칙, 밝기 맞춤 상한, 빈 방 프롬프트에 도기 문장 없음
- 브라우저 테스트: 모의 FLUX 응답으로 합성 결과의 도기 위치 픽셀 일치, 390px 가로 넘침 없음
