## 2. 사용자에게 먼저 확인할 범위

### 이미 진행해도 되는 작업

- 기존 설치된 Node/브라우저/Ollama/Python 환경과 디스크에 준비된 모델로 로컬 분석·재생·검증.

- 단위·브라우저·9장 실제 테스트, 새 진단·비교 자료 작성.
- 새로운 모델·배포 방식의 공식 자료 조사와 기존 환경에서의 실행 가능성 확인.

기존 Python은 현재 정밀 분석의 MoGe 실행에 이미 연결되어 있다. 이 경로를 검증할 때마다 다시 허락을 요청할 필요는 없다. 웹앱 자체는 Next.js/Node.js이며 Python은 공간 분석 작업자라는 점을 유지한다.

### 실제 도입 전에 질문할 작업

- 새로운 모델 가중치의 다운로드, 다른 모델로 교체, 새로운 Python 환경이나 시스템 의존성 설치·업그레이드, GPU 설정 변경.
- 접속 사용자에게 새 대형 모델을 내려받게 하거나, 브라우저/로컬 작업을 다른 PC·서버 처리로 바꾸는 일.
- 상시 서버·컨테이너·서비스 추가, 실행 기본값을 다른 엔진으로 변경, 배포 구조 변경.
- 유료 API·과금 자원·클라우드 자원 생성·실제 배포·사진의 외부 전송. 이 프롬프트만으로 허용된 것이 아니다.

질문 전에 로그·코드·공식 자료로 필요성을 확인하고 가능한 사전 검토를 끝낸다. 사용자에게 다음 내용을 짧고 구체적으로 제시한다.

3. 실제 실행 위치: 방문자 브라우저 / 현재 개발 PC / 별도 서버.
4. 라이선스·상업 이용 조건, GPU/CPU 지원, RAM/VRAM 요구의 공식 수치와 미검증 추정 구분.

## 3. 현재 실패를 후보 단위로 재확인한다

직전 기록은 9장 중 부분 개선 1장, 자동 재현 부족 7장, 미설치 설비 0개 유지 1장이다. 모델 원후보 40개 중 배치 3개·보류 36개·제외 1개였다. 원후보에는 소품·미지원 종류·오분류가 포함되므로 40개를 정답 개수나 재현율의 분모로 사용하지 않는다. 카메라 추정은 2장, 보류는 7장이었다.

우선 확인할 실제 단서:

## 4. 개선 우선순위와 구현 원칙

### A. 방 구조 후보를 실제 관측으로 검증한다

- 단일 최대 평면이나 사진 좌우만으로 뒤벽·옆벽을 선택하지 않는다. 벽/바닥 분할, 법선, 깊이 잔차, 실제 지지 픽셀, 경계·교선, 가시 범위와 직교 관계를 함께 확인한다.
- 한 벽의 여러 패치와 같은 방향의 다른 벽·단차를 구분한다. 같은 방향이라는 이유만으로 합치지 않는다. 합동 평면 적합·거리·가림/경계 근거를 기록한다.
- 가능한 방 구조 후보는 제한된 수로 만들고 후보마다 근거, 모순, 유효한 면, 선택/보류 이유를 기록한다. 기존 코드의 점수를 측정된 정확도 확률처럼 표시하지 않는다.
- 거울의 반사 공간·유리 뒤 실제 벽·문틀·창 밖을 구분한다. 바닥이 좁게 보이거나 가려졌다는 이유로 보이는 패치를 방 전체로 확대하지 않는다.
- 상대 깊이를 곧바로 mm로 바꾸지 않는다. 방 치수·카메라·평면 좌표의 변환과 관측 가능한 자유도를 명시한다. 숨은 벽, 실제 렌즈, 제품 실측치를 알아냈다고 주장하지 않는다.
- 사진 모양에 맞춘 특정 좌표, 파일명·해시별 분기, `orthogonal=true` 강제, 모호성을 숨기는 일괄 임계값 완화는 금지한다.

### B. 설비마다 배치 가능성을 독립적으로 검증한다

- 어느 공통 기하 정보가 실제로 필요한지 확인한다. 방 구조 일부가 불확실해도 관측된 지지면과 후보들 사이에서 안정적인 관계를 얻을 수 있는 설비는 개별적으로 평가한다.
- 여러 유효한 방 구조 후보에서 같은 설치 벽·높이 범위·상대 배치가 일관될 때만 근거 있는 추정 제안으로 사용한다. 방 전체 카메라의 확정 여부와 제품별 배치 근거를 분리한다.
- 설치 기준점, 모형 원점, 중심/앞면/벽 접점, 기둥 접지점, 규격 축, quaternion·회전 단위와 mm 변환을 대조한다. 기둥형 세면대의 세면볼 하단을 바닥 접지점으로 사용하지 않는다.
- 방 밖 모형을 강제로 축소·이동하지 않는다. 관측된 형태/크기·설치 위치에 근거한 대안이 있으면 별도 제안으로 검증하고, 기본값과 관측값을 구분한다.
- 픽셀 중첩과 실제 3D 충돌을 구분한다. 유리 뒤 욕조·변기·벽의 정상 가림을 충돌로 제거하지 않는다. 물리적으로 충돌하거나 지지가 없는 배치는 통과시키지 않는다.
- 위치를 확정할 수 없는 후보는 보존하고 필요한 최소 정보만 요청한다. 설치 벽·방향·높이 등을 기존 간단한 확인 UI에 연결한다. 수동 입력을 자동 배치 실적으로 계산하지 않는다.
- 원사진 카메라가 불확실하면 정밀 재투영 점수를 만들지 않는다. 실제 생성 모형을 카메라로 투영할 수 있을 때만 비교한다. 원 bbox를 다시 그려 정확한 투영처럼 보고하지 않는다.

### C. 종류·형태·설치 관측의 모순을 해결한다

- 세면대의 노출 배관, 아래 빈 공간, 기둥, 닫힌 수납 본체, 상판·세면볼 관계를 함께 관측해 벽걸이/기둥/하부장형을 구분한다. 설치 관측이 종류 변경까지 정당화하는지 별도로 검증한다.
- 현재 설치 v2가 종류·bbox를 바꾸지 않는 계약임을 존중한다. 종류 보정이 필요하면 검증 가능한 별도 제안/계약 revision을 만들고 원후보·원응답을 보존한다. 알려진 값과의 충돌을 몰래 덮어쓰지 않는다.
- 거울이라는 물리적 표면과 거울 속 반사 물체를 구분한다. reflected 값 하나로 물리적 거울 자체를 삭제하지 않는다. 실제 거울·거울장과 비친 설비의 관계를 검증한다.
- 선반은 종류 이름만 아니라 높이·위치·용도 및 주변 관계를 대조한다. 높은 수건 랙과 낮은 수전 받침을 같은 정답으로 계산하지 않는다.
- 색 추출이 배경·그림자를 제품색으로 가져오는지 확인한다. 흰색 제품과 실제 노란색/청록색 제품을 구분한다.
- 이전 설치 프롬프트 A/B의 오분류 증가 기록을 읽는다. 응답 필드가 많아졌다는 이유로 관측이 좋아졌다고 판단하지 않는다.

## 5. 9장 고정 평가와 실험 방법

케이스 ID·원본 경로·평가 참고는 기존 `before-reconstruction-nine-photo-repair.md`의 2절을 사용한다. PC 4장과 원격 5장 모두 유지한다. 원본 바이트 해시를 검증하고 사진별 visible / absent / uncertain 참고표를 직접 확인한다. 그 표는 평가용으로만 사용하며 사진별 정답을 AI 프롬프트·배치 코드에 넣지 않는다.

전후 조건은 실측이 아닌 동일한 기본 방 2400×2400×2400mm, 동일 공통 표시 카메라·출력 크기다. 사용자가 나중에 실측값을 제공하면 별도 조건으로 비교하며 기존 결과와 섞지 않는다. 9장은 이미 본 개발 사례라는 한계를 밝힌다.

1. 먼저 변경 가설을 소수로 나눈다. 예: 벽 조각 판별, 설치 기준점 오류, 거울 역할 구분. 각 가설의 관측 지표·악화 위험·채택 기준을 코드 변경 전에 적는다.
2. 저장된 실제 관측으로 재생·단위 검증한다. Qwen 출력이 필요한 변경은 기존 준비 모델로 실제 대조 실행한다. 재생/캐시/새 추론을 분리한다.
3. 한 번에 여러 변수를 바꾸지 않고 중간 결과를 비교한다. 품질에 도움이 없는 변경은 최종 적용에서 제외하되 이번 실험 파일과 결과는 보존한다. 기존 사용자 변경사항을 되돌리지 않는다.
4. 최종 채택 후보는 9장 모두 실제 분석부터 표준 모형 생성·렌더링까지 실행한다. 관련 새 관측의 실제 AI 추론을 포함하고 정확한 캐시 사용 여부를 기록한다. 모의 응답은 실패 경계 테스트에만 사용한다.
5. 자동 결과를 원본과 직접 비교하고, 원후보와 실제 배치된 모형 ID를 연결해 판정한다. 평가 불가·불확실은 그대로 남긴다.
6. 정상 생성/재분석 화면에서도 동일 엔진을 써서 저장·재진입·수정·비교·출력을 확인한다. Lab만 성공하는 구현으로 끝내지 않는다.

성공 지표는 올바른 종류·설치 방식·상대 위치의 주요 설비 증가, 설비 있는 사진의 빈 결과 감소, 불필요한 확인 감소다. 단순 생성 개수 증가·보류 감소·실행 오류 0건·테스트 통과는 품질 향상의 증거로 충분하지 않다.

평가에는 정답에 대응된 주요 설비, 누락, 오탐, 반사 중복, 잘못된 설치 벽/형태/높이, 실제 배치된 제품의 상대 크기와 방향, 색·거울·유리 표현을 포함한다. 소품과 미지원 건축 구조는 별도 집계한다. mm 정답이 없으므로 치수 정확도 점수나 근거 없는 백분율을 만들지 않는다.

- pc-04의 기존 창·거울·변기 결과가 악화되지 않았는지 확인한다.
- remote-05는 주요 설비 0개를 유지해야 한다. 홈·배관 미재현은 구조 한계로 별도 기록한다.
- 다른 사진에서 오탐·반사 중복·충돌이 늘어난 변경은 평균 배치 개수로 숨기지 않는다. 악화 원인을 해결하거나 채택에서 제외한다.
- 유리나 거울 관련 후보를 모두 보류해 화면에 나타나지 않은 결과를 투명도·가림·반사 중복 처리 성공으로 계산하지 않는다. 실제 생성된 해당 설비의 결과를 확인해야 한다.
- 모델/기하가 끝내 부족하면 실제 비교 근거를 갖춰 다음 실험을 제안하고, 새 환경이 필요한 부분만 사용자에게 확인한다. 로그나 UI만 추가하고 품질 개선을 완료했다고 말하지 않는다.

## 6. 기존 서비스와 실행 환경 유지

- 사진으로 시작하면 재구성 Before와 같은 크기·공통 표시 카메라의 빈 After, 사진 없이 시작하면 양쪽 빈 기본 공간을 유지한다.
- Before/After 공통 표시 카메라와 원사진 해석용 카메라를 분리한다. 재분석의 targetFrame 및 원본 참조·After 시안 보존을 유지한다.
- 기존 시안별 편집·복사·undo/redo·저장 충돌 처리·자산 참조·견적 집계를 유지한다. 표준 설비에 임의 판매 가격을 넣지 않는다.
- 거울 표면에 원본 반사 풍경을 붙이지 않는다. 유리는 독립 반투명 모형으로 유지한다. 복잡한 레이어·수동 마스크·다각형 편집 UI를 되살리지 않고 기본 벽·바닥 삭제 방지를 유지한다.
- AI 진척·취소·재시도·늦은 응답·장시간 작업을 처리한다. 동시에 여러 GPU 추론을 중복 실행하지 않고, 취소 후 작업자 종료·자원 회수를 확인한다.
- 분석 계약·모델·프롬프트·전처리·사진·방 설정·기하 추출 revision을 캐시 키와 유효성 검증에 반영한다. 이전 캐시를 새 관측으로 가장하거나 사용자 캐시를 일괄 삭제하지 않는다.
- 현재 로컬 Python/CUDA 경로는 개발 환경 전용이며 Cloudflare Workers/production에서 미지원이다. 미지원 표시와 명시적 분석 선택을 유지한다. 조용히 다른 엔진으로 대체하지 않는다.
- 모델·사진·로그가 Next trace 또는 Cloudflare 빌드 산출물에 포함되지 않는지 확인한다. 실제 배포나 사용자 사진 외부 업로드는 승인 없이 하지 않는다.

## 7. 진단·테스트·완료 산출물

기존 JSON·IndexedDB 진단에 후보별 원값/보정값/최종값, model / geometry-derived / rule-inferred / default / user 출처, 구조 후보별 선택·탈락 근거, 설치·충돌·모형 범위 판단, 첫 원인과 연쇄 실패, 시간·메모리·캐시·코드 revision을 연결한다. 요청/취소/실패 때 확보한 근거도 보존한다. 로그 한도·저장 실패·새로고침 다운로드를 유지하고 바이너리나 사진을 JSON에 불필요하게 중복하지 않는다.

관련 단위·브라우저 회귀, lint, 타입 검사, Next.js와 vinext 빌드를 순차 실행한다. 정상 사용자 화면에서 실제 AI 생성 → 저장 → 새로고침 → Before 수정/undo/redo → 재분석 → 빈 After 보존 → 비교 PNG를 검증한다. 미확정 후보 확인 결과는 자동 결과와 별도로 시험한다. 변경한 캐시/계약·부분 기하·충돌·가림·반사·손상 관측·취소·늦은 응답·WebGL 실패도 검사한다.

최종 새 실행 폴더에 다음을 제공한다.

- **9행 × 3열 PNG와 확대 HTML:** 원본 / 이번 작업 직전 자동 결과 / 개선 후 자동 결과. 동일 구도·치수·해상도, 개별 PNG도 제공. 생성 결과를 손으로 고치거나 생성형 이미지 도구로 꾸미지 않는다.
- **summary.json 및 케이스별 평가표:** 올바른 배치·누락·오탐·중복·위치 오류·확인 필요 이유, 개선/동일/악화/평가 불가 판정. 사용자 확인 결과는 별도 자료다.
- **추론 원문·진단·실험 대조:** 입력 manifest/해시, 모델·코드·설정 revision, 전후 단계 추적, 채택/폐기 이유.
- **새 docs 보고서:** 원인·변경 파일/함수·일반 화면 사용법·실제 품질 증거·테스트 통과/실패/미실행·남은 한계·실행 구조와 배포 제약.

시간은 모델 다운로드/로드/각 추론/분할/기하/렌더/전체 및 캐시 적중을 구분한다. CPU/GPU/RAM/OS/브라우저/WebGL 백엔드·동시 작업 조건을 기록한다. Python RSS, CUDA allocator, 브라우저 heap 등 실제 측정 범위만 보고하고 전체 시스템 최고치로 합산하지 않는다. 미측정 항목은 명시한다.

완료 보고의 첫머리에 품질이 실제로 얼마나 달라졌는지 말한다. 모든 사진이 정밀 복원됐다고 과장하지 않는다. 개선이 제한적이면 코드·검증 완료와 품질 목표 미달을 분리하고, 무엇이 남았으며 다음 결정에 어떤 증거/승인이 필요한지 구체적으로 적는다.
