## 1. 지켜야 할 것

- **원칙: 권한과 공개 범위 판단은 한 건도 바뀌면 안 된다.** 누가 무엇을 볼 수 있는지는 그대로 두고, 같은 판단을 덜 자주, 덜 비싸게 하도록만 바꾼다.
- **사용자 결정이 필요한 것**: 권한 회수가 늦게 반영될 수 있는 변경은 구현 전에 선택지와 영향을 보이고 결정을 받는다. 예: 브라우저 캐시 시간, 메타 결과 재사용 시간, 준비 검사 재사용 시간.
- **절차**
  - `.agents/skills/d1-query-budget/SKILL.md`를 따른다: 요청 1회 쿼리 수, 읽은 행, 쓴 행, N·5N 비교, 화면 호출 횟수.
  - `.agents/skills/sjn-workflow/SKILL.md`와 references의 `database.md`, `development-environment.md`를 먼저 읽는다.
- **새 폴링과 새 요청을 만들지 않는다.** 줄이는 작업이다.
- **원격 D1 `sjn`**
  - 쓰지 않는다. 읽기는 `wrangler d1 insights`와 `wrangler d1 info`만 자유롭게 쓴다.
  - `wrangler d1 execute --remote` SELECT는 쿼리 원문과 예상 읽기 행을 보이고 승인받은 뒤에만 실행한다.
  - 새 migration은 로컬과 테스트 DB에만 적용한다. 원격 적용은 사용자가 정한다.
- **비밀값**: 토큰과 비밀값은 채팅, 소스, 로그에 넣지 않는다. `wrangler login`은 사용자가 한다.
- **git**
  - 커밋과 푸시는 사용자가 요청할 때만 한다. 그냥 `git stash`는 쓰지 않는다.
  - 최신 `origin/main`에서 새 브랜치를 만들어 시작한다.
- **형식**: Prettier로 쓸 때는 `--end-of-line crlf --write`, 검사할 때는 `--end-of-line auto`를 쓴다. typecheck 뒤에는 `next-env.d.ts`를 되돌린다. CSS는 Tailwind를 쓴다.

## 2. 0단계: 지금 상태 재기 (코드 변경 없음)

### 2-1. 운영 통계 (읽기만)

- wrangler가 로그인돼 있지 않으면 사용자에게 `npx wrangler login`을 부탁한다.
- 다음을 실행해 결과를 표로 정리한다.
  - `npx wrangler d1 info sjn`: 24시간 읽기·쓰기, DB 크기
  - `npx wrangler d1 insights sjn --timePeriod=7d --limit=25 --json`을 `--sort-by=reads`, `count`, `writes`로 각각
- 관리자 화면 `/admin/ai-usage`의 "오늘 DB 사용량"이 보이면 그 값도 적는다(운영 토큰이 있어야 보인다).
- 위 A~H가 통계의 어느 쿼리에 해당하는지 짝을 맞춘다.
  - A: `d1_user_management`·`admin_roles` 조회와 세션 조회의 실행 횟수
  - B·C: 자산 확인과 `listImageOf` 조회
  - D: `sqlite_master` 조회
- 통계에 **새로 상위에 오른 쿼리**가 있으면 후보에 더한다. 10-17 이후 생긴 기능(목록 쪽, 정렬, 종류 관리, 기본 배치, 카드 이미지)의 쿼리를 특히 본다.

### 2-3. 요청 1회 비용 (로컬 D1)

- 위 요청 경로마다 d1-query-budget의 래퍼나 기존 측정 테스트(`tests/d1-read-cost.test.ts`, `tests/d1-write-cost.test.ts`)로 쿼리 수, 읽은 행, 쓴 행을 잰다.
- 이때 바깥 라우트의 세션·역할 확인도 포함해 "요청 1번에 실제로 드는 값"을 잰다.
- F(정리 후보 검색)는 관리자처럼 참조된 자산이 수천 개인 소유자로 N·5N을 재고, `EXPLAIN QUERY PLAN`을 본다.

### 2-4. 보고하고 우선순위 받기

다음 표를 만든다: 화면 흐름 × 요청 수 × 요청 1회 비용 = 하루 추정(사용 패턴은 운영 통계로 보정). 이 표로 A~H의 순서를 제안하고, 사용자 결정이 필요한 항목(3절의 ★)은 선택지와 함께 묻는다.

## 3. 개선 (0단계 우선순위대로, 하나씩)

### A. 역할 확인을 탭당 하나로

- `useSharedCatalogAdmin`을 앱 수준의 공유 구독 하나로 바꾼다(컨텍스트나 모듈 단일 저장소).
  - 컴포넌트 수와 무관하게 30초 주기 1회, 포커스·표시 전환 1회만 부른다.
  - 진행 중인 요청은 합친다.
  - 화면이 숨겨지면 멈춘다.
  - `sjn-admin-role-changed` 이벤트는 지금처럼 즉시 다시 확인한다.
- 서버는 지금처럼 요청마다 권한을 확인한다. 이 훅은 화면 표시용이므로 보안 동작은 같다.
- E와 묶을지 판단한다. 예: 세션 확인 응답에 역할을 실어 한 요청으로 만들기. 묶으면 응답 계약과 계정 변경·정지 처리(`ACCOUNT_CHANGED`, `account_suspended`)가 그대로인지 테스트한다.
- **기준**
  - 2-2의 "편집기 5분"에서 역할 요청이 (5분 ÷ 30초) + 포커스 횟수 이하
  - "자재 수정 창 3회"에서 창 열기·닫기 때문에 생기는 역할 요청이 0

### B. 자산 읽기 요청 줄이기 ★

선택지를 측정값과 함께 제시하고, 사용자가 고른 것만 구현한다.

1. **한 요청으로 합치기(권장 후보)**: raw 요청에 `If-None-Match: <contentHash>`를 보낸다. 서버는 권한 확인 뒤 같으면 304를 돌려주고(R2 본문 읽지 않음), 다르면 본문과 메타(헤더)를 돌려준다. 요청은 1개로 줄고, **권한 확인은 지금처럼 매번 한다**(반영 지연 없음).
2. **끝난 메타 결과를 같은 페이지에서 잠시 재사용**: 예) 60초. 요청이 더 줄지만, 권한 회수가 그만큼 늦게 반영된다.
3. 지금 그대로

구현할 때 지킬 것

- 401·403·404면 캐시를 지우는 지금 동작(`invalidateCachedCloudAsset`)을 유지한다.
- 관리자 프로젝트 범위(`/api/admin/project-assets`)도 같은 방식으로 맞춘다.

### C. 목록·공개 이미지 브라우저 캐시 ★

자산 id의 바이트는 바뀌지 않는다. 다만 그 이미지를 볼 권리는 바뀔 수 있다(자재 비활성, 공유 해제). 다음 선택지를 측정값과 함께 제시한다.

| 대상                                                          | 선택지 예                                                                                                           |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 공개 카탈로그 이미지(`/api/catalog/images`, `size=list` 포함) | `public, max-age=300` / `3600` / `86400`, 또는 지금처럼 `no-store`. 길수록 비활성 자재 이미지가 그 시간 동안 남는다 |
| 회원 카드 이미지(`/api/d1/assets?...&size=list`)              | `private, max-age=…` + ETag/304. 다른 사람에게는 캐시되지 않는다                                                    |
| 원본 raw(`/api/d1/assets?...&raw=1`)                          | B-1을 하면 따로 바꾸지 않아도 된다                                                                                  |

- 응답에는 `Vary`·`X-Content-Type-Options` 등 지금 헤더를 유지한다.
- 계정이 바뀌거나 로그아웃할 때 `private` 캐시가 남는 문제가 없는지 확인한다. 같은 브라우저의 다른 계정이 URL만으로 이전 계정의 이미지를 캐시에서 받지 않아야 한다. 필요하면 URL에 계정 구분자를 넣거나 `private` 캐시를 쓰지 않는다.
- 공개 이미지에 Cloudflare 엣지 캐시(Cache API)를 쓸지는 제안만 한다. 무효화 규칙이 필요하다.

### D. 준비 검사 재사용 ★

- 같은 Worker 인스턴스(isolate) 안에서 **성공한** 준비 검사 결과를 짧게(예: 5분) 재사용한다.
  - 실패는 재사용하지 않는다.
  - 한도 초과(`daily_limit`) 감지는 다른 요청들이 이미 하므로 안내는 그대로 나와야 한다. 이것을 테스트로 확인한다.
- migration 직후 최대 재사용 시간만큼 옛 결과가 보일 수 있다. 그래서 재사용 시간은 사용자에게 묻는다.
- `checkD1Storage`의 문장 수 자체를 줄일 수 있으면 함께 본다. 예: `LIMIT 0` 문장들을 한 batch로. 결과(어떤 스키마 문제를 잡는지)는 그대로여야 하며, 기존 테스트(일부 컬럼·색인을 깨뜨리면 실패)로 증명한다.

### F. 정리 후보 검색

- 2-3에서 1회 읽은 행이 자산 수에 비례하면 고친다. 예: 색인, 후보를 좁히는 순서, `NOT EXISTS`의 색인 사용.
- 정리 대상이 한 건도 바뀌지 않아야 한다. 옛 SQL과 나란히 실행하는 같은 결과 테스트를 만든다(`tests/d1-visibility-equivalence.test.ts` 방식).

### G·H

측정값만 결과 문서에 적는다. 하루 추정이 무료 한도의 5%를 넘을 때만 개선안을 제안한다.

## 4. 테스트

- **회귀 테스트**(d1-query-budget 2절): 바꾼 경로마다 쿼리 수와 읽은 행 기준을 `expect`로 고정한다(N·5N).
- **같은 결과 증명**: 권한·공개 범위·정리 대상이 옛 동작과 같은지 확인한다. 바꾼 SQL은 옛 SQL과 나란히 실행해 비교한다.
- **화면 e2e**: 2-2 흐름의 요청 수 기준을 고정한다. 예: 역할 요청, 카드 이미지 재요청, 자산 메타·raw 수.
- **캐시 테스트**(B·C)
  - 304 경로
  - 권한 회수 뒤 403·404와 캐시 지우기
  - 계정 바뀜
  - 공개 자재 비활성 뒤 동작(고른 캐시 시간 안·밖)
- **준비 검사 테스트**(D): 재사용 중에도 한도 오류 안내가 나오는지, 실패는 재사용하지 않는지
- **기존 검사**
  - D1 시험은 차례로 돌린다(11-04 문서 9절, 약 24분): `npx vitest run tests/d1-*.test.ts tests/admin-projects.test.ts tests/admin-ai-usage.test.ts --fileParallelism=false`
  - `npm run typecheck`, `npm run lint`, Prettier 검사
  - 관련 e2e
