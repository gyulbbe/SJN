# 자재별 방향 사진 ①: 양변기 전용 가이드·프롬프트 개선

## 0. 배경과 범위

자재 등록의 "AI로 방향 사진 만들기"(`src/lib/direction-photo/**`, 라우트 `/api/materials/direction-photo`, 폼 `src/components/materials/direction-photo-generator.tsx`)는 지금 욕조·변기·세면대를 같은 틀로 만든다. 이 틀은 표준 모형 가이드(image 0)에 참고 사진(images 1~3)과 서버가 쓴 문장을 더하고, FLUX.2 klein 4B를 쓴다.

사용자는 앞으로 **타일을 뺀 자재마다 전용 프롬프트와 가이드**를 만들 계획이다. 이번 작업은 그 첫 번째로 **양변기**(`category: 'toilet'`)만 다룬다.

- 사용자가 정한 앞으로의 자재 종류: 타일, 양변기, 소변기, 세면대, 수전, 샤워기, 욕조, 샤워부스, 파티션, 욕실장, 하부장, 액세서리, 환풍기, 천장
  - **이 목록으로 분류를 바꾸는 일은 이번 범위가 아니다.** 분류는 DB CHECK 제약, 타입, 렌더링, AI 계약이 얽힌 별도 작업이다.
  - 양변기는 기존 `toilet` 그대로 쓴다.
- 벽걸이 변기는 지금처럼 만들지 않는다(가이드 없음). 시험 사진에도 없다.
- 욕조·세면대의 가이드와 프롬프트는 **한 글자도 바뀌면 안 된다.** 스냅샷 테스트로 확인한다.

## 2. 지켜야 할 것

- **AI 호출**
  - 사용자는 FLUX를 **하루 무료 제공량 안에서는 모두 써도 된다**고 했다. 못 끝나면 다음 날 이어서 한다. 무료 플랜이라 한도를 넘으면 429가 나고 과금되지 않는다.
  - 그래도 묶음마다 시작 전에 호출 수와 추정 뉴런을 보고하고, 장부(ledger)에 모든 호출을 남긴다.
  - `AI_BUDGET_NEURONS`는 하루(UTC) **6,500 추정 뉴런**으로 둔다. 하루 한도는 10,000이지만 지난 기록상 추정이 실제보다 약 1.5배 낮았기 때문이다.
  - 자동 재시도는 하지 않는다. 429나 `quota_exhausted`가 나면 그날은 멈추고, 다음 날(한국 시간 09:00 이후) 같은 장부로 이어 간다.
  - Gemma와 다른 모델은 쓰지 않는다. klein 4B만 쓴다.
- **문장 원칙**
  - 모델에는 enum과 숫자에서 서버가 쓴 문장만 보낸다. 제품명, 사용자 입력, 자유 문장은 보내지 않는다.
  - 새 선택지는 사용자가 폼에서 고르는 enum으로 만든다.
- **저장**: 방향 사진 선택지는 지금처럼 저장하지 않는 폼 상태로 둔다. 저장이 필요하다고 판단되면 구현 전에 사용자에게 묻는다. 그 경우 DB를 거치는 변경이므로 D1 읽기 비용도 확인한다.
- **3D 방 모형**: `templates.ts`의 저장된 변기 모형(방 렌더링에 쓰이는 투피스)은 바꾸지 않는다. 가이드 전용 옵션(`toiletBody`처럼 "never stored")으로만 늘린다.
- **비밀값**: 토큰과 비밀값은 채팅, 소스, 로그에 넣지 않는다. `wrangler login`과 `.dev.vars` 비밀값은 사용자가 한다.
- **권한 분류기**: `wrangler dev` 등이 막히면 우회하지 않고 사용자에게 실행할 명령을 준다.
- **git**: 커밋과 푸시는 사용자가 요청할 때만 한다. 그냥 `git stash`는 쓰지 않는다.
- **형식**: Prettier로 쓸 때는 `--end-of-line crlf --write`, 검사할 때는 `--end-of-line auto`를 쓴다. typecheck 후에는 `next-env.d.ts`를 되돌린다.
- **시작**: 최신 `origin/main`에서 새 브랜치를 만들어 시작한다.

## 3. 0단계: 준비 (AI 호출 없음)

1. **정답표 확인**: 1절 표를 사용자에게 보여 주고 확인받는다. 특히 t5 몸통, 찍은 각도, 크기를 확인한다.
2. **시험용 Worker 준비**
   - 하네스는 `FLUX_WORKER`(기본 `http://127.0.0.1:8799`)로 시험용 Worker를 부른다.
   - 원본 `test-results/product-representation/real/gen/tools/flux-test-worker.js`는 다른 PC에만 있을 수 있다. 없으면 `test-results/toilet-direction/tools/`(git 제외)에 최소 Worker를 새로 만든다.
     - 라우트(`src/lib/direction-photo/server.ts`)와 같은 모델 입력을 쓴다: multipart, `input_image_0`~, 가이드의 두 배 크기, seed.
     - klein 4B만, 요청당 한 번, 재시도 없음, 게이트웨이 없음, `127.0.0.1`에서만 받는다.
   - `wrangler dev`(원격 AI 바인딩)로 띄운다. 막히면 사용자에게 명령을 준다.
3. **하네스 확장**(`tests/direction-photo-real/variants.ts`)
   - 1절의 t1~t6을 `PRODUCTS`에 추가한다(정답표의 몸통·뚜껑·각도·크기).
   - **배경 제거를 넣는다.** t1(연출 배경·인증 마크)과 t6(리모컨)은 배경이 있다. 화면과 같은 배경 제거(BiRefNet, `src/lib/background-removal/**`)를 하네스에서도 거치게 하고, 보낸 사진(`sent-*.png`)을 저장한다. 지금 하네스는 배경이 이미 없는 사진을 전제로 이 단계를 뺀다.
4. **가이드 미리보기**: `GUIDES_ONLY=1`로 6개 제품 × 정면·왼쪽·오른쪽 가이드를 그리고, 사진과 나란히 놓은 시트를 만든다. 가이드와 실제 제품의 모양 차이를 표로 적는다. 예: t5는 치마형 투피스인데 가이드는 받침 기둥, t2는 각진 상자인데 가이드는 둥근 모서리, t3은 뒤쪽 유닛이 높다.
5. **배경 제거 결과 확인**: t1·t6의 누끼에 인증 마크와 리모컨이 남는지 본다. 남으면 7절의 "누끼 정리"를 후보에 넣는다.

## 5. 2단계: 양변기 전용 개선 시험 (한 번에 하나씩, 같은 seed)

| E 비데 일체형 뒤쪽 유닛 높이 | `tankless`에 `unit`: `low`(지금의 낮은 판)·`tall`(t3처럼 높은 상자)                   | 뒤쪽 유닛이 물탱크가 되거나, 높은 유닛이 판이 됨 | 지난 시험에서 "물탱크 없음" 문장만으로는 효과가 없었다(4/4가 여전히 물탱크). 가이드 모양으로 시험하고, 필요하면 "The raised part at the back is the seat unit of a tankless toilet, not a cistern." 같은 고정 문장을 한 번 더 비교한다                                              |
| F 시트 색                    | `seatColor`: `same`·`different`                                                       | t1의 파란 시트가 흰색으로 바뀜                   | `different`일 때만 "The seat and the lid are a different colour from the bowl: take each colour from the photos." 같은 고정 문장을 쓴다                                                                                                                                             |
| G 누끼 정리                  | 배경 제거 뒤 **가장 큰 덩어리만** 남기기(작은 떨어진 덩어리 제거)                     | 리모컨·인증 마크가 사진에 남아 결과에 그려짐     | 3단계 확인에서 남았을 때만 한다. 변기 외 자재에도 영향이 있으므로 사용자에게 먼저 알린다                                                                                                                                                                                            |

- 변형마다 결과를 1단계 표와 같은 기준으로 채점한다. 효과가 있었던 변형만 다음 변형과 겹쳐 본다.
- 끝나면 **채택 후보와 근거(장 수)**를 사용자에게 보여 주고 결정을 받는다. 지난 작업처럼 "효과가 꾸준하지 않은 것"은 채택하지 않는다.
- 하루 예산을 넘으면 다음 날 이어 간다. 이어 갈 때는 장부의 마지막 상태와 남은 시험 목록부터 보고한다.

## 6. 3단계: 앱에 넣기 (사용자 결정 뒤)

### 6-1. 자재별 구조

앞으로 자재마다 전용 가이드와 프롬프트가 생기므로, 양변기부터 **자재별 모듈**로 나눈다(예: `src/lib/direction-photo/categories/toilet.ts`). 각 모듈에 넣을 것은 다음과 같다.

- 그 자재의 enum(몸통, 뚜껑, 이번에 채택한 선택지)
- 가이드 옵션
- 방향 문장, 안 보이는 것, 추가 문장
- 만들 방향 규칙(변기는 뒤 없음)
- 폼 라벨

욕조·세면대는 이번에 옮기지 않아도 된다. 옮긴다면 **프롬프트·가이드 출력이 그대로인지** 스냅샷으로 증명한다. 다음 자재를 같은 틀에 넣을 수 있게 구조만 맞춘다.

### 6-2. 구현과 테스트

- **계약**(`contract.ts`): 새 enum은 `toilet`에만 허용하고, 몸통에 맞지 않는 조합은 거부한다(예: `skirt`는 `two-piece`만, `outline`·`unit`은 `tankless`만).
- **폼**: 선택지마다 한국어 라벨과 짧은 도움말을 둔다. 기본값은 지금과 같은 결과가 나오게 둔다(선택하지 않으면 기존 프롬프트·가이드와 동일). 필요하면 선택지 옆에 작은 가이드 미리보기를 보여 준다.
- **테스트**
  - 프롬프트 결정성: 같은 spec이면 같은 문장
  - 방향별 레버 문장 표(기하 규칙)
  - 스키마 거부 조합
  - 욕조·세면대·기존 변기 기본값의 프롬프트 스냅샷이 그대로인지
  - 가이드 렌더 브라우저 테스트: 새 옵션의 실루엣 차이와 가이드 PNG 확인
  - 폼 e2e: 선택지가 보이고 요청 spec에 실리는지(AI 호출 없이 라우트 모의)
- **사용량 표시**: 화면의 "AI 요청 N회 · 약 N뉴런"이 바뀐 구성에서도 맞는지 확인한다.

## 7. 4단계: 실제 화면 확인 (예산이 남으면, 아니면 다음 날)

- 로컬 개발 서버에서 관리자 자재 등록 → 양변기 → 사진 → 방향 사진 만들기 → 후보 고르기 → 칸에 넣기까지 실제로 한다(`tests/direction-photo-real/run.mjs` 방식).
- 대상은 **t1**(배경 제거, 파란 시트, 레버)과 **t6**(리모컨, 비데 일체형)이다. 정면·왼쪽·오른쪽 × 후보 2 = 제품당 6회, 합계 약 12회다.
- 로컬 준비(`npm ci`, `.dev.vars`, `npm run db:dev:migrate`, 관리자 지정)가 안 돼 있으면 `development-environment.md`의 "첫 로컬 실행"을 따른다. 비밀값은 사용자가 넣는다.
- 원격 AI 바인딩은 `wrangler.dev.jsonc`에 이 확인 동안만 붙이고 끝나면 되돌린다(커밋 금지).
- 자재는 저장하지 않는다. 저장까지 확인해야 하면 사용자에게 묻는다.

## 8. 검증

- 바꾼 파일의 단위 테스트와 브라우저 테스트
- `npm run typecheck`, `npm run lint`, Prettier 검사
- 전체 `npx vitest run`: 알려진 환경 실패(reconstruction-corpus 해시, source-plane-mapping 기준 파일, D1/R2 첫 연결 5초 초과)만 남아야 한다.
- 욕조·세면대 회귀: 프롬프트·가이드 스냅샷이 그대로여야 한다(AI 호출 없이).
