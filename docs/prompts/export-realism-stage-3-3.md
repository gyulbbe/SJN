# 사실감 3-3: 원본 사진의 조명(밝기·색온도)에 렌더 맞추기

"사진으로 비교 공간 만들기"로 만든 프로젝트에서, Before·After 렌더의 빛 분위기를 **원본 사진과 같게** 맞춰줘. 조사나 계획 설명에서 멈추지 말고 측정, 구현, 테스트, 문서, 보고까지 끝낸다. 단 3-3a의 판단 기준을 통과하지 못하면 그 자리에서 멈추고 보고한다.

## 0. 배경과 범위

- 1~3단계로 렌더 사실감(방 안 시점, 겹쳐 찍기, 사진 효과, 설비 그림자)과 FLUX 대기 표시·제품 확인을 마쳤다([3단계 결과](../export-realism-stage-3-results-20260927.md)).
- **이번 목표**: 사진으로 만든 프로젝트의 After가 "다른 욕실"이 아니라 "우리 집 욕실이 바뀐 모습"처럼 보이게 한다. 원본 사진의 **밝기(노출)와 색온도(화이트 밸런스)**를 렌더 조명에 반영한다.
- **범위**
  - 대상은 "사진으로 비교 공간 만들기"로 만든 프로젝트만이다(`comparison.referenceOriginalAssetId`가 있는 프로젝트). 사진 없는 기본 방은 대상이 아니다.
  - 사진은 한 장 기준이다(여러 장 사진은 하지 않는다).
  - 창 위치·조명 종류처럼 AI가 필요한 판별은 이번 범위가 아니다. **AI 호출 없이** 사진 픽셀 통계로만 한다.
  - FLUX가 자재 색을 바꾸는 문제(3단계 남은 한계: 흰 벽 → 베이지)는 별도 과제다. 여기서는 다루지 않는다.

## 1. 반드시 알아야 할 현재 구조 (2026-09-27 main `9a83bb5` 확인)

- **비교 공간 생성**: `createReconstructionProject`(`src/lib/reconstruction/index.ts`)
  - 원본 사진은 `comparison.referenceOriginalAssetId`로 보관한다.
  - 편집용 배경은 `renderRoomBackground(room)`로 새로 그린다("같은 구도의 비교 공간 생성 중").
  - 벽·바닥 면마다 `createReconstructionTile`로 타일 자재를 만든다.
  - 기본 분석 방식은 `browser-basic`이다. DeepLab·MoGe 등 브라우저 모델만 쓰고 클라우드 AI는 부르지 않는다.
- **중요: Before 타일 색에는 사진 조명이 이미 섞여 있다.**
  - 면의 타일 색은 사진 픽셀의 채널별 중앙값이다(`analysis.ts` → `candidates.ts`의 `representativeColor`, 밝기 35~245 범위).
  - 그래서 사진이 어둡거나 누렇게 찍혔으면 그 기운이 Before 타일 자재 색에 그대로 들어가 있다.
  - After에서 사용자가 새로 고른 카탈로그 자재는 실제 색이다. 이 둘이 한 화면에 섞인다.
  - **렌더 조명만 사진에 맞추면 Before의 바뀌지 않은 면은 조명이 두 번 적용된다.**
- **설비 색**: `resolveProductColor`(`product-color.ts`)가 관측 색이나 기본값을 쓴다. 유리·거울 등은 중립 기본값이다.
- **색 조절**
  - `Scene.color: ColorAdjust { exposure, contrast, saturation, warmth }`(`src/lib/types.ts`)는 편집기 "밝기와 색감"(`inspector.tsx`)에서 사용자가 조절하는 값이다.
  - 2D 합성(`compositor.ts`)과 3D(`renderer.ts`, `sjnBeforeColor/sjnAfterColor`) 모두 반영된다. 설비에도 각자 `color` 조절이 있다.
- **렌더 경로**: 비교 공간 프로젝트는 벽 구조가 없으면 2D 합성, 있으면 3D 렌더러를 쓴다. 공간 둘러보기·고화질 내보내기는 3D다.
- **시험 사진**: `.codex-remote-attachments/01a071fe-92b3-77b3-a261-8698b3d3f8e9/04c0e236-9188-46ed-9a61-a8ff283287f8/1~5-Photo-*.jpg`(git 포함, 1280×960)
  - 서로 다른 실제 욕실 5곳이다: 회색 타일 샤워+변기, 오래된 흰 타일, 좁은 화장실, 베이지 타일+세면대, 시공 중인 빈 욕실.
  - 같은 폴더 `01a07bcf…`의 다른 이미지들은 휴대폰 화면 캡처라 쓰지 않는다.

## 4. 설계 원칙: 조명과 자재 색을 분리한다

1. **사진 조명 추정** → "사진 조명 프로필" `{ exposure, whiteBalance(채널 이득 또는 색온도·틴트) }`
2. **Before 자재 색에서 조명 걷어내기**: 사진에서 뽑은 타일·설비 색을 프로필로 나눠(선형 공간) **추정 실제 색**으로 저장한다.
3. **렌더에 조명 입히기**: Before·After 모두 같은 프로필을 조명으로 적용한다.

이렇게 하면 다음이 성립한다.

- Before는 다시 사진과 비슷해진다.
- After의 새 카탈로그 자재는 사진과 같은 빛 아래 보인다.
- 바뀌지 않은 면은 이중 적용이 없다.

이 원칙과 다른 방법이 더 낫다고 판단되면 근거를 들어 3-3a 보고에 제안한다.

- **프로필 적용 위치**
  - 사용자의 "밝기와 색감"(`Scene.color`)과 섞지 않는다. 별도 값으로 두고, 사용자 조절은 그 위에 그대로 얹는다.
  - 조명 색·세기로 넣을지, 톤 매핑 전 이미지 단계에서 곱할지는 2D·3D 양쪽에서 같은 결과가 나오는 쪽으로 정한다.
- **실제 색 추정의 한계**: 면 안의 조명 기울기(천장 등 감쇠)와 그림자는 걷어내지 못한다. 중앙값 기반이라 대표값만 보정된다. 이 한계를 문서에 적는다.

## 5. 3-3a 측정과 관문 (코드는 시험용만, 사용자 동작 변화 없음)

- 시험 사진 5장을 기존 `browser-basic` 분석으로 비교 공간 프로젝트로 만든다. **클라우드 AI 호출 없음.** 만약 호출이 필요하게 되면 멈추고 사용자에게 호출 수·비용을 알려 승인받는다.
- **조명 추정 방법을 비교한다**(예시, 더 나은 방법 가능)
  - 노출: 벽·천장·바닥 영역 밝기의 강건 중앙값. 기준 대비 로그2 비율로 둔다.
  - 화이트 밸런스
    - 거의 무채색인 영역(천장, 흰 줄눈, 흰 도기, 흰 타일)의 회색 가정
    - 전체 회색 세계 가정
    - 두 방법을 섞은 방식
  - 영역은 기존 DeepLab 분할과 분석의 면(plane) 정보를 쓴다.
  - 조명 추정값은 범위를 제한한다. 예: 노출 ±1.5EV, 색온도 약 2,700~7,500K 상당. 근거가 약하면 중립으로 둔다.
- **사진마다 비교한다**
  - (a) 지금의 Before 렌더
  - (b) 조명을 걷어낸 자재 + 프로필 조명으로 그린 Before 렌더
  - 두 렌더를 원본 사진과 비교한다.
  - 같은 구도이므로 벽·바닥·설비 영역별 평균 색의 ΔE2000과 밝기 차를 잰다.
- **After 시험**: 같은 프로젝트에서 흰색·회색 카탈로그 타일로 바꾼 After를 프로필 켬·끔으로 그리고, 사진과 나란히 놓는다.
- **추정 실제 색이 그럴듯한가**
  - 흰 타일 사진(2번)과 회색 타일 사진(1·5번)에서 조명을 걷어낸 색이 무채색 쪽으로 가는지 확인한다.
  - 베이지 타일(4번)이 베이지로 남는지 확인한다(과보정 금지).
- 결과 이미지는 `test-results/photo-lighting-match/`에 사진 | 지금 Before | 새 Before | After 끔 | After 켬 순서로 저장하고 직접 확인한다.
- **관문(모두 만족해야 3-3b로 간다)**
  1. 새 Before가 지금 Before보다 사진과 가깝거나 같다. 5장 중 4장 이상에서 영역 평균 ΔE가 줄거나 0.5 안에서 같고, 나빠진 사진이 없다(+1 초과 없음).
  2. 베이지·회색 같은 유채색 타일이 무채색으로 과보정되지 않는다.
  3. After 켬이 끔보다 사진과 분위기가 맞다(나란히 비교, 근거 이미지 제시).
- 통과하지 못하면 구현하지 않고 멈춘다. 원인과 대안(예: 노출만 맞추기, 수동 버튼만 제공)을 보고한다.

## 6. 3-3b 구현 (3-3a 통과 시)

- **저장**
  - 프로필과 "조명 걷어낸 색"은 **새로 만드는 비교 공간 프로젝트**에만 넣는다.
  - 기존 프로젝트는 값이 없으면 지금과 똑같이 그린다. 기존 문서를 거부하거나 조용히 바꾸지 않는다.
  - 저장 검증 스키마·정규화·D1/로컬 저장에 새 필드를 더하고 이전 형식 호환 테스트를 넣는다.
  - 기존 프로젝트에 적용하는 "사진 조명 다시 계산" 동작을 둘지는 제안만 한다.
- **렌더**: 2D 합성, 3D 실시간, 시안 미리보기, 고화질 내보내기, FLUX 입력 캡처가 같은 프로필 규칙을 쓴다. 미리보기 캐시 키(렌더러 버전)를 올린다.
- **화면**
  - 편집기 "밝기와 색감" 근처에 "사진 조명 맞춤" 켜기/끄기와 세기(0~100%)를 둔다.
  - 새 비교 공간은 기본 켬이다.
  - 켜져 있을 때 "원본 사진의 밝기·색온도에 맞춘 화면이에요. 자재 본래 색은 끄고 확인하세요." 같은 안내를 둔다.
  - 끄면 자재 본래 색(추정 실제 색 + 중립 조명)으로 보인다.
  - 견적·자재 추천·수량은 조명과 무관하게 **추정 실제 색**을 쓴다. 지금 자재 추천이 사진 색을 쓰는지 확인하고, 바뀌는 점을 보고한다.
- **FLUX와 제품 확인**: 입력 캡처는 화면과 같은 규칙을 따른다. 자재 색 변화 확인은 이번 범위가 아니다.
- **판단 기준**
  - 3-3a 측정을 앱 경로로 다시 해도 같은 결과다.
  - 사진 없는 프로젝트와 기존 프로젝트의 모든 렌더는 기준선과 픽셀 차 0이다.
  - 켜기/끄기·세기가 모든 렌더 경로에 같게 반영된다.
  - 390px에서 넘침이 없다.

## 7. 반드시 지킬 조건

- AI 호출과 비용은 없다. 필요해지면 멈추고 승인받는다.
- 사진 없는 프로젝트, 기존 프로젝트, 편집 화면의 다른 요소는 바뀌지 않는다(기준선 픽셀 차 0).
- 저장된 문서의 이전 형식을 그대로 읽는다.
- 원본 사진은 브라우저 밖으로 새로 보내지 않는다. 추정은 브라우저에서 한다. 관리자 타인 프로젝트 편집·임시 분석의 캐시 규칙(`transient`)을 지킨다.
- 시스템 설정과 Chrome 전역 플래그는 바꾸지 않는다.
- Tailwind를 우선 쓴다. `globals.css`의 `p{margin:0}` 때문에 여백이 필요한 표시 요소는 `<div>`로 만든다.
- 줄바꿈은 작업 사본 CRLF, 저장소 LF다. Prettier는 쓰기에 `--end-of-line crlf --write`, 검사에 `--end-of-line auto`를 쓴다. typecheck 뒤 `next-env.d.ts`를 되돌린다.
