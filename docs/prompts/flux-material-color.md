# AI 현장 사진 변환(FLUX)이 자재 색을 바꾸는 문제 고치기

"AI로 현장 사진처럼" 변환 결과에서 **타일·자재 색이 입력과 달라지는** 문제를 줄여줘. 최근 실측에서 흰 벽 타일이 베이지로 바뀌었다. 목표는 프로젝트 하나의 After 3D를 실사처럼 만드는 흐름에서 자재 색을 지키는 것이다. 조사나 계획 설명에서 멈추지 말고 구현, 측정, 테스트, 문서, 보고까지 끝낸다. **유료 AI 호출은 5절의 승인 절차 뒤에만** 한다.

## 3. 세 가지 방향 (A·B는 호출 없이 먼저 만든다)

### A. 결과 색 검사 (무료, 픽셀 계산)

- 입력 렌더와 FLUX 결과의 **면별 평균 색**(벽·바닥, 설비 제외)을 비교한다. ΔE2000이 기준을 넘으면 결과 아래에 알린다.
  - 예: "벽 타일 색이 원본보다 따뜻하게 바뀌었을 수 있어요."
- 면 마스크는 렌더러에서 얻는다. 3D는 면 ID 패스, 2D는 합성기 면 영역을 쓴다.
- 3단계의 전체 구도 정렬로 어긋난 결과(구도가 바뀐 경우)는 검사하지 않고 그 사실을 적는다.
- 기준값은 기존 결과 10장(2026-09-25 6장, 3단계 4장)으로 정한다. 정상 결과에서 거짓 경고가 없어야 한다.

### B. 면별 색 보정 (무료, 픽셀을 붙이지 않음)

- FLUX 결과의 **명암·질감은 그대로 두고 색(색상·채도, 필요하면 평균 밝기 일부)만** 면별로 입력 렌더의 평균 색에 맞춘다. 예: Lab에서 a\*·b\* 평균 이동, 채도 비율.
- **적용 범위**
  - 경계는 부드럽게 섞는다.
  - 설비·유리·거울과 면 밖은 건드리지 않는다.
  - 정렬이 낮은 결과에는 적용하지 않는다.
- **과보정 금지**: 원래 유채색인 타일(베이지·초록 등)을 무채색으로 만들면 안 된다. 시험 장면에 유채색 타일 방을 하나 넣는다.
- **평가**(기존 10장 + 5절 새 결과)
  - 보정 뒤 면 평균 ΔE
  - 경계 얼룩·후광이 없는지(눈 확인 + 경계 지표)
  - 설비 영역 불변(픽셀 차 0)

### C. 프롬프트 보강 (유료 비교로 판정)

- **색 이름**
  - 매우 밝은 무채색(C\* 작고 L\* 높음)은 "white"로 부르고 hex를 붙인다.
  - "off-white" 같은 크림색을 연상시키는 이름을 피한다.
  - 색 이름 규칙을 다시 정하고 단위 테스트한다.
- **순서와 비중**
  - 벽·바닥 색 문장을 설비 문장보다 **앞**으로 옮긴다. 예: "The walls are white (#ecebe6) tiles and must stay exactly this white; do not warm or yellow them."
  - 길이 줄이기에서 색 문장이 먼저 빠지지 않게 우선순위를 바꾼다.
- **조명 일치**
  - 입력 그림에 사진 조명이 켜져 있으면, 프롬프트 색은 **그림에 보이는 색**(조명을 곱한 색)으로 쓰거나 "as it appears in image 0" 식으로 그림을 기준으로 삼는다.
  - 두 방법 중 하나를 정하고 근거를 적는다.
- 사용자 자유 문장은 여전히 보내지 않는다. 문장은 서버가 만든다.

## 4. 오프라인 개발 순서

1. A·B를 기존 결과 10장으로 만든다. 입력·캡처·마스크가 없는 결과는 장면을 다시 만들어 얻는다.
2. C의 새 프롬프트를 만들고 단위 테스트한다. 결정성, 길이 상한, 색 이름을 본다.
3. 여기까지 AI 호출은 없다.

## 5. 실제 비교 (사용자 승인 뒤에만)

- **먼저 호출 수와 예상 뉴런을 사용자에게 알리고 승인받는다.**
- **계획**(예상, 필요하면 줄인다)
  - 장면 2개: 3단계의 흰 벽 방 안 시점 욕실, 유채색 타일(베이지 또는 초록) 욕실
  - 프롬프트 2개: 지금 / 보강
  - seed 2개
  - **FLUX 8회**, 약 880뉴런
  - 제품 유지 확인이 필요하면 앱과 같은 Gemma 확인 8회를 더한다(약 50뉴런).
  - 합계 약 930뉴런(약 $0.01), 하루 무료 한도 안
- **실행 방법**
  - 운영 `AI` 바인딩을 쓰는 로컬 임시 Worker(127.0.0.1, 호출 상한을 코드에 둠)로 앱 서버와 같은 요청을 보낸다.
  - 도구 권한 검사로 막히면 우회하지 않는다. 사용자에게 실행할 명령을 한 줄씩 주고 결과 파일을 받는다.
  - `wrangler whoami`로 로그인을 먼저 확인한다(로그인은 사용자가 한다).
- **판정표**(결과마다)
  - 면별 평균 ΔE(입력 대비)
  - A 경고 여부
  - B 보정 뒤 ΔE와 얼룩
  - 제품 유지, 새로 생긴 물건
- 결과 이미지는 `test-results/flux-material-color/`에 나란히 저장하고 직접 확인한다.

## 6. 채택과 연결

- **채택 기준**
  - C(프롬프트): 흰 벽 장면에서 면 평균 ΔE 중앙값이 뚜렷이 줄고(예: 30% 이상), 유채색 장면이 나빠지지 않고, 제품 유지가 떨어지지 않는다.
  - B(보정): 보정 뒤 면 평균 ΔE ≤ 3, 눈에 띄는 얼룩·후광이 없고, 유채색이 표백되지 않고, 어긋난 결과는 건너뛴다.
  - A(검사): 정상 결과에서 거짓 경고가 없고, 색이 바뀐 결과를 잡는다.
- **권장 조합**: C를 기본으로 하고, 남은 차이는 B로 보정하고, B를 건너뛴 경우 A로 알린다. 결과가 애매하면 사용자에게 선택지를 보고하고 결정을 받는다.
- **화면**
  - 보정한 결과를 기본으로 보인다. "AI 원본 색 보기" 전환을 둘지 판단해 제안한다.
  - 다운로드 PNG는 보이는 결과다.
  - 제품 확인(Gemma) 동작과 호출 수는 그대로다. 한 클릭에 FLUX 1회 + 확인 1회이고, 색 검사·보정은 호출이 없다.

## 7. 반드시 지킬 조건

- 유료 호출은 승인 뒤에만, 상한 안에서 한다. 실패해도 자동으로 다시 부르지 않는다.
- 토큰·자격 증명을 채팅·소스·브라우저에 넣지 않는다.
- 사용자 자유 문장은 모델로 보내지 않는다. 진단에는 크기·개수만 남긴다.
- 편집 화면, 시안 미리보기, 일반 내보내기 출력은 바꾸지 않는다. 마스크용 새 메서드가 기존 렌더에 영향을 주면 안 된다(기준선 픽셀 차 0).
- Tailwind를 우선 쓴다. `globals.css`의 `p{margin:0}` 때문에 여백이 필요한 표시 요소는 `<div>`로 만든다.
- 줄바꿈은 작업 사본 CRLF, 저장소 LF다. Prettier는 쓰기에 `--end-of-line crlf --write`, 검사에 `--end-of-line auto`를 쓴다. typecheck 뒤 `next-env.d.ts`를 되돌린다.
