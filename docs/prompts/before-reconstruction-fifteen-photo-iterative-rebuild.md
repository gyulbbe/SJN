# 사진 → Before 재구성 재설계: 15장 실제 결과를 보며 반복 개선

SJN의 사진 → Before 공간 재구성을 개선해줘. 제안이나 코드 연결로 끝내지 말고 원인 조사, 필요한 재설계·구현, 실제 사진 실행, 결과 이미지 직접 확인, 로그 분석, 재수정, 저장·출력 검증까지 수행한다. 시간이 오래 걸려도 괜찮다.

저장소는 `C:\dev\SJN`이다. 기존 앱 전체를 다시 만들지 않는다. **사진에서 보이는 설비를 파악하여 수정 가능한 표준 모형으로 배치하는 부분**을 중심으로 다시 설계한다. 기존 편집기·자재·시안·Before/After·저장·렌더러·테스트 도구를 활용한다.

사용자가 원하는 것은 보이지 않는 부분까지 정확히 측량한 디지털 복제본이 아니다. **원본을 보면 알아볼 수 있는 주요 설비가 재구성에도 보이고, 종류·설치 방식·상대 위치·대략적인 크기와 방향이 납득되는 결과**다. 보이지 않는 설비는 만들지 않아도 된다. 보이는 설비를 좌표 계산의 불확실성만으로 전부 숨겨 빈 방으로 만드는 결과는 목표에 맞지 않는다.

## 1. 작업 범위와 우선하는 결정

- 기존 설비 인식·모델 캐시·표준 모형을 가능한 한 재사용하되, 인식 결과를 장면으로 옮기는 설계가 병목이면 해당 부분을 교체한다. 예외 조건만 계속 덧붙이지 않는다.
- **관측한 사실 / 알고리즘으로 추정한 값 / 기본값 / 사용자 입력**을 분리한다. 정확한 촬영 시점·바닥 접점·설치 벽을 모두 확정해야만 설비를 그리는 정책을 그대로 반복하지 않는다.
- 기존 프롬프트의 엄격한 보류 정책과 달리, 이번 작업에서는 관측된 설비와 관계에 근거한 **명시적인 추정 배치**를 허용한다. 추정 위치를 실측·확정 관측으로 표시하지 않는다.
- 불확실한 모든 값을 무조건 통과시키거나, 방 안에 들어가도록 무작정 축소·이동하는 방식도 금지한다. 가능한 관계·규격 범위·지지 방식·물리적 제약을 함께 고려한다.
- 기존 엔진과 데이터를 먼저 삭제하지 않는다. Lab에서 새 경로를 기존 경로와 비교한 뒤, 실제 품질을 확인한 새 경로를 일반 생성·재분석 기능에도 연결한다. 다른 실행 환경으로 조용히 전환하지 않는다.
- 복잡한 레이어 목록·수동 마스크·다각형 영역 UI를 다시 추가하지 않는다. 기본 벽·바닥 삭제 방지는 유지한다.

## 3. 사용할 사진은 15장 모두다

정확한 파일 경로와 해시는 위 manifest를 기준으로 실제 파일을 확인한다.

| 그룹 | ID | 사진 |
|---|---|---|
| PC 4장 | pc-01, pc-02, pc-03, pc-04 | TEST 화장실.jpg, TEST 화장실2.jpg, test 화장실3.jpg, images.jpg |
| 원격 5장 | remote-01 ~ remote-05 | 1-Photo-1.jpg ~ 5-Photo-5.jpg |
| 추가 6장 | additional-04 ~ additional-09 | TEST 화장실4.jpg ~ TEST 화장실9.jpg |

- 원사진을 실제로 열어 본다. 스크린샷이나 이전 출력으로 원본을 대체하지 않는다. 원본이 없으면 제공된 위치·기존 보관 위치를 확인하고 해시로 동일성을 검증한다. 그래도 없으면 해당 파일만 요청하고 나머지 독립 작업은 진행한다.
- 15장은 이미 반복해서 본 개발·회귀 자료다. 이 결과를 처음 보는 사진의 일반화 성능이라고 보고하지 않는다.
- 사진별 설비 정답·좌표·파일명·해시를 AI 프롬프트나 런타임 분기·배치 규칙에 넣지 않는다. 평가용 주석은 분석 입력과 분리한다.
- 원사진과 로그는 로컬에 보관한다. Git에 개인 사진·생성물·모델을 자동 추가하거나 외부 서비스에 전송하지 않는다.

## 4. 수정 전에 기준 결과와 사진별 평가표를 고정한다

### 기준 결과

최초 15장 기준 실행을 현재 코드에서 확보한다. 기존 `final-v3-fifteen`은 역사적 대조 자료다. 이후 소스가 달라졌다면 과거 결과를 현재의 개선 전 결과라고 표기하지 않는다. 동일 조건으로 재현 가능한 저장 관측은 활용하되 재생 여부를 명시한다.

원본 / 작업 시작 기준 / 현재까지 가장 좋은 채택 결과 / 이번 실험 결과를 구분해 보존한다. 특정 사진에서 잘 나온 다른 실행들을 섞어 한 번의 전체 실행처럼 만들지 않는다.

기존 공통 방 2400×2400×2400mm는 실측이 아닌 기본값이다. 기본 비교에서는 동일 입력 치수·공통 표시 카메라·출력 크기를 사용한다. 방 비율 추정도 바꾸려면 별도 실험으로 분리해 기존 조건의 비교를 함께 남긴다. 원사진 해석용 카메라와 Before/After 공통 표시 카메라를 혼동하지 않는다.

### 사진별 평가표

자동 출력에 맞춰 정답을 정하지 말고, 먼저 원사진을 보고 다음을 `evaluation-rubric.json`과 읽기 쉬운 표로 작성한다.

- 확실히 보이는 주요 설비, 실제로 없는 설비, 판단이 애매한 설비.
- 종류와 형태: 변기, 벽걸이·기둥·하부장·상판형 세면대, 욕조, 거울, 거울 수납장, 독립 수납장, 유리 파티션, 선반·수건 랙, 샤워 설비, 창 등. 현재 구현에 없는 주요 종류도 평가표에서 지우지 않는다.
- 설치 방식·부착 벽, 좌우·앞뒤·위아래 관계, 제품의 주된 방향, 방과 제품 사이의 대략적인 크기 비율.
- 유리와 뒤쪽 설비의 정상 가림, 거울 내부 반사와 실제 물체의 구분, 벽·바닥·단차·주요 구획.
- 원본에서 확인 가능한 색과 특징. 조명·그림자를 재료색으로 단정하지 않는다.
- 확실히 평가할 수 없는 치수·깊이·가려진 형태와 그 이유.

평가표는 참고 정답이지 모델 출력이 아니다. 모델 후보 개수를 정답 개수의 분모로 사용하지 않는다. 실제 치수 정답이 없으면 mm 정확도나 임의의 정확도 백분율을 만들지 않는다. 평가 기준을 변경해야 하면 원본 근거와 변경 이력을 남기며 실패한 결과를 통과시키기 위해 기준을 낮추지 않는다.

## 5. 새 배치 흐름이 해결해야 할 것

권장 흐름은 **설비 관측 → 공간과 설비 관계 정리 → 배치 가설 생성·검증 → 표준 모형 장면 생성 → 간단한 수정**이다. 구체적인 구현은 현재 코드 조사에 따라 결정하되 다음을 충족한다.

1. 후보 ID와 원응답을 유지하고 종류·형태·사진 속 영역·설치 단서·관계를 별도 기록한다. 위치 계산 실패가 원후보 삭제로 이어지지 않게 한다.
2. 존재가 관측된 설비의 좌우·앞뒤·부착·지지·가림 관계를 이용해 가능한 위치·방향을 계산한다. 사진의 2D 좌우를 무조건 방의 좌우 벽으로 변환하지 않는다. 여러 후보가 가능하면 모순과 선택 이유를 기록한다.
3. 세면대의 볼 하단, 기둥 접지점, 하부장 중심, 벽 부착점, 모형 원점을 구별한다. 같은 종류도 설치 방식에 맞는 모형과 기준점을 사용한다. 치수·회전축·단위 오류를 먼저 제거한다.
4. 제품이 사진에서 잘렸거나 바닥이 가려졌더라도, 존재·설치 방식·주변 관계가 충분하면 기본 규격 범위를 활용한 추정 배치를 검토한다. 가려진 제품 뒷면을 표준 모형의 기본 형상으로 표현하는 것은 허용하지만 관측했다고 주장하지 않는다. 보이지 않는 별도 설비는 추가하지 않는다.
5. 관측값과 추정값이 충돌하면 각각 보존하고 판단 근거를 남긴다. 한 모델의 라벨 또는 한 픽셀 검사 실패를 모든 설비의 일괄 탈락 조건으로 만들지 않는다. 모델 간 충돌도 무조건 무시하지 않는다.
6. 카메라·바닥 추정 일부가 실패해도 개별 설비의 배치 근거를 평가한다. 정확한 원사진 시점 재현 실패와 표준 공간 배치 실패를 분리한다.
7. 벽 관통·바닥 아래 배치·공중 부양·불가능한 지지·심한 실제 충돌은 검사한다. 투명 유리의 겹침, 거울 반사, 정상 가림, 세면볼과 상판의 결합을 동일한 충돌로 취급하지 않는다.
8. 거울·거울장은 외곽·프레임·문 경계·중립 반사면으로 표현한다. 원본 반사 풍경을 텍스처로 붙이지 않는다. 유리는 독립된 반투명 모형으로 뒤 타일·제품이 보이게 한다.
9. 확실히 판단할 수 없는 후보는 사라지게 하지 말고 이유와 함께 보존한다. 간단한 종류·벽·위치·규격 수정으로 해결할 수 있게 하되, 자동 품질 문제를 사용자의 수작업으로 전부 떠넘기지 않는다.
10. 개별 입력에 예외를 추가하기보다 여러 사례의 공통 원인을 해결한다. 새 데이터·계약·캐시 revision이 필요하면 호환성과 검증을 함께 구현한다.

필드별 출처는 최소한 model-observed / geometry-derived / estimated / default / user와 같이 구분한다. 표현 명칭은 기존 계약과 일치시켜도 되지만, 추정된 설치 좌표를 실제 관측 좌표로 바꾸어 저장하지 않는다. 점수는 측정된 정답 확률처럼 표시하지 않는다.

## 6. 실제 이미지와 로그를 사용하는 반복 절차

아래 순환을 코드 안정성과 시각적 목표를 모두 충족할 때까지 수행한다. 매 반복을 실행했다는 사실만으로 진전이라고 보고하지 않는다.

1. **이미지를 먼저 본다.** 원본과 이번 실제 출력의 전체 비교판을 열고, 문제 있는 개별 이미지를 확대한다. JSON·후보 개수·자동 점수만 보고 시각 검사를 대체하지 않는다. 같은 공통 시점과 필요한 추가 시점에서 누락·설치·가림을 확인한다.
2. **문제와 로그를 연결한다.** 원본의 설비 → 후보 ID → 설치/기하/배치 판단 → 생성 모형 ID → 렌더 결과를 추적한다. 최초 실패와 연쇄 실패를 구분한다. 렌더에는 있으나 다른 모형에 가려진 경우도 별도로 확인한다.
3. **수정 가설을 적는다.** 어떤 공통 원인이며 어떤 사진에서 좋아져야 하는지, 다른 사진의 악화 위험, 확인할 증거를 짧게 기록한다. 가능한 한 한 원인 또는 분리 가능한 변경 묶음으로 실험한다.
4. **구현하고 좁게 검증한다.** 영향받는 대표 사진으로 확인한다. 배치·렌더만 바뀌었다면 유효한 실제 분석 캐시를 재생해 빠르게 비교할 수 있다. 인식 프롬프트·전처리·모델 입력이 달라졌다면 해당 경로는 실제 AI로 다시 실행한다.
5. **15장 전체로 회귀를 본다.** 채택 후보마다 모든 사진을 같은 코드·설정에서 재구성·렌더링한다. 좋아진 사례와 나빠진 사례를 함께 기록한다. 캐시·새 추론·수동 입력 여부를 명시한다.
6. **채택하거나 원인을 다시 조사한다.** 시각적으로 나아지지 않은 변경을 성과로 누적하지 않는다. 실험 결과는 보존하고 이번 작업에서 만든 무효 변경만 안전하게 제외한다. 기존 사용자 변경을 되돌리지 않는다.
7. **다음 반복을 진행한다.** 해결 가능한 주요 결함이 남아 있으면 최종 답변으로 종료하지 말고 계속 수정한다. 로그 개선·빌드 통과·인식 후보 증가만으로 멈추지 않는다.

매 반복 `iteration.json`에 가설, 소스/설정 해시, 입력·관측 실행 ID, 바뀐 파일, 사진별 전후 판정, 채택 여부와 다음 작업을 남긴다. 전체 상태·가장 좋은 채택 실행·미해결 목록·진행 중 작업은 `progress.md`에 갱신해 대화가 압축되거나 재개되어도 이어서 작업할 수 있게 한다. 사용자에게는 달라진 결과와 남은 핵심 문제를 간단히 알린다.

같은 원인에 대한 서로 다른 검증 가능한 시도 3회가 연속으로 개선을 만들지 못하면 같은 방식의 반복 실행을 멈추고 설계·가설을 재검토한다. 이는 전체 작업을 완료하거나 중단할 조건이 아니다. 기존 승인 범위에서 다른 접근을 구현할 수 있으면 계속한다. 새 모델·실행 환경 또는 필수 사용자 정보 없이는 진전할 수 없다는 근거가 확보되면 그 부분만 구체적으로 질문한다. 이유 없는 무한 재시도나 같은 입력·코드의 재추론으로 시간을 소비하지 않는다.

## 7. ‘괜찮은 결과’ 판정과 종료 기준

사용자의 미적 만족을 대신 승인했다고 말하지 않는다. 다음은 개발자가 직접 이미지와 로그로 확인할 작업 완료 기준이다.

### 사진마다 반드시 확인할 핵심 기준

- 확실히 보이는 주요 설비가 알아볼 수 있는 종류와 설치 방식으로 표현된다. 현재 모형이 부족하면 필요한 일반 모형을 보완하며, 미지원이라는 이유로 평가에서 빼지 않는다.
- 세면대가 기둥형으로 잘못 바뀌거나 벽걸이가 바닥에 놓이는 등의 큰 형태·설치 오류가 없다.
- 주요 좌우·앞뒤·상하 관계와 상대 크기가 원본과 납득 가능하게 대응한다. 작은 위치·크기 조정만으로 사용 가능해야 하며, 대부분을 다시 배치해야 하면 실패다.
- 벽 이탈·심한 관통·공중 부양·핵심 설비를 가리는 비정상 겹침이 없다. 유리 뒤 물체는 정상적으로 보인다.
- 반사된 설비가 추가 생성되지 않고, 거울에 원본 풍경이 붙지 않는다. 원본에 없는 주요 설비를 채워 넣지 않는다.
- 설비가 있는 사진에서 빈 결과가 나오지 않는다. 설비가 아직 설치되지 않은 `remote-05`는 주요 설비를 임의로 생성하지 않는다. 벽의 홈·단차 등 구조 표현은 별도 평가한다.
- 정확한 치수·보이지 않는 뒷면·미세한 소품·조명·텍스처의 완전 일치는 필수 조건이 아니다. 사진에서 확실히 확인할 수 없는 항목은 이유를 적고 평가 불가로 둔다.

사진별 결과는 **바로 사용 가능 / 간단한 보정 필요 / 재구성 실패 / 평가 불가**로 분류하고 근거를 남긴다. ‘간단한 보정’은 주요 설비 누락·잘못된 종류·잘못된 설치 벽·구조를 다시 만드는 작업을 포함하지 않는다. 해당 분류를 입증하려면 자동 결과를 먼저 보존하고 별도 사본에서 실제 보정 단계와 조작 수를 기록한다. 그 사본을 자동 결과 비교판에 섞지 않는다.

완료하려면 15장 모두를 검토하고, 평가 가능한 주요 항목에 치명적인 재구성 실패가 없어야 하며, 각 사진이 위 기준에서 바로 사용 가능하거나 간단한 보정 수준이어야 한다. 평가 불가를 실패 은폐용으로 사용하지 않는다. 평균 점수나 배치 개수 증가로 특정 사진의 심각한 실패를 상쇄하지 않는다. 처음부터 잘되던 사진의 주요 품질도 유지한다.

이 기준을 충족하지 못하면 완료라고 쓰지 않는다. 기존 환경에서 진행 가능한 수정은 이어서 한다. 외부 승인·필수 입력·접근 권한 부족 등 실제 장애로 더 진행할 수 없는 경우에는 현재 최고의 결과와 남은 실패, 시도한 대안, 필요한 결정만 정확히 보고한다. 오래 실행했다는 이유로 성공으로 처리하지 않는다.

## 8. 최종 검증은 실제 경로와 실제 AI로 한다

- 최종 소스 상태에서 15장 전체를 다시 실행해 모델 원응답부터 장면·PNG까지 연결한다. 최종 품질 검증에서는 실제 AI 분석을 포함한다. 변경한 분석 단계는 해당 최종 프롬프트·전처리·계약으로 새 추론을 실행한다.
- 변경하지 않은 고비용 단계의 유효 캐시는 재사용할 수 있으나 단계별로 명시한다. 전 단계 캐시 재생을 ‘15장 신규 AI 추론 완료’라고 보고하지 않는다. 평가 자료에 원응답·코드·입력·모델 버전 연결이 없는 출력을 사용하지 않는다.
- 모의 응답은 오류 경계·단위 테스트에만 사용한다. 수동 배치·정답 입력·후보 강제 주입·이미지 생성 도구의 보정 결과를 실제 자동 재구성 성공으로 집계하지 않는다.
- 각 사진에서 결과가 달라지도록 반복 실행한 뒤 가장 좋은 것만 고르지 않는다. 선택한 알고리즘을 고정한 하나의 전체 실행을 최종 결과로 남긴다. 출력 변동이 큰 사례는 반복성도 별도로 확인하고 모두 기록한다.
- 일반 사용자 화면에서 생성·사진 재분석·저장·닫기·새로고침·재진입·Before 수정·undo/redo·비교·PNG 다운로드까지 확인한다. Lab만 다른 알고리즘으로 성공하면 완료가 아니다.
- 사진으로 시작하면 재구성한 Before와 같은 공간·공통 카메라의 빈 After, 사진 없이 시작하면 양쪽 빈 기본 공간을 유지한다. 기존 After와 시안은 재분석으로 덮어쓰지 않는다.
- 미리보기와 다운로드는 같은 장면을 사용한다. 확인 표시·선택 테두리·편집 도구·로그·금액 패널이 출력 이미지에 섞이지 않게 한다. 기존 회전·공통 시점 기능이 있으면 해당 상태의 저장·비교·출력도 회귀한다.
- 기존 시안 최대 5개·복사 독립성·저장 충돌·실패 시 작업 보존·자산 참조·자재 수량/금액을 유지한다. 재구성 모형에 임의의 판매 가격이나 구매 수량을 추가하지 않는다.
- 취소·늦은 응답·손상 캐시·부분 분석 실패·WebGL 실패·저장 용량 오류를 확인한다. 같은 GPU 작업을 중복 시작하지 않고 취소·실패 시 세션과 자원을 정리한다.
- 관련 단위·브라우저 회귀, lint, 타입 검사, Next.js·vinext 빌드를 실행한다. 변경된 동작에 맞춰 테스트를 보완하되 실패를 숨기기 위해 테스트를 삭제·무력화하지 않는다. 빌드 검사 후 최종 소스와 검증 소스가 같은지 확인한다.
- 미사용 사진이 기존 승인된 평가 자료에 있으면 별도 일반화 검사로 활용한다. 없으면 15장 개발 사례 검증과 미사용 사진 미검증을 구분하며, 이를 이유로 15장 작업을 미루지 않는다.

## 9. 로그와 비교 자료는 다음 분석자가 바로 읽을 수 있게 한다

전체 요약부터 후보별 근거로 내려갈 수 있게 만든다. 거대한 JSON 하나만 남기지 않는다.

- `manifest.json`: 15장 ID·원본 경로·SHA-256, 기준 실행·소스·환경·방 치수·카메라·렌더 크기.
- `iterations/<번호>/`: 각 실험의 가설·수정·실행 조건·원시 진단·사진별 판정·채택/폐기 사유.
- `cases/<사진ID>/`: 원본 참조, 기준·최종 PNG, 원후보·보정·배치·렌더 연결 자료, 오류 및 처리 시간.
- `summary.json`과 `summary.md`: 15장별 주요 설비·올바른 배치·누락·오생성·형태·설치·관계·가림·색·확인 필요 항목, 기준 대비 개선/동일/악화와 근거.
- `comparison.png`: 15행 × 3열, 원본 / 작업 시작 기준 / 최종 자동 결과. 사진명과 실행 ID를 식별 가능하게 표시한다. 개별 이미지를 충분한 해상도로 보존하고 확대 가능한 `comparison.html`도 제공한다. 원본은 보존한 채 비교판으로 합성하며 생성형 이미지 보정은 하지 않는다.
- 후보별 진단: 존재/종류 관측, 근거 영역, 설치 단서, 관계, 모형·기준점, 원값/제안/최종값, 필드별 출처, 선택·탈락 사유, 최초 원인과 연쇄 보류, 최종 생성 여부·범위·실제 가림.
- 성능: 모델 다운로드·로드·각 AI 추론·기하·배치·렌더·총시간, 캐시 적중, 장치·OS·브라우저·백엔드·동시 작업 조건. 브라우저 heap, Python RSS, CUDA allocator 등 측정 범위를 분리하며 미측정 RAM/VRAM 최고치를 추정해 채우지 않는다.
- 보안·크기: 비밀키·쿠키·토큰을 로그에 남기지 않고 이미지·바이너리를 JSON에 중복하지 않는다. 로그 저장 실패도 기록하며 이전 결과를 지우지 않는다. 모델·개인 사진·진단 파일이 배포 산출물에 포함되지 않는지 확인한다.

## 10. 승인 범위와 환경

기존 설치된 Node·브라우저·Ollama·Python 및 이미 준비되고 승인된 모델의 로컬 실행, 코드·프롬프트·알고리즘 수정, 실제 15장 테스트와 문서 작성은 계속 진행해도 된다. 같은 범위의 로컬 테스트를 매번 재승인받지 않는다.

**새 모델 가중치 다운로드·교체, 새 런타임/가상환경·시스템 의존성 도입이나 업그레이드, GPU 설정 변경, 별도 상시 서비스·서버·컨테이너, 사용자 PC 다운로드 정책 변경, 유료 자원·외부 사진 전송·실제 배포가 필요하면 먼저 사용자에게 물어본다.** 과거에 제안만 했던 8B 모델 등을 승인받은 것으로 간주하지 않는다. 기존 모델 파일이 디스크에 있다는 사실만으로 그 모델의 사용 승인이 있다고 추론하지 않는다.

질문 전에는 기존 환경에서 할 수 있는 조사·대조 실험·설계안을 완료한다. 어떤 실패 때문에 필요한지, 설치 대상/크기, 실행 위치, 공식 라이선스·상업 이용 조건, 메모리·GPU/CPU 지원, 비용·사진 전송 여부, 품질 비교 방법과 중단·되돌림 기준을 짧게 설명한다. 승인 대기 중에는 독립적으로 가능한 작업을 계속한다.

웹앱과 로컬 AI 작업자의 역할을 분리한다. 현재 Python/CUDA 로컬 분석을 Cloudflare Workers에서도 그대로 실행할 수 있다고 표시하지 않는다. 배포되지 않은 것을 배포·실사용 검증 완료라고 보고하지 않는다. TripoSR 제품 입체화와 배경 제거 모델은 이번 공간 재구성과 무관하게 교체하지 않는다.
