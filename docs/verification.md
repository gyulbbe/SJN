## 2026-10-05 — 직접 등록한 제품에 "표준 모형으로 보기" 켜고 끄기(선택형, B2)

- 만든 것

  - 전체의 3% 미만인 부품(수전·병 뚜껑)은 한 재질로 합쳐져 흰색에 가깝고(조명 보정과 같음), 색이 다른 병이 선 받침은 병 밑에 병 색이 약간 번진다.

## 2026-10-01 — 제품의 방향은 각도 이름이 정한다

- 무엇: 제품이 향하는 방향을 편집기에서 따로 고르지 않는다. 자재 등록·360° 편집에서 고른 **각도 이름**(정면·왼쪽·오른쪽·위·아래·뒤, 목록에서만 고름)이 방향이고, 2D 편집기·3D 방·AI 변환 입력이 모두 따른다. 속성 패널의 "보는 방향"(벽 안쪽 / 앞쪽)과 벽에 따른 회전 곱하기(왼쪽 벽 +90°, 오른쪽 벽 −90°)는 없앴다. 상세는 [방 크기](room-dimensions.md), 360° 제품 편집 문서(삭제됨, [제거 기록](product3d-removal.md)), [자재 이미지](material-images.md), [FLUX 내보내기](flux-export.md)에 있다. 아래 "벽 제품의 보는 방향" 항목은 이 변경으로 대체됐다.
- 바꾼 것
  - 이름: 닫힌 목록 6개(방향마다 한 장, 최대 6장). 쓰기는 엄격(zod, 목록·중복·6장), 읽기는 너그럽게(오른쪽 측면→오른쪽, 뒤에서→뒤, 사선→가까운 옆, 읽을 수 없으면 정면으로 읽고 다시 고르게 안내). `사선`·`원본 사진 방향`은 없앴다.

## 2026-09-30 — 저장한 3D 제품이 3D 방에서 기울어 놓이던 문제 수정

- 증상: 360° 편집기에서는 정상인 변기·세면대가 공간 둘러보기·AI 내보내기의 3D 방에서는 앞으로 기울고 바닥 아래로 빠져 보였다.
- 원인: `createSavedProductGeometry`가 제품을 "저장한 카메라의 좌표"에 놓았다(`cameraQuaternion⁻¹ × objectQuaternion`). 360° 편집기의 기본 카메라는 제품을 10° 내려다보므로, 그 각도가 제품 자세에 그대로 들어가 똑바른 제품이 10° 앞으로 기울었다. 또 기울어진 상자의 세로 길이(높이 × cos + 깊이 × sin)로 규격에 맞춰서 제품이 실제보다 작게 놓였다.
  - 완전히 똑바른 상자(TripoSR 좌표)를 기본 자세로 놓으면 뒤쪽 아랫면이 바닥에서 65mm 떠 있고 앞쪽 아랫면만 바닥에 닿았다(깊이 368mm에서 10.0°).
  - 실제 변기·욕조 모형을 자동 수평 맞춤 자세로 놓으면 바닥의 앞뒤 기울기가 −6.8°(변기)·−5.9°(욕조)였다.
- 수정: `levelCameraQuaternion`(src/lib/product3d/pose.ts)으로 카메라가 위아래로 본 각도만 뺀다. 카메라가 선 쪽(좌우 돌림)과 카메라 기울기(roll)는 그대로 둔다. 바로 위·아래에서 본 카메라는 화면 위쪽 방향으로 쪽을 정한다.
  - 같은 실제 모형: 변기 −0.3°, 욕조 +0.2°, 스툴 −0.6°로 바닥이 수평이 된다.
  - 어느 높이(−30°~85°)에서 본 카메라로 저장해도 같은 자리에 같은 모양으로 놓인다.
- 검증: 단위 테스트(`tests/product3d-pose.test.ts`의 수평 카메라 5개, `tests/room-viewer-fixtures.test.ts`의 "똑바로 세운다" 3개)와 전체 244개 파일·3,413개 통과. 실제 변기 모형을 3D 방 바닥에 놓아 렌더 비교(수정 전 앞으로 기울고 그림자가 떨어져 보임, 수정 후 바닥에 평평).
- 알아 둘 점
  - 기존 테스트의 도우미가 항등 회전을 카메라로 썼다(실제 앱이 만들지 않는 자세). TripoSR 좌표의 상자와 수평 카메라로 바꿨다.
  - 자동 수평 맞춤 이전에 저장한 자세는 모형 자체의 기울기(약 5~9°)가 3D 방에서 그대로 보인다. 360° 편집기에서 **자동 수평 맞춤** 뒤 다시 저장하면 바닥에 평평해진다.
  - "바닥 아래로 빠져 보임" 중 배치 기준점이 제품 아랫면보다 위에 있어서 생기는 경우는 확인하지 못했다(사용자 프로젝트 없음).

## 2026-09-30 — 벽 제품의 보는 방향(벽 안쪽 / 앞쪽)

> 2026-10-01에 각도 이름 방식으로 대체됐다(위 항목). "보는 방향" 선택과 `facing`은 더 쓰지 않는다. 아래는 당시의 기록이다.

- 무엇: 왼쪽·오른쪽 벽의 사진·입체 제품에 "보는 방향"을 넣었다. 벽 안쪽(기본, 이전과 같음) 또는 앞쪽(정면, 방 기준 고정). 앞쪽이면 3D 방에서 회전 0으로 열린 앞면을 향하고 옆면이 벽에 붙도록 가로 위치만 맞춘다. 저장은 `roomPlacement.facing: 'front'`일 때만. 표준 모형·바닥·정면 벽은 영향 없음. 상세는 [방 크기](room-dimensions.md)에 있다.
- 잔여 기울기 조사: 기본 자세의 3D 제품은 좌우 돌림 0°(앞 방향 벡터가 정확히 +z)이다. 앞으로 10° 기울어 있는 것은 "촬영 고도"라서 정상이라고 결론냈으나 **틀렸다.** 그 기울기는 바닥 접지를 깨는 결함이었고 아래 "저장한 3D 제품이 3D 방에서 기울어 놓이던 문제 수정"에서 고쳤다.
- 검증
  - 전체 vitest 244개 파일·3,405개 통과. 스키마(없음·wall·front 허용, 잘못된 값 거부, 옛 모양 그대로), 복제·시안 복사·실행 취소·저장·불러오기·스키마 왕복, 3D 방(값 없음·wall은 행렬까지 같음, 왼쪽·오른쪽 + front는 회전 0·벽 접촉·세로·벽 따라간 위치 유지, 바닥·정면 벽 불변, 사진 평면·입체 둘 다, 방 밖 안내), 기본 자세 yaw 0.

`npm run test:webgl`은 시스템 Chrome의 실제 앱 렌더러와 shader를 실행합니다. 원본·불투명 타일·보호·분할 비교·제품 투명도·이동 잔상·가림의 실제 픽셀, 네 점 텍스처 정면 보정, 비교 출력의 전체 크기 제한을 확인했습니다. 미리보기에서 원본을 미리 읽지 않는 점, 4096×3072 출력과 4096px 마스크/2048px 텍스처 atlas, 내보내기 성공·실패 후 이전 화면/품질 복원도 통과했습니다.

`npm run test:images`는 시스템 Chrome에서 7개 검증을 통과했습니다. EXIF 6 이미지의 방향 정리와 원본 바이트 보존, 직접 올린 타일의 네 점 보정, 자재 버전 2 추가, 수동 제품 배경 지우기와 undo, 원본 알파 보존, 새로고침, 두 번째 탭의 등록 금지를 확인했습니다.

`npm run test:ui`는 실제 편집 화면에서 수동 복제 도장 영역 지정·Alt 원점 선택·미리보기·취소·재적용을 검증했습니다. 취소 시 장면이 동일하며, 적용 시 별도 배경 자산이 생기고 원본 ID 및 마스크 밖 픽셀이 유지됩니다. 모바일 390×844에서 자재·속성 드로어와 슬라이더, 닫기 동작을 확인했습니다. JS pageerror는 0개입니다.

모바일 헤더는 최종 수정 후 390px와 320px에서 다시 검증했습니다. 프로젝트 정보와 작업 버튼을 두 줄로 표시하며, 헤더와 문서의 너비가 화면 너비와 같고 모든 버튼이 안쪽에 위치합니다. 도움말과 양쪽 패널 열기/닫기도 통과했습니다. 이후 전체 UI 재검증에서도 390px 헤더 너비와 드로어 동작을 확인했습니다.

`npm run test:failure`는 임시 Chrome 컨텍스트에 실패를 주입합니다. WebGL2 컨텍스트 생성을 실패시키면 오류 안내가 나타나고 무한 로딩 없이 프로젝트/원본이 유지되며, 실패를 해제한 뒤 재진입하면 렌더링됩니다. 프로젝트 저장에 한 번 `QuotaExceededError`를 주입해 이전 IndexedDB 문서와 현재 입력이 유지되는 것을 확인했습니다. 명시적 저장 재시도 후 오류 알림이 사라지고 새로고침으로 마지막 편집을 복원했습니다. 실제 디스크 공간은 변경하지 않았습니다. 처리되지 않은 페이지 오류는 없었습니다. WebGL 실패 컨텍스트에서 출처를 식별하지 못한 콘솔 404 메시지 한 건이 기록됐으며, 캡처된 HTTP 실패는 없었습니다. 보고서와 화면은 `test-results/failure-qa/`에 생성됩니다.

Codex의 실제 브라우저 화면에서도 가상 욕실 BEFORE 사진을 일반 업로드 흐름으로 열고 바닥 네 점, 타일, 변기·세면대 보호 영역, 비교 슬라이더를 직접 조작했습니다. 같은 위치의 원본과 변경된 바닥, 보호된 물체, 비교 시 숨겨지는 편집 핸들을 시각적으로 확인하고 저장했습니다. 미리 만든 After 이미지는 사용하지 않았습니다.

## 추가 구현: 자재 클릭으로 벽·바닥 자동 적용

최종 검사: **프로덕션 빌드·타입 검사·린트 통과, 단위 테스트 58개 통과, 전체 E2E 9개 통과(1.2분)**. 마지막 E2E는 병렬 검증 간 산출물 충돌을 피하기 위해 `npx playwright test --output=test-results/final-e2e`로 단독 실행했습니다. 앞선 동시 실행의 trace 파일 경로 충돌은 앱 기능 실패와 구분해 처리했습니다.

후속 사용자 요청에 따라 **벽 타일 → 차콜 스톤** 두 번의 클릭만으로 실제 사진의 벽을 찾아 적용하도록 변경했습니다. 사진에 지정된 면이 없다면 Google DeepLabV3 MobileNetV2 ADE20K 모델을 실행합니다. 이미 면이 있으면 바로 자재만 바꾸며, 처음 분석할 때 다른 종류의 면도 함께 준비해 후속 바닥 적용에 분석을 반복하지 않습니다. 기존 수동 면과 보호 영역은 유지합니다.

- 분할 결과는 실제 모델의 픽셀에서 정확한 윤곽선과 내부 구멍으로 변환합니다. 임의 사각형이나 예시 사진 전용 마스크를 적용하지 않습니다.
- 전체/개별 적용 대상을 선택할 수 있습니다. 생성과 자재 적용을 한 편집 명령으로 저장하므로 undo/redo가 가능합니다.
- 모델 파일과 WASM 실행 파일 약 3.66MB가 앱에 포함됩니다. 사진은 Web Worker에 전달하며 원격 서버로 업로드하지 않습니다. 모델 요청도 같은 로컬 출처의 정적 파일 GET만 허용합니다.
- `npm run test:segmentation`에서 실제 모델 실행을 검증했습니다. Chrome 152, 단일 스레드 WASM CPU, 1536×1024 입력 → 512×341 분할. 최초 3.90초, 모델 재사용 3.34초였습니다. 편집기는 결과를 별도로 캐시하므로 단순 재질 변경 시 추론을 다시 하지 않습니다.
- 가로/세로 사진 비율, 벽 세 지점·바닥, 변기·세면대·거울·창 중심의 제외를 확인했습니다. 메인 스레드가 응답했고 외부 요청과 처리되지 않은 오류는 0건이었습니다. [실제 추론 보고서](local-segmentation-verification.json).
- `e2e/auto-apply.spec.ts`의 실제 자동 적용·바닥 캐시·undo/redo, 모델 로드 실패 후 재시도, Escape 취소 뒤 늦은 결과 무시와 캐시 재사용 3개 흐름이 통과했습니다. 저장된 문서 크기는 예시 검증에서 history 포함 약 113KB였습니다.
- 벽 적용 시 확인 지점 RGB는 (209,207,206) → (85,92,90)으로 변경됐고, 바닥·변기·거울 확인 지점은 같았습니다. 후속 바닥 적용은 바닥만 (148,146,152) → (180,165,142)로 바뀌었습니다. 이 측정은 확인 지점에 대한 검증이며 모든 사진/픽셀의 정확도 보장은 아닙니다.

실제 브라우저에서도 기존 예시 프로젝트를 열어 **벽 타일 → 차콜 스톤**만 눌러 결과를 확인했습니다. 문/문틀과 작은 수전의 일부는 벽으로 오분류될 수 있습니다. 맞닿은 여러 벽은 RGB 코너 근거 없이 임의로 분할하지 않으며, 원근/실제 치수는 추정입니다. 경계 브러시·지우개, 별도 수동 면, 원근점으로 수정할 수 있습니다. 고화질 생성형 AI 보정과 자동 제품 배경 제거는 이번 추가 범위에도 포함하지 않았습니다.

모델 API 및 출력 형식은 [TensorFlow 공식 DeepLab 문서](https://github.com/tensorflow/tfjs-models/tree/master/deeplab)를 확인했습니다. 고정된 모델/라이선스/해시와 런타임 고지는 `public/models/`에 포함합니다.

## 추가 수정: 바닥 가장자리·원근·명암
