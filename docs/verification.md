# 로컬 구현 검증 기록

검증일: 2026-09-06. 작업 환경: Windows, Node.js 22.13.1, npm 10.9.2. 외부 서버 연결·배포 없이 `127.0.0.1:3000`의 로컬 모드를 검증했습니다. 사용자가 입력한 실제 Supabase 자격 증명은 없습니다.

## 2026-09-07 — 수동 영역 도구 제거와 기본 면 보호

- 사용자 요청에 따라 캔버스의 면 만들기·다각형·경계/원근점·브러시·지우개·보호/가림 그리기를 제거했습니다. 수동 벽/바닥 경계 재지정, 사진 면 4점 보정, 수동 배경 복원/도기 추출 창도 진입점과 실행 컴포넌트에서 제거했습니다. 자재 등록의 타일 한 장 자르기와 제품 이미지 배경 지우기는 자재 준비 기능으로 유지합니다.
- 오른쪽 레이어 목록과 공통 선택 항목 삭제를 제거했습니다. 화면이나 적용 위치에서 기본 벽/바닥을 선택해 타일 속성을 바꾸고, 제품은 화면에서 선택해 이동·복제·잠금·제품 삭제를 수행합니다. 제품 앞뒤 순서·접지 그림자·색감·방 크기·견적·비교·출력은 유지합니다.
- Tool은 select/pan 두 가지로 제한했습니다. 같은 방 치수·원본·화면에서 기존 roomFace와 벽 구간 ID가 일반 편집에서 빠지면 보존합니다. 자재 해제는 허용하며 방 크기 변경·사진 재분석의 새 배경은 정당한 면 교체로 처리합니다. 기존 문서·원본·사용자 자재·undo/redo 기록을 읽을 때 초기화하지 않습니다.
- 제품 전용 삭제 명령은 없는 ID/기본 면/잠금/미확정 드래그/Before 비교 열람 중에는 변경하지 않습니다. 실제 삭제는 현재 편집 장면에만 한 번의 undo 명령으로 적용합니다. Before 비교 화면에서 속성 편집도 비활성화합니다.
- 단위 **30개 파일/235개 테스트 통과**, 기본 면과 벽 구간 보호·제품 삭제 관련 신규 16개 포함. 프로덕션 빌드/TypeScript 단계 및 전체 ESLint 통과했습니다.
- 집중 Playwright 2개(simple-editor/fixture-tiling)는 **2/2 통과, 57.2초**. 기본 네 면 각각에서 자재 적용/해제·Delete/Backspace 뒤 ID/geometry 보존, 제품 삭제·undo/redo·재진입 뒤 Before 전체 PNG 일치를 확인했습니다. 제품 이동 전 자리 151,790픽셀 변화량 0, 모든 새 제품 삭제 뒤 전체 타일 PNG 일치, 선택 유무의 출력 RGBA 일치도 확인했습니다. 결과는 test-results/simple-editor-focused와 test-results/fixture-tiling-qa/fixture-tiling-report.json입니다.
- 최종 활성 Playwright **전체 29개 통과, 5.2분**. 자동 타일 적용·모델 실패/취소·기본 공간·제품 방향/이미지 읽기 실패/지연 취소·견적·사진 재구성·공간 치수·저장/읽기 전용·내보내기와 신규 간소화 편집을 함께 실행했습니다. 최종 전체 ESLint·TypeScript·프로덕션 빌드도 통과했습니다. 실행: npx playwright test --output=test-results/simple-editor-all. 데스크톱 결과 화면과 320/390/391px 모바일 흐름을 확인했습니다.
- 삭제한 기능만 검사하던 E2E 원문과 이전 UI 진단 스크립트는 docs/retired-tests에 .txt로 보관하며 현재 통과 항목에 포함하지 않습니다. 계속 제공하는 견적·공간 치수·제품 방향·재구성 검사는 이전에 저장된 수동 면의 테스트 fixture로 호환성 검증을 유지합니다. test:ui는 현재의 간소화 편집기와 규격 제품 브라우저 검사로 갱신했습니다.

## 2026-09-06 — Before 보관, After에서 바로 작업

- 사진 비교 프로젝트는 사진의 재구성 결과를 Before에 보관하고, 생성·재진입 때 빈/저장된 After 편집 화면을 엽니다. Before 보정이나 확인은 After 작업의 필수 단계가 아닙니다. 사용자가 Before를 편집하던 중에도 상단 After 또는 After 꾸미기로 돌아가기 버튼으로 전환할 수 있습니다.
- 사진 없는 새 프로젝트는 Before·After 모두 빈 방으로 시작합니다. 기존 기본 공간의 원본 배경이 Before이며, After 자재를 추가해도 그 배경은 바뀌지 않습니다. 기존 프로젝트의 디자인을 초기화하거나 자동 변환하지 않습니다.
- 홈에는 사진으로 비교 공간 만들기와 기본 공간으로 시작을 두고, 사진 드롭도 참고 사진이 선택된 비교 생성창으로 연결했습니다. 기존 사진 합성 진입은 펼침 항목 사진 위에 직접 편집에 유지했습니다. 프로젝트 썸네일은 초안 상태와 관계없이 After를 기준으로 만듭니다.
- 단위 **29개 파일/219개 테스트**, 전체 ESLint와 Next.js 프로덕션 빌드/TypeScript 단계 통과. 추가 상태 회귀는 draft/confirmed 모두 After 진입, 저장 내용 보존, 확인 상태 undo/redo가 편집면을 임의로 바꾸지 않는 것을 검증했습니다.
- 관련 Playwright **7개 시나리오 확인 완료**. 첫 전체 실행 6개 통과, 드롭 1개는 실행 시작 이후 바뀐 테스트의 펼침 메뉴 처리를 반영하기 전이라 실패했습니다. 수정된 테스트로 해당 시나리오를 재실행해 통과했습니다. 앱 코드 추가 변경이나 허용 오차 완화는 없었습니다. 산출물: test-results/reconstruction-after-entry, test-results/reconstruction-after-entry-drop.
- 실제 사진 생성 후 빈 After 작업, Before 수정/After 복귀의 revision 불변, 비교 출력·저장·재진입·취소·재분석, 391px 모바일, 사진 드롭과 기본 빈 방을 검증했습니다. 사진 없는 방은 After 타일 적용 전후·새로고침 뒤에도 Before의 검사 위치 RGB가 초기 빈 방과 같았습니다.
- 홈 1440px/390px 캡처를 직접 검토했고 가로 넘침은 없었습니다. 산출물: test-results/after-first-home. 개발 모드에서 기존 favicon.ico 404와 첫 화면 이미지 LCP 안내가 관찰됐으며, 기능 오류로 분류하지 않았습니다.

## 2026-09-06 — 사진 재구성 품질 우선 개선

사용자가 제공한 447×447 민트색 욕실 사진에서 세면대 하부장을 욕조로, 휴지통을 두 번째 변기로 배치하고 창·거울과 타일을 놓친 결과를 재현했습니다. 처리 시간보다 원본 특징과 배치 보존을 우선하도록 분석·모형·원근·표면 구간을 수정했습니다. 이 아래의 이전 187개/36개 기록과 5.83초 수치는 개선 전 구현의 기록입니다.

- 최종 Vitest **29개 파일, 216개 테스트 통과**. 추가 회귀는 복합 세면대 분류·모호한 후보 보류·반전 좌표 복구, 관측 창/거울 정면 보정, 밝고 어두운 줄눈·반 높이 타일 구간, 부피 투영과 방 내부 배치, 벽 구간의 크기 변경·면적·입력 검증을 확인합니다.
- Next.js 16.3.4 **프로덕션 빌드와 TypeScript 단계, 전체 ESLint 통과**. 새로운 의존성이나 원격 분석 서비스는 추가하지 않았습니다.
- 전체 Playwright 최초 실행에서 **37개 중 36개 통과**했습니다. 새 재구성 5개 시나리오는 모두 통과했으며, 사진 재분석이 현재 Before만 바꾸고 After·견적을 유지하는지, undo/redo·재진입까지 확인했습니다. 실패한 기존 벽 보호 검사는 원인과 집중 재검증을 아래에 기록합니다. 전체 최초 산출물은 test-results/reconstruction-quality-regression에 있습니다.
- 기존 벽 보호 실패는 앱/분할 코드 변경 없이 집중 실행에서 먼저 통과했습니다. 실패 기록은 문뿐 아니라 바닥·기존 제품까지 모두 크게 달랐으나 첨부 결과 이미지는 정상이었고, 최초 원본 캡처가 첫 GPU 렌더보다 앞서는 검사 동기화 문제로 확인했습니다. e2e/wall-refit.spec.ts가 원본 PNG에서 읽은 문·거울·창의 3×3 기대 RGB와 배치 제품의 #e8275d를 확인한 뒤 기준 캡처를 잡도록 수정했습니다. 기존 허용차 ≤3은 유지합니다. 수정 후 해당 시나리오 **1개 통과(총 23.0초)**, 보호 확인점 14곳의 RGB 변화가 모두 0이고 세 벽은 38/36/52로 변경됐습니다. 재검증 산출물은 test-results/wall-regression-synchronized, 읽기 쉬운 보고서는 test-results/wall-refit-qa/automatic-wall-coverage.json입니다. 전체 37개 중 최초 통과 36개와 이 집중 재검증으로 37개 시나리오를 확인했으며, 수정 후 전체를 다시 실행한 것으로 표시하지 않습니다.
- 사용자 사진을 실제 로컬 모델로 재생성하고 PNG를 직접 확인했습니다. 변기·세면대 하부장·창·거울이 각각 한 개이며 욕조는 없고, 세 벽의 민트색 상부/작은 하부 타일, 베이지색 바닥/밝은 줄눈을 보존했습니다. 창과 거울은 해당 원본 자산에서 만든 정면 보정 이미지를 참조하고, After는 적용 자재·제품이 없는 같은 방입니다. 이 확인은 해당 사진의 주요 특징에 대한 검사이며 모든 사진의 인식 정확도 보장은 아닙니다.
- 원본 전체·반전·확대 후보 5곳을 실제로 분석했습니다. 생성부터 자산 준비까지 **약 54.1초**였으며, 같은 Windows 호스트에서 단위/E2E 검사를 함께 실행하던 Chrome/SwiftShader 측정입니다. 독립 성능 벤치마크나 FPS로 해석하지 않습니다. 오류 및 외부 요청 0건을 확인했고, 디버그 마스크를 얻기 위한 두 번째 분석은 생성 시간에 포함하지 않았습니다.
- 실제 결과는 test-results/reconstruction-quality-final의 before.png, after.png, masks.png, result.json입니다. 개인 사진을 public 예시로 복사하거나 서버로 전송하지 않았습니다. 재현 스크립트는 RECONSTRUCTION_PHOTO에 로컬 경로를 지정한 뒤 npm run test:reconstruction:quality로 실행합니다. RECONSTRUCTION_OUTPUT으로 출력 디렉터리를 지정할 수 있고, RECONSTRUCTION_EXPECT=mint-bathroom은 이 사진의 주요 특징만 별도로 검사합니다.
- 기존 욕실 회귀 이미지에서도 품질 분석·저장·빈 After·캐시·외부 요청 없음 검증을 통과했습니다. 기존 사진 타일 편집은 단일 분석 경로를 유지합니다. 조작 FPS 및 이전 GPU 비교 23개는 이번 품질 변경에서 새로 측정하지 않았습니다.

품질 한계: 원본 447×447 사진의 없는 디테일은 복원하지 않습니다. 창·거울은 촬영 당시 모습을 유지하며, 도기는 실제 제품 형상 대신 편집 가능한 기본 모형입니다. 러그·조명·액자·샤워 커튼 등의 장식과 가려진 면을 모두 복원하지 않으며, 타일 규격·방 안 상대 위치는 추정입니다. 이동에 따라 반사·그림자·숨은 면을 물리적으로 다시 계산하는 기능은 아닙니다. 결과를 실사 복원이나 실측으로 표시하지 않습니다. Supabase 실제 연결·마이그레이션 적용·사용자 격리·배포는 미실행입니다.

## 2026-09-06 사진 재구성 Before / After 추가

- 홈의 **사진으로 비교 공간 만들기**에서 사진과 방 치수를 입력하고, 브라우저 분석으로 기존 공간의 Before 초안을 만듭니다. After는 같은 방 치수·카메라·화면 비율의 빈 방으로 시작합니다. 기존 사진 편집과 기본 공간 프로젝트는 유지합니다. 사용 흐름과 추정 기준은 [재구성 안내](reconstructed-comparison.md)에 있습니다.
- Vitest 최종 **24개 파일, 187개 테스트 통과**. Before/After 편집 분리, 견적의 After 전용 집계, 공유 치수 변경과 단일 undo, 전환의 revision 불변, v1 읽기/v2 조건부 저장, 원근 배치와 잘못된 입력, 자재 버전과 양쪽 이력 참조를 검증했습니다. 프로젝트 복제 후 공유 자산 보존, 24시간 미참조 내부 캐시 정리 및 일반/수정 자재 보존도 포함합니다.
- 새 Playwright 4개 시나리오는 실제 욕실 사진의 로컬 모델 분석, 사진 면 네 점·깊이 구간·도기 규격 수정, 후보 제외/undo, Before 확정 후 빈 After와 빈 견적, 공유 치수/undo, 재진입/복제, 4096px 비교 출력, 391px 모바일 생성/확정, 잘못된 파일/치수와 취소를 검증했습니다. 실제 모델 응답을 지연한 뒤 취소하고 다른 프로젝트를 생성해도 늦은 결과가 저장되지 않는지 확인했습니다.

`npm run test:images`는 시스템 Chrome에서 7개 검증을 통과했습니다. EXIF 6 이미지의 방향 정리와 원본 바이트 보존, 직접 올린 타일의 네 점 보정, 자재 버전 2 추가, 수동 제품 배경 지우기와 undo, 원본 알파 보존, 새로고침, 두 번째 탭의 등록 금지를 확인했습니다.

`npm run test:ui`는 실제 편집 화면에서 수동 복제 도장 영역 지정·Alt 원점 선택·미리보기·취소·재적용을 검증했습니다. 취소 시 장면이 동일하며, 적용 시 별도 배경 자산이 생기고 원본 ID 및 마스크 밖 픽셀이 유지됩니다. 모바일 390×844에서 자재·속성 드로어와 슬라이더, 닫기 동작을 확인했습니다. JS pageerror는 0개입니다.

모바일 헤더는 최종 수정 후 390px와 320px에서 다시 검증했습니다. 프로젝트 정보와 작업 버튼을 두 줄로 표시하며, 헤더와 문서의 너비가 화면 너비와 같고 모든 버튼이 안쪽에 위치합니다. 도움말과 양쪽 패널 열기/닫기도 통과했습니다. 이후 전체 UI 재검증에서도 390px 헤더 너비와 드로어 동작을 확인했습니다.

`npm run test:failure`는 임시 Chrome 컨텍스트에 실패를 주입합니다. WebGL2 컨텍스트 생성을 실패시키면 오류 안내가 나타나고 무한 로딩 없이 프로젝트/원본이 유지되며, 실패를 해제한 뒤 재진입하면 렌더링됩니다. 프로젝트 저장에 한 번 `QuotaExceededError`를 주입해 이전 IndexedDB 문서와 현재 입력이 유지되는 것을 확인했습니다. 명시적 저장 재시도 후 오류 알림이 사라지고 새로고침으로 마지막 편집을 복원했습니다. 실제 디스크 공간은 변경하지 않았습니다. 처리되지 않은 페이지 오류는 없었습니다. WebGL 실패 컨텍스트에서 출처를 식별하지 못한 콘솔 404 메시지 한 건이 기록됐으며, 캡처된 HTTP 실패는 없었습니다. 보고서와 화면은 `test-results/failure-qa/`에 생성됩니다.

Codex의 실제 브라우저 화면에서도 가상 욕실 BEFORE 사진을 일반 업로드 흐름으로 열고 바닥 네 점, 타일, 변기·세면대 보호 영역, 비교 슬라이더를 직접 조작했습니다. 같은 위치의 원본과 변경된 바닥, 보호된 물체, 비교 시 숨겨지는 편집 핸들을 시각적으로 확인하고 저장했습니다. 미리 만든 After 이미지는 사용하지 않았습니다.

## 추가 구현: 자재 클릭으로 벽·바닥 자동 적용

최종 검사: **프로덕션 빌드·타입 검사·린트 통과, 단위 테스트 58개 통과, 전체 E2E 9개 통과(1.2분)**. 마지막 E2E는 병렬 검증 간 산출물 충돌을 피하기 위해 `npx playwright test --output=test-results/final-e2e`로 단독 실행했습니다. 앞선 동시 실행의 trace 파일 경로 충돌은 앱 기능 실패와 구분해 처리했습니다.

후속 사용자 요청에 따라 **벽 타일 → 차콜 스톤** 두 번의 클릭만으로 실제 사진의 벽을 찾아 적용하도록 변경했습니다. 사진에 지정된 면이 없다면 Google DeepLabV3 MobileNetV2 ADE20K 모델을 실행합니다. 이미 면이 있으면 바로 자재만 바꾸며, 처음 분석할 때 다른 종류의 면도 함께 준비해 후속 바닥 적용에 분석을 반복하지 않습니다. 기존 수동 면과 보호 영역은 유지합니다.

- 분할 결과는 실제 모델의 픽셀에서 정확한 윤곽선과 내부 구멍으로 변환합니다. 임의 사각형이나 예시 사진 전용 마스크를 적용하지 않습니다.
- 전체/개별 적용 대상을 선택할 수 있습니다. 생성과 자재 적용을 한 편집 명령으로 저장하므로 undo/redo가 가능합니다.
- 모델 파일과 WASM 실행 파일 약 3.66MB가 앱에 포함됩니다. 사진은 Web Worker에 전달하며 원격 서버로 업로드하지 않습니다. 모델 요청도 같은 로컬 출처의 정적 파일 GET만 허용합니다.
- `npm run test:segmentation`에서 실제 모델 실행을 검증했습니다. Chrome 152, 단일 스레드 WASM CPU, 1536×1024 입력 → 512×341 분할. 최초 3.90초, 모델 재사용 3.34초였습니다. 편집기는 결과를 별도로 캐시하므로 단순 재질 변경 시 추론을 다시 하지 않습니다.
- 가로/세로 사진 비율, 벽 세 지점·바닥, 변기·세면대·거울·창 중심의 제외를 확인했습니다. 메인 스레드가 응답했고 외부 요청과 처리되지 않은 오류는 0건이었습니다. [실제 추론 보고서](local-segmentation-verification.json).
- `e2e/auto-apply.spec.ts`의 실제 자동 적용·바닥 캐시·undo/redo, 모델 로드 실패 후 재시도, Escape 취소 뒤 늦은 결과 무시와 캐시 재사용 3개 흐름이 통과했습니다. 저장된 문서 크기는 예시 검증에서 history 포함 약 113KB였습니다.
- 벽 적용 시 확인 지점 RGB는 (209,207,206) → (85,92,90)으로 변경됐고, 바닥·변기·거울 확인 지점은 같았습니다. 후속 바닥 적용은 바닥만 (148,146,152) → (180,165,142)로 바뀌었습니다. 이 측정은 확인 지점에 대한 검증이며 모든 사진/픽셀의 정확도 보장은 아닙니다.

실제 브라우저에서도 기존 예시 프로젝트를 열어 **벽 타일 → 차콜 스톤**만 눌러 결과를 확인했습니다. 문/문틀과 작은 수전의 일부는 벽으로 오분류될 수 있습니다. 맞닿은 여러 벽은 RGB 코너 근거 없이 임의로 분할하지 않으며, 원근/실제 치수는 추정입니다. 경계 브러시·지우개, 별도 수동 면, 원근점으로 수정할 수 있습니다. 고화질 생성형 AI 보정과 자동 제품 배경 제거는 이번 추가 범위에도 포함하지 않았습니다.

모델 API 및 출력 형식은 [TensorFlow 공식 DeepLab 문서](https://github.com/tensorflow/tfjs-models/tree/master/deeplab)를 확인했습니다. 고정된 모델/라이선스/해시와 런타임 고지는 `public/models/`에 포함합니다.

## 추가 수정: 바닥 가장자리·원근·명암

2026-09-06 사용자 비교 이미지에서 기존 수동 바닥 영역이 왼쪽 벽에 닿지 않는 문제를 확인했습니다. 기존 면이 있으면 자재만 바꾸는 동작이 과거의 좁은 경계를 계속 사용했습니다. 큰 보호 다각형은 제품 주변에 기존 바닥을 남겼고, 항상 표시되던 보호 오버레이는 제품을 노랗게 보이게 했습니다.
