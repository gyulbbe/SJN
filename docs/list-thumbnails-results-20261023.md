# 자재 카드 목록 이미지(긴 변 256px) 결과 (2026-10-23)

자재 목록 페이징([결과](material-paging-results-20261022.md)) 9절의 후속 작업이다. 공개 목록 첫 쪽(48개)의 카드 이미지는 합계 6.0MB였다. 이미지 하나는 평균 126KB, 평균 594×975px다. 카드는 많아야 약 200px 너비로 보인다. 그래서 카드마다 긴 변 256px의 작은 사본(목록 이미지)을 두고, 카드는 그것을 받는다.

## 1. 사용자 결정

- 범위: 등록할 때 만들기 + 기존 자재 일괄 생성 둘 다(2026-10-22)
- 기존 자재 일괄 생성: **관리자 화면 버튼**. 배포 뒤 관리자가 누를 때만 원격 R2·D1에 쓴다(2026-10-23)
- 형식: **WebP**(품질 0.82). WebP를 못 쓰는 브라우저는 PNG를 주고, 서버는 둘 다 받는다(2026-10-23)

## 2. 설계

**저장:** 목록 이미지는 기존 자산 하나다. migration은 없다.

| 항목 | 값 |
| --- | --- |
| 표 | `d1_assets` 한 행 + R2 객체 하나 |
| `kind` | `thumbnail` |
| `metadata.derivation` | `list`(새 값, [검증](../src/lib/storage/validation.ts)) |
| `source_asset_id` | 카드가 보이는 이미지(`getMaterialImageAssetId`: 타일은 첫 텍스처, 제품은 대표 방향 사진) |
| 크기 | 긴 변 256px, 키우지 않음. 서버는 긴 변 512px까지만 받음 |
| 개수 | 원본 하나에 하나. 두 번째 업로드는 409(같은 batch의 조건 검사) |

- **불변 버전은 그대로다.** 자재 버전 payload에 필드를 더하지 않는다. `d1_material_assets` 참조도 바꾸지 않는다. 목록 이미지는 원본을 가리키는 파생 자산일 뿐이다.
- **찾기:** 원본 id로 `d1_assets_source` 인덱스를 따라간다(`LIST_IMAGE_OF`, [list-images.ts](../src/lib/d1/list-images.ts)). 원본 하나의 자식은 몇 개뿐이다.

**읽기:** 카드는 **원본 id**에 `size=list`를 붙여 요청한다.

| 경로 | 요청 | 권한 확인 |
| --- | --- | --- |
| 회원·관리자 | `GET /api/d1/assets?id=<원본>&raw=1&size=list` | 원본에 대해 지금과 같은 `readableAsset` |
| 관리자 프로젝트 | `GET /api/admin/project-assets?projectId=..&id=<원본>&raw=1&size=list` | 같은 `assets()` 경로 |
| 공개·게스트 | `GET /api/catalog/images?id=<원본>&size=list` | 원본에 대해 지금과 같은 `publiclyDisplayed` |

- 원본이 허락되면 그 원본의 목록 이미지 바이트를 보낸다. 없으면 원본 바이트를 보낸다. 응답 머리글 `X-SJN-List-Image: 1|0`이 어느 쪽인지 알린다.
- **권한·공개 범위는 넓어지지 않는다.**
  - 판단은 늘 원본으로 한다. 목록 이미지 자체 id로 읽으면 지금 규칙(`visibleAssetsQuery`는 요청 자산에서 자식 방향으로만 간다)에 따라 아무도 못 읽는다(시험: 회원 404).
  - 원본을 못 읽는 사람은 목록 이미지가 있어도 404를 받는다(시험).
  - 공개 경로는 원본이 지금 공개 자재의 표시 이미지일 때만 준다. 자재를 비활성화하면 404다(시험).
- `size`는 `list`만 받는다. 회원 경로에서는 `raw=1`과 함께여야 한다. 다른 값은 400이다.
- 캐시는 더하지 않았다. 카드 요청은 한 번에 하나이고, 같은 id의 **진행 중** 요청만 합친다(`sharedAssetReads`). 권한 반영 시점은 지금과 같다.

**쓰는 화면**
- 편집기 서랍 카드, 관리자 자재 카드: `AssetImage lazy size="list"` → 저장소 `assets.getListImage`
  - cloud·관리자 프로젝트·게스트 저장소가 구현한다.
  - 게스트는 이미 원본을 받은 이미지면 그 원본을 쓴다.
- 공개 `/materials` 카드: `images[0].url + '&size=list'`
- 장면(편집기 캔버스·3D·AI 입력)과 상세 창은 지금처럼 **원본**을 받는다(e2e: 게스트가 고른 타일은 `size` 없는 요청).

**만들기**
- **등록·수정할 때:** [자재 폼](../src/components/materials/material-form.tsx)이 저장에 성공한 뒤 `ensureListImage`를 기다리지 않고 부른다. 자재 등록·수정은 관리자만 한다(서버가 회원의 `create`·`update`를 403으로 막는다).
  1. `listImages({ids})`로 카드 이미지에 목록 이미지가 이미 있는지 묻는다(쿼리 2개·3행).
  2. 없으면 원본을 받아 줄여 올린다. 수정에서 이미지를 바꾸지 않았으면 1에서 끝난다.
  - 실패해도 저장은 성공이다. 빠진 것은 관리자 버튼이 채운다.
  - 두 탭이 동시에 올리면 두 번째는 409이고, 이를 "이미 있음"으로 처리한다.
- **기존 자재(관리자 버튼):** `/admin/materials`의 "목록 이미지 만들기"([list-image-backfill.tsx](../src/components/materials/list-image-backfill.tsx))
  1. `materials({operation:'listImages', cursor})`가 공용 현재 자재(활성 → 비활성)의 카드 이미지 id와 목록 이미지 유무를 48개씩 준다. 0009 요약의 `d1_list_recent`를 쓴다.
  2. 브라우저가 없는 것만 원본을 받아 줄이고 올린다. 한 번에 3개씩이다.
  3. "확인 n / 전체개, 새로 만듦 m개"를 보인다. 멈출 수 있고, 다시 누르면 있는 것은 건너뛴다.
  - 관리자의 개인 자재와 예시 자재(코드 안 파일)는 대상이 아니다. 개인 자재는 저장할 때 만들고, 없으면 원본을 쓴다.
- 서버는 이미지를 줄이지 않는다(Workers에 이미지 처리 바인딩이 없다). 줄이는 일은 브라우저 캔버스가 하고, 서버는 업로드를 지금처럼 검증한다. 검증 항목은 형식 판별, 크기, 원본 읽기 권한(`assetAssertion`)이다.

**정리:** [cleanup](../src/lib/d1/cleanup.ts)의 "참조 없음" 조건에 다음을 더했다. 목록 이미지(`derivation='list'`)는 원본이 `d1_material_assets`에 참조되는 동안 지우지 않는다. 원본을 아무 자재도 쓰지 않으면, 지금처럼 24시간 유예 뒤 지운다(시험).

## 3. D1 비용 (d1-query-budget)

`tests/d1-list-images.test.ts`의 비용 측정이다. 자재 100개와 500개(각각 목록 이미지 있음)에서 잰 값이 같았다.

| 경로 | 쿼리 | rows_read N / 5N | rows_written |
| --- | --- | --- | --- |
| 회원 카드 1장(`raw=1&size=list`) | 2 | 9 / 9 | 0 |
| 공개 카드 1장(`size=list`) | 2 | 5 / 5 | 0 |
| 백필 한 쪽(48개, 첫 쪽은 합계 포함) | 4 | 245 / 245 | 0 |
| 등록 뒤 있는지 확인(`listImages {ids}`) | 2 | 3 / 3 | 0 |
| 원본 메타 / 원본 바이트 | 1 / 1 | 5 / 5 | 0 |
| 목록 이미지 저장 1개(정리 기록 포함) | 9 | 13 / 13 | 18 |

- 카드 1장은 목록 이미지를 찾느라 쿼리 1개, 1행을 더 읽는다(공개 이미지는 페이징 결과의 1쿼리·4행에서 2쿼리·5행).
- 쿼리 계획: `SEARCH d1_assets USING INDEX d1_assets_source (source_asset_id=?)`, `d1_assets`의 `SCAN`은 없다(시험이 검사).
- 화면 요청 수는 변하지 않는다. 카드 1장에 요청 1개다(전에는 원본 메타 + 원본 바이트 2개). e2e(`material-paging`)의 "보이는 카드 수 이하"를 그대로 통과한다.

**운영 백필 추정(한 번, 관리자가 누를 때만)**

공용 현재 자재 약 960개(타일 930 + 제품 30) 기준이다.

| 항목 | 추정 |
| --- | --- |
| D1 읽기 | 쪽 21개 × 약 245행 + 자재마다 약 23행(원본 메타·바이트·저장) ≈ **2.7만 행** |
| D1 쓰기 | 자재마다 18행 ≈ **1.7만 행** |
| R2 쓰기 | 객체 960개(PUT 960회), 합계 약 10MB(256px WebP 하나에 약 10KB로 추정) |
| R2 읽기 | 원본 960회 |
| 관리자 브라우저 내려받기 | 원본 약 960 × 126KB ≈ 120MB |

- 쓰기 1.7만 행은 무료 한도(하루 10만 행) 안이다. 하지만 기능 목표(하루 5,000행)를 넘으므로 알린다. 한 번만 일어나고, 멈췄다 이어서 해도 이미 만든 것은 다시 쓰지 않는다.
- 이후 등록 1건마다 목록 이미지 1개(쓰기 18행)가 더 생긴다.

**카드 이미지 전송량(기대)**
- 첫 쪽 화면에 보이는 카드 10~16장은 지금 1.3~2MB다. 목록 이미지로는 약 0.1~0.2MB가 된다(256px WebP 하나에 약 10KB로 추정).
- 백필 뒤 실제 크기는 `SELECT SUM(json_extract(metadata_json,'$.size')) FROM d1_assets WHERE json_extract(metadata_json,'$.derivation')='list'`로 확인할 수 있다(원격 읽기는 승인 뒤).

## 4. 시험

- `tests/d1-list-images.test.ts`(5개)
  - 업로드 규칙: `thumbnail`만, 원본 필수, 512px 넘으면 400, 못 읽는 원본이면 404, 두 번째는 409
  - 읽기: 목록 이미지가 없을 때와 있을 때, 목록 이미지 자체 id는 404, `size` 검증
  - 공개: 비활성화하면 404. 개인 이미지는 다른 회원이 404
  - 정리: 쓰는 원본의 목록 이미지는 남고, 안 쓰는 원본의 목록 이미지는 지운다. 규칙을 빼면 시험이 실패하는 것을 확인했다.
  - `listImages`: 쪽, `ids`, 회원 403(쪽과 `ids` 모두), 잘못된 커서 400
  - 비용 N / 5N
- `e2e/list-thumbnails.spec.ts`(3개)
  - 관리자 버튼: 130개를 만들고, 다시 누르면 0개를 만든다. 쪽 요청은 4회다. 카드는 전에는 `X-SJN-List-Image: 0`, 뒤에는 `1`과 `image/webp`를 받는다.
  - 등록: 1600×800 텍스처로 새 타일을 등록하면 목록 이미지가 1개 생긴다. 원본 비율 그대로 긴 변 256px의 WebP다.
  - 공개·게스트 카드: 모든 카드 요청이 `size=list`이고 목록 이미지를 받는다. 고른 타일은 원본을 받는다.
- 기존 `material-paging` e2e의 요청 기록이 목록 이미지 요청(`raw=1&size=list`)도 카드 이미지 요청으로 센다.
- 기존 `material-images` e2e의 카드 색 비교는 WebP 손실 때문에 채널마다 ±3을 허용한다.

## 5. 배포 뒤 할 일

1. 배포가 끝나면 관리자 계정으로 `/admin/materials`를 열고 "목록 이미지 만들기"를 누른다. 이때 원격 R2·D1에 위 추정만큼 쓴다.
2. "끝 · 확인 n / n개"와 실패 0개를 확인한다. 실패한 자재 이름이 보이면 다시 누른다.
3. 다음 날 `npx wrangler d1 insights sjn --sort-by=reads --timePeriod=1d --limit=10`로 읽기 상위 쿼리를 확인한다.

## 6. 하지 않은 것

- 서버(Workers)에서 줄이기: 이미지 처리 바인딩이 없어 브라우저에서 줄인다.
- 상세 창·장면용 중간 크기 이미지
- 개인 자재 일괄 생성: 저장할 때만 만든다.
- 목록 이미지 다시 만들기(원본이 바뀌는 일은 없다. 새 이미지는 새 자산이다)
