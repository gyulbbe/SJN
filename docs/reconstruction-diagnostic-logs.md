# 재구성 진단 로그

사진 분석 테스트(/reconstruction-lab)에서 **진단 로그 JSON**을 누르면 최근 실행들을 한 파일로 받는다.
사진 본문은 포함하지 않으며 원본 사진을 함께 제공하면 미검출과 배치 보류를 구분해 점검할 수 있다.

- 최근 20회, 합계 최대 25MiB를 이 브라우저의 전용 IndexedDB에 보관한다. 새로고침 뒤에도 다운로드할 수 있다.
- 성공/실패/취소를 구분하고 실행 ID, 사진 이름/크기, SHA-256(읽기 성공 시), 공간 치수, 모델/규칙 revision, 재사용 출처를 기록한다.
- 성공: report.diagnosticSummary → counts / originCounts / outcomeCounts / commonBlockers / candidates.
- 후보별 candidateId와 fixtureId, 최초 보류/제외 지점, 단계·상태 code, 실제 이유와 evidencePaths를 연결한다.
- report.candidateTraces의 7단계 입력·출력과 pipeline/review를 함께 읽는다. trace-gap은 원인 미기록이며 미검출로 단정하지 않는다.
- report.runLog.events: 순번, ISO 시각, 상대시간, 현재 단계, 진행/체크포인트/종료. 단계 시간은 함수 경계의 경과시간이며 순수 AI 추론 시간이 아니다. 세부 측정 범위는 report.timing을 따른다.
- 실패/취소: failure.runLog에 마지막 단계, 이전 체크포인트, 오류 종류/내용/스택을 보존한다. 원래 모델 파싱 진단도 유지한다.
- 성공 로그의 큰 체크포인트는 같은 보고서 필드 경로로 연결해 중복 용량을 줄인다. 실패 로그는 부분 증거를 직접 보관한다.
- 실행 로그 최대 600개; 초과 이벤트/긴 값/깊은 값 생략은 명시한다. 이미지 본문, 바이너리, 인증 정보는 진단에 넣지 않는다.
- 저장 실패는 분석 결과를 실패로 바꾸지 않으며 logStorage에 이유를 남긴다. 현재 화면의 전체 보고서 JSON/실패 진단 JSON으로 메모리의 기록을 받을 수 있다.
- 저장 트랜잭션 실패 시 기존 보관 기록을 유지한다. 프로젝트/자재 저장소와 분리하며 자동 서버 전송하지 않는다.
- 과거 로그에는 없던 실행 시각·오류 단계를 소급해서 생성하지 않는다. 이 변경 후 새로 실행한 분석부터 보관된다.

실행 완료/PNG 생성은 품질 성공이 아니다. 사람이 확인한 원본과 비교해야 미검출·형태·상대 위치의 정확도를 판단할 수 있다.
이 로그 변경은 인식 모델이나 배치 규칙을 변경하지 않는다.
