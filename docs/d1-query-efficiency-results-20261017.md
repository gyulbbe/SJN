## 1. 원인과 바꾼 방식

### 1-1. 자산 가시성 (A·B·C)

이전 `visibleAssets` CTE는 요청과 관계없이 "볼 수 있는 자산 전체"를 만들었다.

- 기본 집합: 내 자산과, 공유 자재 버전이 참조한 자산이다. 관리자 프로젝트 범위에서는 프로젝트·관리자 프로젝트 참조와 보이는 버전의 자산이다.
- 확장: 보이는 자산의 원본(`source_asset_id`)을 재귀로 더했다.
- 재귀 CTE라 바깥 `WHERE a.id=?`가 안으로 내려가지 않았다. 그래서 1회 비용이 전체 자산 수에 비례했다. 업로드 검사는 원본이 없을 때도(빈 목록) 전체 집합을 만들었다.

새 [`visibleAssetsQuery(ctx, refs)`](../src/lib/d1/database.ts)는 확인할 id 목록(JSON)을 받는다.

- 요청한 자산에서 파생 자산 쪽(`source_asset_id`를 거꾸로, 삭제 중 제외)으로 내려가며 각 자산이 "직접 보이는지"를 상관 EXISTS로 본다. 직접 보이는 자산을 만나면 그 아래로는 더 내려가지 않는다.
- 판단은 이전과 같다. 자산 X는 X 자신이나, 삭제 중이 아닌 사슬로 이어진 X의 파생 자산 중 하나가 기본 집합에 들면 보인다.
- 관리자 범위의 "보이는 버전"도 전체 집합을 만들지 않는다. 확인할 버전 하나에 대해 조건을 본다.
- 사용처 네 곳(`readableAsset`, `assetAssertion`, `validateReferences`, `checkMaterialAssets`)은 refs만 넘긴다. 바깥 SQL과 batch 안의 `INSERT INTO d1_checks … SELECT` 형태는 그대로다.

### 1-2. 버전 가시성

- `visibleVersionsQuery(ctx, refs)`도 요청한 버전만 본다.
- 관리자 범위는 이전에 모든 공개 현재 버전을 집합으로 만들어 1회 963~2,910행이었다. 이제 3~40행이다.
- 회원 범위는 이전에도 SQLite가 CTE를 접어 넣어 참조 수에 비례했다(3~30행). 이제 4~40행이다. 같은 규칙으로 맞추면서 참조 1개당 1행가량 늘었지만 데이터 크기와 무관하다.
- 관리자 프로젝트의 자재 목록(`list`)은 목록 자체가 집합이라 기존 CTE(`adminVisibleVersionsSet`)를 그대로 쓴다.

### 1-3. 공개 이미지 (G·H)

- [`publiclyDisplayed`](../src/lib/catalog/public.ts)는 그 자산을 참조하는 버전(`d1_material_assets`)에서 출발한다.
- 현재 공개 버전인지와 직접 표시 이미지인지(`directDisplay`, `source_asset_id`는 따라가지 않음)는 그대로 본다.
- 처음에는 JOIN 순서만 바꿨는데, SQLite가 여전히 `d1_materials_public`(세 칸 동등 조건)부터 공개 자재 전체를 읽었다. 측정에서 나아진 것이 없어 `CROSS JOIN`으로 순서를 고정했다. SQLite는 CROSS JOIN의 왼쪽을 바깥 반복으로 둔다.
- 같은 이유로 자산·버전 조건의 JOIN도 `CROSS JOIN`으로 고정했다. 운영에 통계(`sqlite_stat1`)가 생겨도 계획이 바뀌지 않는다.
- 쿼리 계획(공개 배치 이미지, 자재 1개)

  | | 순서 |
  | --- | --- |
  | 이전 | `SEARCH m USING INDEX d1_materials_public (purpose=? AND scope=? AND active=?)` → 버전 PK → payload `json_each` 3번(이미지마다 공개 자재 전체) |
  | 지금 | `SEARCH r USING INDEX d1_material_assets_asset (asset_id=?)` → 버전 PK → payload `json_each` → `SEARCH m USING INDEX sqlite_autoindex_d1_materials_1 (id=?)` |

- 이 출발점은 두 불변식에 기댄다. 둘 다 코드와 원격 점검으로 확인했다.
  1. **자재의 현재 버전은 그 자재의 버전이다.** `current_version_id`를 쓰는 곳은 [materials.ts](../src/lib/d1/materials.ts)의 INSERT·UPDATE 둘뿐이고, 같은 batch에서 그 자재의 버전을 만든다. 원격 점검: 어긋난 자재 0개.
  2. **버전이 표시하는 이미지는 모두 `d1_material_assets`에 있다.** D1 도입(705eb3f, 2026-09-17) 이후 모든 저장이 같은 입력에서 payload와 `materialReferences`(cover·imageAssetIds·textureAssetIds·views)를 만들고, 같은 batch에서 참조를 넣는다. 원격 점검: 공개 현재 버전 928개의 표시 참조 932개 중 빠진 것 0개.

### 1-4. 재시도 기록 정리 (E)

- [`0008_query_indexes.sql`](../migrations/d1/0008_query_indexes.sql)이 `d1_mutations(owner_id,created_at)` 인덱스를 더한다.
- 이전에는 PK `(owner_id,request_key)`나 단독 `created_at` 인덱스로 그 소유자의 기록 전체를 읽었다.
- 준비 검사(`checkD1Storage`)에는 넣지 않았다. 인덱스가 없어도 결과는 같고 읽는 행만 많다.

## 5. 측정했지만 바꾸지 않은 것 (제안)

### D. 카탈로그 읽기 (`readCatalog`)

- 요청 하나에 한 번만 읽는다. 같은 요청 안에서 두 번 읽는 곳은 없었다.
- 부르는 곳
  - 자재 저장(`resolveCatalogInput`): 1일 약 930회
  - 공개 목록(`publicMaterials`)
  - 관리자 분류 관리(`includeInactive`)
- 1회 118행(옵션 76 + 하위 분류 42)이고 하루 약 13만 행이다.
- **제안(구현 안 함):**
  - 자재 저장에서 고른 id만 읽기(`WHERE id IN (…)`, 1회 약 5행). 결과는 같다.
  - 요청 사이 캐시는 관리자 수정 즉시 반영 규칙과 부딪쳐 권하지 않는다.

### F. 세션·역할 조회

요청마다 세션 1~2행과 상태·역할 1~2행을 읽는다. 하루 3.9만 행(한도의 0.8%)이다. 실행 횟수는 많다.

- **역할 폴링이 컴포넌트마다 따로 돈다.** `useSharedCatalogAdmin`([shared-access.ts](../src/components/materials/shared-access.ts))을 6개 컴포넌트가 쓰고, 각자 30초 폴링·포커스·표시 전환 때마다 `/api/d1/role`을 부른다.
  - 로컬 개발 서버의 관리자 자재 화면에서 한 번에 3회, 자재 수정 창을 열고 닫는 동안 7회 불렸다.
  - 제안: 탭당 하나의 구독으로 묶는다. 서버가 요청마다 역할을 확인하므로 보안 동작은 같다. 비용은 훅을 컨텍스트로 옮기는 수정이다.
- **자산 하나에 요청이 둘이다.** 클라이언트 `assets.get`([cloud.ts](../src/lib/repositories/cloud.ts))은 메타 요청과 raw 요청을 따로 보내고, 서버는 각각 세션·권한을 확인한다. 캐시가 맞으면 raw는 건너뛴다.
  - 편집기를 열 때 같은 자산의 메타를 4번 다시 묻는 것도 보였다.
  - 제안 1: 같은 페이지에서 진행 중이거나 방금 끝난 메타 요청을 합친다. 몇 초 안의 권한 회수 반영이 늦어질 수 있다.
  - 제안 2: raw 응답에 contentHash(ETag)를 실어 조건부 요청 하나로 줄인다. 캐시 규칙을 바꿔야 한다.
- Better Auth 세션 쿠키 캐시처럼 정지·만료 반영 시점을 바꾸는 방법은 쓰지 않았다.

### 목록 크기

목록 자체라 바꾸지 않았다. 공용 자재 수에 비례하는 목록이 남는다.

- 공개 `/materials` 목록: 1회 4,908행(5배면 24,108행)
- 공개 배치 목록: 7,680행
- 회원 자재 목록: 2,880행

방문이 늘면 이것이 다음 한도 요인이다. 선택지는 쪽 나누기, 공개 목록 응답 캐시(Cache API, 짧은 TTL·관리자 변경 시 무효화), 목록용 요약 열이다.

## 6. 데이터 증가 원인

- 7일 쓰기(자재 628, 버전 1,045, 자산 1,548, 참조 937)는 거의 모두 **관리자 공용 타일 등록**이다.
  - 원격 기준 10-10 이후 공용 카탈로그 자재 914개, 버전 928개, 원본 사진 932장, 파생 텍스처 919장이다.
  - e2e는 격리 Miniflare만 써서 원격에 쓰지 않는다.
- 타일 한 장을 등록하면 이렇게 쌓인다.
  - 자산 2개: 원본과 텍스처. [`importImage`](../src/lib/images.ts)가 원본과 파생 텍스처를 함께 올린다.
  - 자재 1, 버전 1, `d1_material_assets` 1(텍스처), 버전 옵션 약 4
  - 업로드 검사 2회, 자재 저장 확인 1회
- **정리 여부**
  - 버전은 불변이라 옛 버전과 그 자산을 지우지 않는다.
  - 원본 사진은 파생 텍스처가 가리키므로 정리 대상이 아니다(`cleanup.ts`의 `child.source_asset_id`).
  - 프로젝트용 개인 자재(`purpose='project'`)는 프로젝트를 지워도 남는다(지금 25개).
  - 재시도 기록은 24시간 뒤 소유자별로 지운다.
- **판단:** 지금 규모(7.8MB)는 정상적인 카탈로그 증가다. 이번 쿼리 수정 뒤에는 권한 확인 비용이 데이터 크기와 무관하므로 정리 정책을 바꿀 필요가 없다.
- **선택지(사용자 결정)**
  1. 그대로 둔다(권장).
  2. 쓰이지 않는 프로젝트용 자재·자산을 정리하는 작업을 따로 만든다.
  3. 텍스처 등록에서 원본 사진을 따로 남기지 않는다(업로드 흐름 변경).
- **발견:** 정리 후보 검색(`cleanup.ts`의 `SELECT … LIMIT 4`)은 그 소유자의 오래된 자산을 참조 확인 3개와 함께 훑는다. 관리자처럼 대부분 참조된 자산을 가진 소유자는 1회에 자산 수 × 수 행을 읽을 수 있다. 프로젝트 삭제 때만 불려 이번 통계에는 나오지 않았다. 측정·수정하지 않았다.

## 7. 같은 결과 증명

[`tests/d1-visibility-equivalence.test.ts`](../tests/d1-visibility-equivalence.test.ts)가 옛 SQL 고정 사본과 지금 코드를 같은 Miniflare D1에서 나란히 돌린다. 마이그레이션은 0001~0008 실제 파일을 쓴다.

- **무작위 그래프 요소**
  - 소유자 4명
  - 공유·개인·프로젝트용·비활성 자재, 자재당 버전 1~3개(현재가 아닌 옛 버전 참조 포함)
  - 타일 텍스처, 방향 사진(옛 방향 이름 `위`·`오른쪽 측면`), 대표 이미지만 있는 자재, imageAssetIds만 있는 옛 형식, 표시되지 않는 product3d 참조
  - `reconstruction` 객체와 명시적 `null`
  - 깊이 0~4의 파생 사슬과 가지, 중간·뿌리 `deleting=1`
  - 프로젝트 자산·버전, 다른 관리자의 관리자 프로젝트 자산·버전
  - 없는 id, 중복 id
- **범위:** 회원 4명 + 관리자 프로젝트 2개 × 관리자 2명
- **비교 항목**
  - 모든 id(없는·중복 id 포함)에 대한 보이는 자산·버전 집합
  - 앞 3개 seed는 실제 함수로 한 건씩 더 비교했다.
    - 단건 `readableAsset`, `getVersion`
    - 실제 batch로 돌린 `assetAssertion`·`versionAssertion`의 CHECK 실패 여부
    - `validateReferences`
    - `checkMaterialAssets`의 결과 행(중복 포함)
    - `publicImage` 응답 상태, `publicPlacement`의 목록·단건 JSON. 같은 코드에 옛 조건을 바꿔 넣은 DB로 비교했다.
- **결과(`SJN_EQ_SEEDS=60`, 최종 SQL 기준):** 불일치 0. 386초 걸렸다.

  | 항목 | 수 |

  | 그래프 | 60개 |
  | 범위 | 480개 |
  | 자산 id 판정 | 28,480건 |
  | 버전 id 판정 | 14,544건 |
  | 실제 함수 단건 | 288건 |

- **기존 테스트 데이터 한 곳 수정:** `d1-catalog`의 "대표 이미지 … 위·아래" 시험은 옛 버전에 `위` 사진을 넣으려고 `payload_json`만 고치고 `d1_material_assets`를 넣지 않았다. 실제 저장은 늘 그 행을 넣는다(불변식 2, 원격 점검 0). 그래서 시험 데이터에 그 행을 더했다. 시험이 검사하는 동작은 바뀌지 않았다.
