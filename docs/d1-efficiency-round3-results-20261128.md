# D1 사용 줄이기 3차: 요청 수와 반복 확인 (2026-11-28)

[작업 프롬프트](prompts/d1-efficiency-round3.md)의 0단계로 운영 통계와 화면별 요청 수, 요청 1회 비용을 재고, 사용자 결정에 따라 네 가지를 바꿨다.

- **A:** 역할 확인을 탭당 하나로

- **C:** 공개 이미지 브라우저 캐시 5분
- **D:** 준비 검사 재사용 5분

권한과 공개 범위 판단은 바뀌지 않았다. 새 migration은 없다.

## 3. 사용자 결정 (2026-11-28)

- **고칠 것:** A, I. B(304 한 요청)와 F는 이번에 하지 않는다.
- **C:** 공개 카탈로그 이미지는 **5분**(`public, max-age=300`). 회원 이미지(`/api/d1/assets`)는 그대로 `private, no-store`다.
- **D:** 성공한 준비 검사는 같은 isolate에서 **5분** 재사용한다. 검사 문장 수도 함께 줄인다.

## 4. 바꾼 것

### A. 역할 확인을 탭당 하나로

- [src/lib/admin-role.ts](../src/lib/admin-role.ts): 탭 하나에 저장소 하나다.
  - 컴포넌트가 몇 개든 확인 요청은 한 번에 하나다. 진행 중인 요청이 있으면 합친다.
  - 30초마다(보일 때만), 포커스나 다시 보일 때 확인한다.
  - `sjn-admin-role-changed`가 오면 진행 중인 요청을 버리고 바로 다시 확인한다.
  - 마지막 컴포넌트가 사라지면 멈춘다.
  - 나중에 열린 창(자재 수정 창 등)은 요청 없이 마지막 답을 쓴다. 다른 계정의 답은 쓰지 않는다.
- [shared-access.ts](../src/components/materials/shared-access.ts): `useSharedCatalogAdmin`이 이 저장소를 `useSyncExternalStore`로 읽는다.
- 서버는 지금처럼 요청마다 역할을 확인한다. 이 훅은 화면 표시용이라 보안 동작은 같다.
- **E(세션 확인)와는 묶지 않았다.**
  - 세션 확인은 5분 주기이고, 응답이 `ACCOUNT_CHANGED`·`account_suspended` 처리의 기준이다.
  - 역할을 세션 응답에 실으면 Better Auth 응답 계약을 바꿔야 하는데, 줄어드는 요청은 5분에 1개다.

### I. 공개 배치 이미지 확인 (새 후보)

- [placementsOf](../src/lib/catalog/public.ts)는 한 쪽(48개)의 표시 이미지마다 "지금 공개된 어떤 버전이 이 이미지를 보이는가"를 확인한다. 옛 쿼리는 이미지를 쓴 **모든 버전**(옛 버전 포함)을 차례로 읽었다. 그래서 버전이 많은 운영에서 1회 평균 776행이었다.
- 새 `publicImageRows`가 확인하는 방법은 다음과 같다.
  - 손에 든 (공개 버전, 이미지) 짝마다 그 이미지·참조 행·버전·자재를 기본 키로 한 번씩 읽는다.
  - 여기서 확인되지 않은 이미지만 옛 조건(어느 공개 버전이든)으로 한 번 더 묻는다.
  - 짝으로 확인되면 옛 조건도 참이고, 나머지는 옛 조건 그대로 묻는다. 그래서 결과는 옛 쿼리와 같다.
- 처음 시도(버전 id 목록으로 좁히기)는 이미지마다 버전 목록 전체를 훑어 1회 1,416행이 됐다. 더 나빠서 버렸다.

### C. 공개 이미지 브라우저 캐시 5분

- [publicImage](../src/lib/catalog/public.ts)의 성공 응답을 `public, max-age=300`(`PUBLIC_IMAGE_MAX_AGE`)으로 바꿨다. 오류 응답(400·404·503)은 그대로 `no-store`다.
- 자산 id의 바이트는 바뀌지 않는다. 비활성으로 바꾼 자재의 이미지는 이미 본 브라우저에 최대 5분 남는다. 서버는 바로 404를 준다.
- [게스트](../src/lib/guest/session.ts)의 공개 이미지 요청도 `cache: 'no-store'`를 빼서 같은 5분 캐시를 쓴다.
- `public`이지만 Worker 응답이라 Cloudflare 엣지에는 캐시되지 않는다. 엣지 캐시(Cache API)는 무효화 규칙이 필요해 제안만 한다.

### D. 준비 검사 재사용 5분과 문장 수

- [storageStatus](../src/lib/storage/server.ts)는 D1/R2 검사가 통과하면 그 DB·버킷 바인딩에 대해 `READY_REUSE_MS`(5분) 동안 다시 묻지 않는다.
  - 실패는 저장하지 않는다.
  - Google 로그인 같은 설정 값은 매번 새로 계산한다.
- 재사용 중에 하루 한도가 차도 "준비됨"으로 답한다. 화면은 다음 D1 요청의 `SERVICE_LIMIT` 응답으로 한도를 안다([한도 안내](service-limit-notice-results-20261018.md)). 이것을 시험으로 확인했다.
- migration 직후에는 최대 5분 동안 옛 결과가 보일 수 있다.
- [checkD1Storage](../src/lib/d1/database.ts)는 문장을 줄였다. 이 함수 자체는 재사용하지 않아서 기존 시험(컬럼·색인을 깨면 실패)이 그대로 돈다.
  - 스키마 버전 3개 읽기 → 1문장
  - 컬럼 확인 21개 batch → 1문장(행을 읽지 않는 하위 질의 21개를 묶음)
  - 무엇을 잡는지는 같다.

## 6. 바꾸지 않은 것과 이유

- **B 자산 304:** 사용자가 이번에 하지 않기로 했다. 관리자 수정 창은 열 때마다 같은 자산의 메타·raw를 다시 받는다(3회 열면 각 3). 304 방식은 다음에 고를 수 있다.
- **F 정리 후보 검색:** 사용자가 이번에 하지 않기로 했다.
  - 쿼리 계획은 `d1_assets_owner_created` 색인에서 출발하고 `NOT EXISTS` 4개가 모두 색인을 쓴다.
  - 그래도 소유 자산이 모두 참조되어 있으면 자산마다 약 2행을 읽는다(650개에 1,308행). 프로젝트 삭제 때만 불린다.
- **J (새로 찾음):** 관리자가 다른 회원 프로젝트의 자산을 볼 때 메타·raw 요청마다 감사 기록을 써서 요청당 6행을 쓴다. 사진 10장을 열면 약 120행이다. 하루 쓰기 한도 10만의 0.1%로 작아서 측정만 한다. 감사 정책(읽기도 기록) 그대로다.
- **E 세션:** 5분 1회와 다시 보일 때 1회다. 그대로 둔다(A에서 묶지 않은 이유 참고).
- **G 상태 변경·수정 저장:** 11-04 측정(버전 20개에 210행 읽기)에서 바뀌지 않았다.
- **H 로그인 요청 제한:** 로그인 1회에 6행 읽기·9행 쓰기다. 양이 적어 그대로 둔다.
- 목록 쪽 쿼리(2·3·5위)는 쪽 크기에 묶여 있고 자재 수와 무관하다(10-22). 이번 범위가 아니다.
