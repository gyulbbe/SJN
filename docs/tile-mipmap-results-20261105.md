# 타일 텍스처에 밉맵 넣기: 결과 · 2026-11-05

가는 줄이 반복되는 타일(DWJ 9881·9922)과 벽돌 테두리가 있는 타일(ROMAN OLVIE-G)이 편집 화면 크기에서 굵은 띠와 얼룩으로 깨져 보였다. 원인은 두 렌더러가 타일 텍스처를 밉맵 없이 줄여 그린 것이다. 2D 합성과 3D 렌더러 모두 같은 규칙으로 밉맵을 써서 읽게 바꿨다.

- 저장 데이터, DB, API, 화면 조작은 바꾸지 않았다.
- AI는 부르지 않았다. 원격 D1은 쓰지도 읽지도 않았다.

## 1. 사용자 결정

| 질문 | 답 | 반영 |
| --- | --- | --- |
| Q1 작게 보일 때 줄무늬 | ① 실제처럼 곱게 | 단계 −0.25(아래 6절). 실제 DWJ 9881·ROMAN 벽을 편집 화면 크기로 렌더한 그림을 먼저 보내고 물었다 |
| 병합·push | 끝나면 main 병합과 push까지 | 처음 요청에 포함 |

- **Q1 값 조정:** 질문 그림의 ①은 −0.5로 그렸다. 답을 받은 뒤 합성 시험을 돌려 보니, −0.5에서는 화면 한계에 가까운 흑백 줄무늬가 다시 물결무늬로 깨졌다.
- **고른 값:** 같은 ① 안에서 −0.25를 골랐다. 두 그리기 방식(SwiftShader, D3D11)의 모든 시험을 넘은 값은 −0.25 하나였다. 실제 타일 6개에서 3배 참고 그림과 가장 가깝기도 했다.
- **화면 차이:** DWJ 9881에서는 −0.5와 −0.25를 눈으로 구분하기 어렵다(6절 그림).

## 2. 명세와 코드에서 다르게 확인한 것

- **명세의 "지금 상태":** 코드와 같았다.
- **3D 아틀라스:** 빈 칸을 자재 색으로 채우지 않는다. 그림을 `createImageBitmap`에서 줄임 품질 설정 없이 바로 그린다.
- **2D 셰이더의 미분:** `fwidth(mm)`를 조기 `return` 뒤에서 계산했다. 이웃 픽셀이 먼저 빠지는 흐름 안의 미분이라 값이 정해져 있지 않다. 이번에 미분을 `return` 앞으로 옮겼다.
- **아틀라스 크기를 보는 시험:** `tests/render-browser.ts`가 아틀라스 크기(미리보기 512px, 내보내기 2048px)를 확인한다. 그래서 텍스처 1장(칸 1개)은 여백 없이 크기를 그대로 두었다.
- **R2 읽기:** 렌더 버전을 올리면 프로젝트 목록이 R2를 읽는다. `ROOM_VIEWER_RENDERER_REVISION`이 `PROJECT_SUMMARY_PREVIEW_REVISION`에 들어가기 때문이다(8절).
- **기존 진단 자료:** 11-05 진단 하네스와 DWJ 원본 3장이 남아 있어 다시 썼다. 원본은 다시 받지 않았다.
- **줄무늬 방향과 아틀라스 줄임:** DWJ 9881은 가로 줄이다. 970×487 원본을 512² 칸에 넣으면 가로로 1.9배 줄어든다. 그래서 아틀라스 칸을 그릴 때도 `imageSmoothingQuality='high'`를 쓴다.
- **로컬 개발 DB:** DWJ 9881이 없다. 그래서 화면 확인은 e2e의 격리된 D1/R2에 시험 자재를 넣어 했다(9절). 로컬 개발 DB는 건드리지 않았다.

## 3. 원인과 바꾼 방식

공용 모듈 [tile-atlas.ts](../src/lib/render/tile-atlas.ts)를 2D([compositor](../src/lib/render/compositor.ts) `atlasFor`, `tileShader`)와 3D([surfaces](../src/lib/room-viewer/surfaces.ts) `ViewerTileCache`, `sjnTileColor`)가 함께 쓴다.

- **밉맵:** 타일 아틀라스를 `generateMipmaps = true`, `LinearMipmapLinearFilter`로 만든다.
  - 공용 `canvasTexture`는 그대로 두었다. 그래서 배경·마스크·명암·제품·천장 텍스처는 바뀌지 않는다.
- **이음매:** 끊기는 `tileUv`로 단계를 고르면 타일 경계에서 가장 흐린 단계가 골라진다. 그러면 경계마다 줄이 생긴다.
  - 그래서 이어지는 좌표의 화면 미분으로 단계를 정한다. 이어지는 좌표는 회전한 뒤의 mm를 타일 크기로 나눈 값이며, brick 밀기와 `mod` 전의 값이다.
  - 그다음 `textureGrad`로 읽는다. 아틀라스 좌표로 바꿀 때 `칸/아틀라스` 비율과 y 뒤집기를 미분에도 곱한다.
- **여러 무늬(아틀라스 칸 여러 개)**
  - 칸마다 여백을 두고, 가장자리 픽셀을 늘려 채운다. 여백은 칸의 1/16이며 2의 거듭제곱이고, 최소 4px이다.
  - 칸 크기는 여백의 배수로 맞춘다. 그래서 log2(여백) 단계까지 단계 경계가 칸 경계와 맞는다.
  - 화면 미분이 그보다 큰 단계를 고르면 미분을 줄여 그 단계에서 멈춘다(긴 축 기준). 그래서 이방성 필터의 긴 발자국도 여백 안에 머문다.
  - 텍스처가 1장이면 여백이 없고, ClampToEdge가 가장자리를 맡는다. 반 텍셀 자르기는 이제 필요 없어 뺐다.
- **감마:** 아틀라스를 sRGB(SRGB8_ALPHA8)로 올린다.
  - GPU가 선형으로 풀어서 거르고 밉맵을 만든다. 그래서 셰이더의 `decodeSRGB`·`sjnDecode`를 아틀라스 값에서는 뺐다.
  - 흑백 50% 줄무늬의 면 평균 밝기(선형, 정답 0.500)는 2D에서 0.452에서 0.500이 됐다(두 방식 모두 같다).
  - 비교로 sRGB 저장 없이 예전처럼 감마 값으로 밉맵을 만들어 보았다(D3D11 한 번, 커밋 안 함). 흑백 줄 평균이 0.310으로 어두워졌고, 깨짐도 75.7 → 41.3으로 절반 기준을 넘지 못했다. 리브 타일(주기 3~8px)도 면 밝기가 2~3% 어두워졌다. 그래서 sRGB 저장을 썼다.
  - 3D와 3배 참고 그림은 0.30이다. 512px 텍스처를 1024px 칸으로 키울 때 캔버스가 감마 공간에서 보간해서다(10절 한계).
- **단계 조절:** 미분에 `2^TILE_LOD_BIAS`를 곱한다(−0.25, 6절).
- **이방성:** 기기가 지원하면 최대 8배다(`capabilities.getMaxAnisotropy()`). 3D는 `ViewerTileCache`의 세 번째 인자로 넘긴다.
- **아틀라스 그리기 품질:** 칸을 그릴 때 `imageSmoothingQuality='high'`를 쓴다.
- **그대로 둔 것:** 줄눈, 테두리 입체, 명암 보존, 광택 계산은 바꾸지 않았다.

## 4. 시험 방법

### 합성 시험 [tile-mipmap-browser](../tests/tile-mipmap-browser.ts)

- **방법:** 캔버스로 그린 텍스처를 기본 방의 세 벽에 붙인다. 2D·3D로 편집 화면 크기(1200×800)와 3배(3600×2400)를 그리고, 3배 그림은 선형 빛으로 3×3 평균을 내서 줄인다.
- **텍스처:** 가로 줄 주기 3·5·8px, 세로 줄, 흑백 줄, 벽돌 6장 시트, 단색, 결 있는 무늬 없는 타일, 주기 맞춘 그러데이션, 4색 변형
- **기준:** 바꾸기 전 코드로 `baseline`을 먼저 찍고 비교한다. SwiftShader와 `--gpu`(D3D11, RTX 4070 Ti) 둘 다 돌렸다.
- **판정:** 면 안쪽(각 벽에서 3px 안쪽)에서 잰다.

| 항목 | 기준 |
| --- | --- |
| 깨짐 | 줄무늬·벽돌의 \|편집 크기 − 3배 줄임\| 평균이 기준의 절반 이하 |
| 이음매 | 줄눈 0인 단색·그러데이션의 2차 차분이 2/255 이하. 기준 코드가 이미 그보다 크면 그 값 이하 |
| 변형 | 2D는 네 색 중 하나에서 ΔE 2 넘는 픽셀이 기준보다 많지 않음. 3D는 기준 그림과 3/255 넘게 다른 픽셀 0 |
| 무늬 없는 타일 | 면 평균 ΔE2000 1.0 이하 |
| 타일 밖 | 면 마스크를 2px 넓힌 바깥 픽셀이 기준과 완전히 같음 |
| 다른 경로 | 오류 없이 그려지고 타일 밖이 같음 |

- **다른 경로:** brick, 0·45·90°, 시작점, 부분 타일, SMC 천장, 표준 모형 변기와 그 그림자, 벽 홈·젠다이(3D), 사진 프로젝트(명암 보존 0.7), 3D 내보내기 겹쳐 찍기(4장), AI 입력(2D `exportImage`+`onRegionMask`, 3D `export`+`regionMask`)
- **바꾼 판정 세 가지:** 처음 기준 실행에서 판정 자체가 틀린 것을 찾아 고쳤다. 고친 뒤 기준을 다시 찍었고, 새 코드의 결과를 보기 전이었다.
  - **면 안쪽:** 벽 전체를 한 덩어리로 줄였더니 두 벽이 만나는 모서리가 남았다. 그래서 벽마다 따로 줄였다.
  - **그러데이션:** 원래 곡률만으로 옛 코드에서도 2차 차분 6이 나왔다. 그래서 진폭과 크기를 줄였다. 3D는 조명과 반올림만으로 옛 코드가 3이라, 기준을 "max(2, 기준값)"으로 했다.
  - **3D 변형:** 색도 판정은 조명 때문에 옛 코드에서도 5%가 섞임으로 잡혔다. 그래서 같은 위치의 기준 그림과 비교하게 바꿨다. 단색 칸은 섞임이 없으면 모든 단계에서 같은 색이다.
- **타일 밖을 2px 넓혀 보는 이유:** 2D 면 마스크 가장자리는 흐린 픽셀(`featherMaskCoverage`)이고, 3D는 MSAA 경계다.

## 6. 단계 값 비교

D3D11 기준이다. 실제 타일 합은 6개 자재 × 2D·3D 12개 값의 합이다.

| 단계 | 가로 줄 8px 2D | 흑백 줄 2D | 벽돌 시트 2D | 실제 타일 합 | 합성 시험 |
| --- | --- | --- | --- | --- | --- |
| 지금(밉맵 없음) | 18.0 | 75.7 | 7.7 | 88.0 | 기준 |
| 0 | 1.2 | 10.9 | 5.6 | 29.3 | 벽돌 시트 2D·3D 미달 |
| **−0.25** | 3.7 | 18.4 | 3.3 | **23.6** | 모두 통과 |
| −0.5 | 9.3 | 22.1 | 3.0 | 24.1 | 가로 줄 8px 2D 미달 |
| −1 | — | — | — | 31.0 | 재지 않음 |
| −2 | — | — | — | 60.6 | 재지 않음 |

- **0:** 삼선형 필터 특성상 3배 참고보다 조금 부드럽다. 그래서 벽돌 시트 가장자리의 밝은 줄이 넓어 보인다. 깨짐은 아니다.
- **−0.5와 가로 줄 8px:** 숫자가 미달이지만 실제로는 내 결과가 맞다. 편집 크기에서 거의 균일한 회색인데, 그 주파수에서는 3배 참고 그림이 오히려 깨진다(`test-results/tile-mipmap/h8-bw8-n05.png`).
- **−0.5와 흑백 줄:** 흑백 줄은 −0.5에서 물결이 눈에 띄었다.
- **고른 값:** −0.25가 두 방향의 문제 사이에서 모든 판정을 넘었다.

## 7. 성능

편집 화면 1200×800, 15장 중앙값이다. 1px을 읽어 GPU가 끝나기를 기다린다.

| 항목 | SwiftShader 전 → 후 | D3D11(RTX 4070 Ti) 전 → 후 |
| --- | --- | --- |
| 2D 한 장(줄무늬 / 무늬 없음) | 119 → 151 / 128 → 141 ms | 1.2 → 0.4 / 1.1 → 0.6 ms |
| 3D 한 장 | 113 → 147 / 117 → 144 ms | 1.7 → 0.7 / 1.5 → 0.6 ms |
| 이방성 끄면(후) 2D / 3D | 138 / 134 ms | 0.4 / 0.6 ms |
| 2D 준비(`setSnapshot`) | 523 → 588 ms | 395 → 399 ms |
| 첫 장(아틀라스 올리기와 밉맵 만들기) 2D / 3D | 263 → 327 / 1448 → 1519 ms | 30 → 39 / 21 → 51 ms |

- **GPU:** 한 장 시간이 늘지 않았다(밉맵은 텍스처 캐시에 유리하다). 3D 첫 장만 약 25~30ms 늘었다(1024² 아틀라스의 밉맵을 만들어서).
- **SwiftShader(소프트웨어 그리기):** 한 장에 약 13~34ms(약 11~30%) 늘었다. 1ms 기준을 넘는다.
  - 이유: 삼선형 필터와 이방성 필터를 CPU가 계산한다. 이 가운데 이방성 필터가 약 7~13ms다.
  - SwiftShader는 GPU 가속이 꺼진 기기에서만 쓰인다.
- **재지 못한 것:** Iris급 내장 GPU는 이 PC에 없어 재지 못했다.
- **메모리**
  - 밉맵으로 아틀라스 메모리가 약 1/3 늘어난다. 미리보기 512²이면 1MB → 1.4MB, 3D 1024²이면 4MB → 5.3MB, 내보내기 2048²이면 16MB → 21MB.
  - 무늬가 여러 장이면 여백으로 (1 + 2/16)² ≈ 1.27배가 더해진다.

## 8. 버전과 영향

- **버전:** `ROOM_VIEWER_RENDERER_REVISION`을 `room-view-v12-tile-mipmaps`로, `DESIGN_RENDER_REVISION`을 4로 올렸다. 3D 시안 카드와 2D 시안 미리보기 모두 새로 그려진다.
- **3D 재질 키:** 프로그램 키를 `sjn-room-world-tile-v3`로 바꿨다.
- **R2 읽기:** 렌더 버전이 프로젝트 요약 리비전에 들어간다.
  - 그래서 프로젝트를 다시 저장할 때까지 목록을 열면 프로젝트마다 R2 문서를 한 번씩 읽는다(`src/lib/d1/projects.ts` list).
  - D1 읽기·쓰기는 늘지 않는다. 이전 렌더 변경(v5~v11) 때와 같다.
- **AI 입력:** AI 변환 입력 그림도 같은 셰이더를 지나서 타일 부분이 함께 바뀐다(띠가 사라짐). 타일 밖은 같다.

## 10. 한계

- **시트로 등록된 자재:** 운영에 약 256개다. 벽돌 여러 장이나 모자이크 한 판을 한 장으로 등록한 자재(ROMAN OLVIE-G 등)는 그대로다.
  - 깨짐만 줄었다. 시트가 벽지처럼 반복되고, 앱 줄눈이 시트 둘레에 한 번 더 그려지는 문제는 남는다.
  - 고치려면 자재 등록을 바꿔야 한다(낱장 크기 + brick 배열, 모자이크 처리 방식 결정).
- **흑백 줄 극단 사례:** 순흑·순백 줄이 화면 주기 1.4px 안팎이면 옆벽에 옅은 물결이 남는다. 실제 자재에서는 보이지 않았다.
- **아틀라스 그리기:** 아틀라스 칸을 그릴 때 캔버스가 감마 공간에서 줄이거나 키운다. 텍스처 크기와 칸 크기가 다를 때 아주 가는 흑백 줄은 조금 어두워진다(3D 흑백 줄 평균 0.30, 정답 0.50). 밉맵은 선형이다.
- **바꾸지 않은 텍스처:** 제품 사진, 배경, 마스크, 명암, 천장 텍스처는 그대로 밉맵이 없다. 제품 사진도 작게 그릴 때 같은 깨짐이 생길 수 있다. 필요하면 같은 방식(제품 텍스처만 밉맵)을 따로 시험하기를 제안한다.
- **성능 측정 범위:** 성능은 이 PC의 GPU와 SwiftShader만 쟀다.
